# Quick Task 260817-j58 — Summary

## What was wrong

`countSheetElements` walked `xl/workbook.xml` with a bare `xml.Decoder.Token()`
loop and treated a clean `io.EOF` as "this parsed". `encoding/xml` does not
report a second top-level element as a second document root — it yields it like
any other element — so
`<workbook><sheets><sheet/></sheets></workbook><ext><sheets><sheet/></sheets></ext>`
published `sheet_count: 2` with complete coverage for a part that is not
well-formed XML.

## What was measured first

The stdlib was probed before the fix was designed, not reasoned about:

| document | `Token()` loop | `xml.Unmarshal` | `Decode` + require EOF |
|---|---|---|---|
| second root element | accepts, 2 top-level | **accepts** | rejects |
| non-whitespace text after root | accepts | **accepts** | rejects |
| non-whitespace text **before** root | accepts | **accepts** | **accepts** |
| whitespace / comment / PI / DOCTYPE / prolog around one root | accepts | accepts | accepts |
| truncated, mismatched end tag | syntax error | syntax error | syntax error |

Both conclusions changed the shape of the fix:

- `xml.Unmarshal` is not an oracle — it accepts multiple roots, so
  well-formedness could not be delegated to the stdlib.
- Leading character data is rejected by *nothing* in the stdlib, so it had to
  be handled here or it would have come back as a later round of the same
  finding.

## What changed

`internal/inspect/container.go` — `countSheetElements` now enforces one
document root and nothing outside it but the prolog, whitespace, comments and
PIs:

- `rootClosed` is set when `depth` returns to 0 on an `EndElement`;
- any `StartElement` while `rootClosed` → `ok=false`;
- any non-whitespace `CharData` at `depth == 0`, before or after the root →
  `ok=false`.

`ok=false` (never a count) is what the caller at `container.go:716` maps to
`sheet_count: nil` + `sheet_count_reason: malformed_input`, rather than to a
ceiling reason — the part was read in full, so no limit increase could repair
it.

## Tests

- `TestAnalyzeContainerMultipleTopLevelElementsPublishNoSheetCount` — the
  reported document plus six more shapes of the same class (second root in the
  SpreadsheetML namespace, three roots, root separated by whitespace, trailing
  text, trailing CDATA, leading text). Asserts both that no count is published
  AND that the reason is `malformed_input`, not a ceiling. All 7 failed before
  the fix.
- `TestAnalyzeContainerSingleRootWithLegalSurroundingsStillCounts` —
  over-rejection guard: prolog, comment + PI, DOCTYPE, and trailing
  whitespace/comment/PI still publish the real count.
- `TestEncodingXMLLenienceOnMultipleRoots` — pins the measured stdlib
  behavior, so a future Go release that starts rejecting multi-root documents
  fails loudly instead of leaving the old assumption available to be
  re-adopted.

## Follow-up: codex round 21 on `aeb0768`

The review round on this task's own commit raised two P2s, both closed:

**`3115bf9` — a regression of this task's own check.** The trim was
`bytes.TrimSpace`, which is Unicode-aware; XML's S production is
`(#x20 | #x9 | #xD | #xA)` and nothing else, so a UTF-8 NBSP outside the root
was erased by the trim and the document accepted — the check let through
exactly the leading garbage it was written to reject. Measured per rune:
`encoding/xml` passes NBSP (U+00A0), NEL (U+0085), U+2028 and U+3000 through as
CharData outside the root while `TrimSpace` erases all four; it rejects U+000B
and U+000C itself. `trimXMLSpace` trims the four legal characters only.

Lesson worth carrying: measuring `encoding/xml`'s *tokenization* was not enough
— the fix then leaned on a *second* stdlib helper (`bytes.TrimSpace`) whose
definition of whitespace was never checked against the format's. Measure every
borrowed definition, not just the parser.

**`900aba4` — WebP RIFF container size (`image.go:519`), not from this task.**
`scanRIFFChunkMetadata` checked each chunk against the buffer and never the
container, so a truncated WebP with a complete VP8X chunk ending at the
buffer's end reported `metadata_present: clean`. Both inequalities are now
structural; a truncated read *window* still resolves to a ceiling via
`composeMetadataStatus`'s precedence, with a test pinning that. WAV's identical
RIFF field is deliberately left alone (streaming writers leave it wrong by
design), as is convert's WebP dimension parser.

## Follow-up: codex round 23 on `12110cc` — the class, swept

Two P2s reported (`pdf.go:172` tail read, `image.go:38` dimension peek), both
instances of one accounting rule: `dispatchInspectFamilies` charges an operation
its allowance exactly ONCE (`tr.Consume(maxBytes)`) assuming the analyzer read at
most that much. Swept for the class instead of patching the two sites, and found
four:

| site | second read | reported |
|---|---|---|
| `pdf.go` | trailer tail, up to 64 KiB after the head took the whole allowance | yes |
| `image.go` | `convert.Dimensions`' independent 64 KiB peek | yes |
| `container.go` | `extractXLSXSheetCount`, another 256 KiB | **no** |
| `inspect_handlers.go` | `ClassifyCFB`'s walk, ~16 MiB against an 8 MiB default | **no** |

Closed in `1d154cd`. Two decisions worth keeping:

- **image.go was NOT fixed by deduction.** Both windows start at offset 0, so
  deducting double-charges the same bytes and gives any file smaller than the
  peek a zero-byte metadata window over bytes already in memory. Read the window
  once, use it twice. And when the shared window is shorter than the peek the
  parser would have taken alone, its failure must be reported as OUR ceiling —
  a naive clamp would have re-created the `malformed_input` misattribution
  PR9R16 fixed on this same path two rounds earlier.
- **CFB is bounded from the outside** (`inspect.BudgetedReaderAt`), because
  `ClassifyCFB` is shared with the conversion path where no allowance exists.
  A truncated walk now reports unknown/work_ceiling_bytes for all three CFB
  codes instead of publishing `ole_cfb_unclassified` as a Finding.

The test pins the property, not the fixes: a counting reader asserts each family
requests no more than its allowance. Pre-fix it measures **64314 bytes on a
4096-byte allowance** — a 15x overshoot, the reviewer's "many times the
configured limit" measured rather than predicted.

## Follow-up: codex round 24 on `1d154cd` — the gap my own sweep left

One P2 (`container.go:157`): the container analyzer called `zip.NewReader` on
bytes `detectInspectFormat` had already parsed via `SniffContainer`, so an
accepted OOXML/ODF upload walked its attacker-controlled central directory
twice — up to ~184 KiB of unaccounted reads on top of the part reads the new
shared budget does track.

**This one was mine to have caught.** The round-23 sweep shipped with a test
comment reading "archive/zip's own central-directory reads are outside this
allowance by design" — I scoped out exactly the read that was then reported. The
design it appealed to did not exist; it was an assumption written while closing
the very class it belonged to.

It also violated a rule already in the code: `SniffContainer`'s doc comment says
"never re-parse the central directory more than once per upload". An earlier
round deduplicated the *sniff* and stopped one step short — handing over the
result without the reader left the second caller no way to honor it.

Closed in `909e7e6` by reuse rather than accounting: `SniffContainerReader`
returns the `*zip.Reader`, threaded detection → dispatcher → analyzer. Measured
on a 2000-entry docx: analysis asks for **127 bytes** with the handoff vs
**121310** parsing it itself — a 121183-byte saving, exactly the sniff's own
cost. The test is differential (the nil-reader fallback is the control) and
requires both paths to return an identical FamilyResult.

Lesson to carry: a sweep's own scoping comments are claims like any other. "X is
out of scope by design" needs the design cited, or it is just an assumption
wearing a justification's clothes.
