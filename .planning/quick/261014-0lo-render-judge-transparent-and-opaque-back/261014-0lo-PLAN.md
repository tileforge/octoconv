# Quick 261014-0lo: the 3D render judge gives one verdict on both backgrounds

## Objective

Phase 76-02 (`76-02-bounds.txt`, STOP on cell M2) found that the production judge `cadJudgeFacts`
(`internal/convert/cadpixel.go`) refuses the transparent render of an admitted sparse assembly (step-nauo
n=1518 on the 200 mm grid, draft mesh, iso 2048) with "transparent fraction 0.9564 is outside 0.05..0.95"
(`ErrCADRenderRejected`, mapped to `cad_empty_result`), while the opaque render of the same mesh passes as a
blob at ink fraction 0.0469. Same mesh, same view; only the background differs.

This is the class phase 75 fixed for DXF ("one definition of empty"): the verdict on a 3D preview must not
depend on the requested background, except for checks of the alpha channel itself. Fix the class: one
part-pixel definition, J1 to J4 computed identically on both backgrounds, and only alpha checks per route.

## Premise check (before any code)

Shipped image `octoconv-cad-worker:latest` (2026-10-13 build), `cad-corpus-gen.py --kind step-nauo` of
LinearSlide-MGN15x-Block on the 200 mm grid, `cad-mesh --quality draft`, `cad-render --view iso`, judged by
`cad-pixel-judge` built at HEAD 8b12a80:

|---|---|---|---|---|---|
| 4 | 1280 | ok blob, frac 0.0429 | refused, transparent fraction 0.9577 | 70337 / 69345 | identical |
| 4 | 2048 | ok blob, 0.0426 | refused, 0.9578 | 178723 / 177125 | identical |
| 16 | 1280 | ok blob, 0.0408 | refused, 0.9602 | 66857 / 65193 | identical |
| 16 | 2048 | ok blob, 0.0403 | refused, 0.9603 | 168959 / 166327 | identical |
| 64 | 1280 | ok blob, 0.0498 | refused, 0.9521 | 81619 / 78470 | identical |
| 64 | 2048 | ok blob, 0.0488 | refused, 0.9524 | 204823 / 199824 | identical |

So the refusal reproduces at n=4 (a 631 KB draft STL, seconds to render), at the default size.

Pixel comparison of the pairs (scratch tool, opaque pixel against the transparent pixel composited on white):

- The transparent render's alpha is binary: every pixel is alpha 0 or 255, none partial.
- The opaque image equals the transparent image's RGB plane exactly. The only pixels that differ after
  compositing are alpha-0 pixels whose RGB is not white: FXAA (`renderer.UseFXAAOn()`) blends edge colour into
  the neighbouring background pixels' RGB but leaves their alpha at 0. On the opaque PNG those fringe pixels
  are visible; on the transparent PNG they are not.
- Composited on white, the transparent part set is a subset of the opaque one; the difference is exactly that
  fringe: 1.4% to 3.9% of the opaque count at 1280, 0.9% to 2.4% at 2048. Box, margin and dark count are
  identical in all six pairs, and no fringe pixel is dark.

The two backgrounds also use two definitions today: opaque counts a pixel with a channel below 250, transparent
counts any pixel with alpha above 0. A lit face can reach 0.8 x (0.45 + 0.55 x 1.45) = 0.998 of white, so on the
opaque route a near-white face pixel (all channels 250 or more) is not a part pixel while on the transparent
route it is.

## Decisions fixed before any code

1. **One part-pixel definition.** A pixel is composited onto a white page (straight alpha:
   `c' = (c x a + 255 x (255 - a) + 127) / 255` per channel) and is a part pixel when a composited channel is
   below 250 (`cadBackgroundCutoff`); dark when all three are below 80. `cadMeasure` no longer takes the
   background. For an alpha-255 pixel this is today's opaque rule unchanged, so every opaque PNG the renderer
   writes (RGB, no alpha) is judged exactly as before. This is the white page phase 75 judges DXF emptiness on.
2. **J1 to J4 are shared and run first**, on both backgrounds, in the 3D judge and in the DXF drawing judge.
   Then the route's alpha checks, which are the only background-specific checks left:
   - opaque: no pixel is fully transparent (unchanged);
   - transparent T1: the PNG carries an alpha channel (unchanged);
   - transparent T2 (new, replaces `cadTransparentMin`): every pixel of the frame's outermost one-pixel ring
     has alpha 0, that is, the background a client asked to be transparent is transparent.
3. **`cadTransparentMin` / `cadTransparentMax` are removed.**
   - Max (at least 5% of the frame not transparent) is a "something is drawn" check. J1 (a part pixel exists)
     and J4 (a blob needs frac >= 0.02, a thin part needs dark pixels along its long side) already do that job
     on the part-pixel set, the same on both backgrounds. On the transparent route it was a second, stricter
     floor (5% against 2%), which is the M2 defect.
   - Min (at least 5% of the frame transparent) was the only check that a "transparent" PNG's background is
     transparent. J3 cannot do it, because an alpha-254 white background composites to white and holds no
     part pixel. Its job stays, as T2, defined on the alpha channel alone. T2 cannot disagree with the
     opaque verdict of the same model: it runs after the shared J3, which has put every part pixel at least
     3% of the size from every edge (and the renderer frames the model with a 6% margin), so the ring is
     background on both routes and T2 only asks whether that background is alpha 0.
   - `opaquePx == 0` on the transparent route ("no pixel is opaque") is removed: J1 on the composited pixels
     decides whether anything shows; a part drawn only in partial alpha that darkens the white page is
     visible content on both routes.
4. **Pre-registered tolerance for real render pairs** (same STL, view and size, opaque against transparent,
   judged by the new judge). Every pair must meet all of:
   - (a) the same verdict: both accepted with the same mode, or both refused by the same rule;
   - (b) BoxX, BoxY, BoxW, BoxH and Margin each differ by at most 1 px (the premise shows 0; any non-zero is
     reported);
   - (c) the same DarkCount;
   - (d) the transparent part set is a subset of the opaque part set;
   - (e) on blob frames, (Count_opaque - Count_transparent) / Count_opaque <= 0.10. On thin frames the gap is
     reported only (an FXAA fringe can rival a one-pixel line), and (a) still holds.
   A pair outside the tolerance stops the task and is reported; the tolerance is not relaxed after the fact.
   The residual gap is the renderer's FXAA fringe, which the client sees on an opaque PNG and does not see on
   a transparent one; it is documented, not hidden.
5. **Measurement corpus for the tolerance** (shipped image, scratch harness, both backgrounds of each STL):
   the five identity parts (LinearSlide-MGN15x-Block, LM8UU, SC8UU, V-Slot-20x20-100mm,
   2020_corner_bracket-Corner) in all seven views at 1280; LM8UU and V-Slot iso at 256, 512 and 2048;
   degenerate_rod, degenerate_plate, units_inch and stl_ascii_box iso at 1280 and 256; step-nauo n=4, 16 and
   64 iso at 1280 and 2048; the 71 W15 slice (`stl-ascii-nasa-sls-block1-1MiB.stl`) at 256, 1280 and 2048 if
   it is in the cache. Every row is recorded, the HEAD verdicts beside the new ones.
6. **Tests (pure Go, D-19).**
   - A differential test on synthetic scenes: each scene is drawn once with alpha coverage on a transparent
     page, and its opaque twin is the same scene composited on white. Cases: sparse (ink about 4.5%), dense,
     a thin band and an edge-on sliver, an empty frame, a full-coverage frame, anti-aliased edges in partial
     alpha, near-white lit faces, an FXAA fringe (alpha 0 with non-white RGB). Requires the same error text
     (or both nil) and the same J1 to J4 facts (Count, DarkCount, Frac, Dark, box, Margin, Mode) on both.
     The fringe case is exact too, because a fringe pixel composites to white on the transparent twin and is
     white on the opaque twin built from it.
   - Committed real-render pairs under `testdata/cad/render-bg/` (from the shipped image, provenance with
     argv and sha256): step-nauo n=4 iso 1280 (the sparse regression), one dense part, one thin frame. Required:
     both accepted, same mode, and the tolerance of decision 4.
   - The route alpha checks: T1, T2 (alpha-254 background, one opaque ring pixel, a ring pixel at alpha 1),
     opaque with one alpha-0 pixel; and the drawing judge on the same rules.
   - RED first: the new tests run against HEAD's judge and fail (evidence/red-*.txt).
   - Mutation probe on the new and changed checks (evidence/mutations.txt).
7. **Live.** At HEAD, through the compose stack of a fresh clone: render step-nauo n=4 (generated in the image
   as the liveproof generates n=1000) with `{"background":"transparent"}`, confirm `failed` /
   `cad_empty_result`. After the fix, a new liveproof row `background_transparent_sparse`: the same input,
   transparent, must be `done`, judged ok by the transparent judge with mode blob, and its opaque twin is

   fix (bundle clone, `octoconv-bundle.ttb` copied, untracked override `127.0.0.1:18090:8090`,
   `CAD_LIVEPROOF_API_BASE`, `tracked_dirt=0`): ALL PASS. Then `scripts/ci-local.sh helm gate race` from the same
   clone.
8. **Docs.** ERROR-CODES `cad_empty_result` row and docs/MEASUREMENTS.md: the preview is judged on a white
