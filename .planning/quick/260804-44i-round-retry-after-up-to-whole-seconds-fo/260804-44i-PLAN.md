<objective>
Round the daily-quota `Retry-After` value UP to whole seconds instead of truncating down.

`secondsUntilUTCMidnight` (internal/api/handlers.go:982) computes
`int(nextMidnight.Sub(now) / time.Second)`. Integer division on `time.Duration`
followed by `int(...)` truncates toward zero -- it is a floor, not a ceiling.
With 10.5 seconds left until UTC midnight it returns 10. A well-behaved client
that honours `Retry-After: 10` retries 0.5s *before* the daily quota window
resets and earns a second 429 for the identical reason.

Flagged by Codex review on open PR #5 and independently confirmed by reading the
code. This is a correctness bug in already-shipped D-11 code (plans 52-04/52-06,
same PR), not new feature work.

Purpose: a `Retry-After` a client obeys must land at or after the reset it points
at, otherwise it is actively misleading and provokes exactly the retry storm the
header exists to prevent.
Output: ceiling arithmetic in `secondsUntilUTCMidnight` + fractional-second test
coverage that the current three-case test entirely lacks.
</objective>

    // secondsUntilUTCMidnight returns the whole seconds remaining until the next
    // UTC midnight after now, clamped to a minimum of 1 -- a zero Retry-After
    // would invite an immediate retry into the same rejection. now is taken as a
    // parameter rather than read internally via time.Now() so this stays unit
    // testable.
    func secondsUntilUTCMidnight(now time.Time) int {
        now = now.UTC()
        nextMidnight := time.Date(now.Year(), now.Month(), now.Day()+1, 0, 0, 0, 0, time.UTC)
        secs := int(nextMidnight.Sub(now) / time.Second)
        if secs < 1 {
            secs = 1
        }
        return secs
    }

<decision_record>
**Chosen arithmetic:** integer ceiling via `(d + time.Second - 1) / time.Second`,
keeping the existing `if secs < 1 { secs = 1 }` clamp after it.

Rejected: `math.Ceil` on a float64 -- introduces a float import and float
rounding into an integer-nanosecond domain for no benefit.

**Empirically measured** (all eight cases run against both the old and the new
implementation before writing this plan; values below are observed, not derived
on paper):

| input (UTC)          | remaining      | old | new   |
|----------------------|----------------|-----|-------|
| 23:59:59.0           | 1s             | 1   | 1     |
| 00:00:00.0           | 86400s         | 86400 | 86400 |
| 12:00:00.0           | 43200s         | 43200 | 43200 |
| 23:59:49.5           | 10.5s          | 10  | **11** |
| 12:00:00.5           | 43199.5s       | 43199 | **43200** |
| 00:00:00.000000001   | 86399.999999999s | 86399 | **86400** |
| 23:59:59.9           | 0.1s           | 1   | 1     |
| 23:59:59.999999999   | 1ns            | 1   | 1     |

Two consequences the executor MUST internalize:

1. **The three existing cases are bit-identical old vs. new.** The fix is
   additive at second boundaries. If any of them changes, the edit is wrong.
2. **The two sub-second cases (0.1s, 1ns) pass BEFORE the fix as well**, because
   the clamp-to-1 masks them. They are clamp-composition regression guards, NOT
   bug-exposing cases. Only three of the five new cases are genuinely RED.

The clamp still cannot be removed: it also guards the defensive `d <= 0` path,
where rounding up yields 0. Ceiling and clamp compose without double-counting --
`0.1s -> ceil 1 -> clamp no-op -> 1`, not 2.
</decision_record>
