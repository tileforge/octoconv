**Замечание (`inspect_handlers.go:414`), дословно:** «A ZIP can keep both EOCD fields below these limits while still making `archive/zip.NewReader` parse far more than 4096 entries. Go reads central-directory headers until they stop and validates the result only modulo 65536, so an archive with 65,537 minimal 46-byte directory records can declare `entries=1` and `dirBytes=3,014,702`; this check passes, but `SniffContainer` then allocates and walks all 65,537 records. This directly bypasses the structural work bound, so count directory records with a bounded pre-scan rather than trusting the wrapping 16-bit EOCD count.»

Проверено оркестратором: `entries` действительно читается как `binary.LittleEndian.Uint16` (строка ~412), то есть переполняется на 65536. Арифметика ревьюера верна — 65537 × 46 ≈ 2.9 МиБ, что ниже границы 4 МиБ.

**Корень проблемы: граница доверяет числу, которое архив о себе объявляет, и которое физически не может быть больше 65535.** Любая правка, продолжающая опираться на это поле, останется обходимой.

Одно из двух, выбрать и обосновать комментарием:

  (а) **Вывести потолок записей из размера каталога, а поле `entries` не использовать вообще.** Минимальная запись central directory — 46 байт, поэтому `dirBytes / 46` — верхняя оценка числа записей, не зависящая от переполнения. Задать `inspectMaxZipDirBytes` так, чтобы `dirBytes / 46 <= inspectMaxZipDirEntries`: при 4096 записях это ≈ 184 КиБ. Реальный каталог office/epub-архива — обычно хорошо ниже 100 КиБ, так что запас остаётся. Дёшево: тех же ≤64 КиБ чтения хвоста, ноль декомпрессии, ни одного лишнего прохода.

  (б) **Ограниченный пре-скан:** считать подписи `PK\x01\x02` в области каталога до потолка. Точнее, но читает область каталога, то есть добавляет работу — и её тоже надо ограничить, иначе граница снова становится тем, что она ограничивает.

Вариант (а) предпочтителен: он не добавляет чтения вообще и убирает зависимость от объявленного поля целиком, а не уточняет её.

**Обязательно учесть zip64.** `dirBytes` — uint32, и значение `0xFFFFFFFF` в ZIP64 означает «смотри ZIP64 EOCD», а не «каталог размером 4 ГиБ». Такое значение обязано трактоваться как превышение границы, а не как большое число, прошедшее сравнение. То же для `entries == 0xFFFF`.

Если поле `entries` остаётся прочитанным для диагностики — записать комментарием, что на него НЕ опирается решение, чтобы будущий читатель не «упростил» проверку обратно.

**Согласование с `maxZipEntriesScanned`.** Комментарий первого круга обосновывал равенство границ. Если потолок записей теперь выводится из байт, перепроверить, что он по-прежнему не отвергает архив, который `AnalyzeContainer` спокойно бы просканировал, и обновить довод — либо честно записать, что согласование стало приблизительным и почему это допустимо.
