<objective>
Close the two remaining PR#2 review findings.

1. **The API accepts what the worker will certainly reject.** `NewServer` defaults the
   pandoc per-engine ceiling to 100 MiB while every deployment sets
   `PANDOC_MAX_INPUT_BYTES=3145728` (3 MiB). A 4 MiB markdown upload returns 202, burns
   an S3 object and a queue slot, then fails asynchronously in the worker with
   `input_too_large`. The API must honour the same configured byte limit the worker uses.

2. **UTF-8 is validated on a prefix that can end mid-rune.** `readSniffPrefix` reads at
   most `htmlSniffCap` (1 MiB) and then calls `utf8.Valid(buf)`. For any input larger
   than the cap the boundary can fall inside a multi-byte rune, so `utf8.Valid` returns
   false and a perfectly valid text/LaTeX file is rejected as unrecognized content. This
   hits `LooksLikeText` (md/rst/org) and `LooksLikeLaTeX` — real uploads AND pandoc's own
   output validation.

Purpose: stop wasting storage/queue capacity on uploads that are already known to be
over-cap, and stop falsely rejecting valid large markup files.
Output: a fail-fast pandoc upload gate driven by the deployed cap, a rune-safe sniff
prefix, a regression test per finding, and deployment/doc parity for the newly-shared
env var.
</objective>

    applied to a rune the CAP itself severed.

    Add an unexported helper — `trimPartialTrailingRune(buf []byte) []byte` — that scans
    backwards from the end over at most `utf8.UTFMax-1` bytes looking for the first
    rune-start byte (`utf8.RuneStart`). Once found at index i: decode the declared length
    from that lead byte and, ONLY IF that declared length is greater than 1 AND greater
    than `len(buf)-i` (i.e. the encoding demands more bytes than the prefix actually
    holds), return `buf[:i]`. In every other case return buf unchanged. Deriving the
    needed length from the lead byte — rather than trimming on any `utf8.RuneError` — is
    what keeps the fix fail-closed: bytes like 0xFF/0xFE declare no length at all, are
    never valid lead bytes, and must therefore survive into the utf8.Valid check and be
    rejected. Document that reasoning inline; it is exactly the "why" a future reader
    will need.

    Call the helper in readSniffPrefix immediately after `buf = buf[:read]` and its
    `len(buf) == 0` check, and ONLY when the prefix was actually severed by the cap:
    guard it with `size > cap && int64(read) >= cap`. Both halves matter — `size > cap`
    means more bytes genuinely exist beyond the prefix, and `read >= cap` means we really
    did stop at the cap rather than at a short read from a client that overstated size.
    When the whole file fits within the cap, no trim happens and a dangling lead byte
    stays a rejection, unchanged.

    Re-check `len(buf) == 0` after the trim and return `nil, false` if the trim emptied
    the buffer, so the NUL/UTF-8 checks below always see a non-empty slice.

    a rune boundary before validation, so a file larger than the cap is judged on
