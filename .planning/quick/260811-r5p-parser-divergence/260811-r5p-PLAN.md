**Замечание (`inspect_handlers.go:530`), дословно:** «Fresh evidence shows the structural bound is still bypassable because `archive/zip` does not necessarily start at the raw EOCD `directoryOffset`: it derives `baseOffset = eocdOffset - dirBytes - directoryOffset` and reads from `baseOffset+directoryOffset`. A 65,537-record directory can declare its honest full `dirBytes`, wrapped `entries=1`, and a `directoryOffset` pointing to only the final 100 records; this gate walks that short suffix and returns false, while `zip.NewReader` uses the negative base offset to start at the true beginning and parses all 65,537 records. Mirror the effective-offset calculation used by the parser before performing the bounded record walk.»

История этой границы — она обойдена ЧЕТЫРЕЖДЫ, и каждый фикс был предложен как окончательный:

1. Круг 1: граница по `entries` и `dirBytes`. Обойдена: `entries` — uint16, переполняется.
2. Круг 2: убрали `entries`, оставили `dirBytes`. Обойдена: `dirBytes` тоже подконтролен.
3. Круг 4: перестали сравнивать объявленные поля вообще, стали считать настоящие записи от `directoryOffset`. Обойдена: Go читает не от `directoryOffset`.
4. Круг 5: настоящее.

**Форма ошибки, общая для всех четырёх: мы ПРЕДСКАЗЫВАЕМ поведение чужого парсера, переписывая его по кускам.** Каждый круг находил очередной кусок, который мы переписали неверно. Пятый фикс обязан перестать быть предсказанием.

**Оркестратор прочитал исходники Go 1.26 (`$(go env GOROOT)/src/archive/zip/reader.go`) и нашёл, помимо названного ревьюером, ещё три расхождения. Ни одно из них ревьюер не называл — они найдены чтением, а не по подсказке, и это ровно та работа, которую надо было сделать в круге 2:**

- **`reader.go:624`** (названное): `baseOffset = directoryEndOffset - directorySize - directoryOffset`, чтение с `baseOffset + directoryOffset` (`:137`). При `baseOffset > 0` есть ветка отката (`:636-641`): если по СЫРОМУ `directoryOffset` лежит валидный заголовок, `baseOffset` сбрасывается в 0. То есть возможных стартов два, и какой выберется — зависит от содержимого.
- **`findSignatureInBlock`**: Go принимает EOCD, чей комментарий заканчивается ДО конца файла (`n+22+i <= len(b)`), и жёстко падает (возвращает -1) при УСЕЧЁННОМ комментарии. Наш локатор требует `offset+22+commentLen == size` ТОЧНО и при несовпадении продолжает сканировать назад. Значит, на архиве с коротким комментарием Go берёт EOCD X, а мы либо берём другой, более ранний EOCD, либо не находим ни одного и возвращаем `exceeds=false` — то есть пропускаем полностью. Это пятый обход, и он есть в коде прямо сейчас.
- **`readDirectoryEnd`**: Go ищет сначала в последних 1024 байтах, потом в последних 65 КиБ — двухступенчато. Мы читаем один хвост длиной `zipEOCDRecordMaxLen`. Совпадение окон надо проверить, а не предположить.
- **`readDirectoryEnd`** ZIP64-триггер: Go уходит искать ZIP64-локатор при `directoryRecords == 0xffff || directorySize == 0xffff || directoryOffset == 0xffffffff`. Обратите внимание: `directorySize` сравнивается с **0xffff**, а не с 0xffffffff. Наш код отвергает по `dirBytes == 0xFFFFFFFF`. Значит `dirBytes == 0xffff` (65535) заводит Go в ZIP64-ветку, а нас — нет.

**Вывод, который надо реализовать: перестать спорить о том, какое поле читать. Проверяться против настоящего парсера.**

Это можно себе позволить, потому что дорого только в тесте, а не в запросе. Требуемая форма:

- В ПРОДЕ гейт остаётся дешёвым и обязан быть НЕ МЕНЕЕ подозрительным, чем Go — снисходителен: любое расхождение, любая неоднозначность, любой вход, где мы не пришли ровно к тому же старту каталога, что и Go, — это `exceeds=true`, то есть честный `unknown`, никогда не `clean` и никогда 500.
- В ТЕСТЕ — дифференциальное свойство: для корпуса враждебных архивов запрещённая комбинация «`zip.NewReader` разобрал больше потолка записей, а гейт сказал `exceeds=false`» не встречается ни на одном входе.

Свойство, а не перечень сценариев, — единственное, что закрывает шестой круг, потому что оно не требует от нас угадать следующее поле.
