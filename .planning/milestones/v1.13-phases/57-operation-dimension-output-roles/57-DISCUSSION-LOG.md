## Приём operation в API

### Как клиент передаёт операцию при создании джобы?

| Option | Description | Selected |
|--------|-------------|----------|
| multipart-поле `operation` | Рядом с существующими `preset`/`target`/`opts`; один endpoint, один admission-гейт, один fail-closed путь | ✓ |
| Отдельный endpoint на операцию | `POST /v1/sanitize`; дублирует весь путь создания — тот класс дублирования, который Phase 56 схлопнула в воркере | |
| `operation` внутри `opts` | Без нового поля; но `opts` — per-engine схема со strict-parse, а движок ещё не известен в момент резолва операции | |

**Notes:** Пользователь по ходу спросил, как будут выглядеть названия операций. Ответ: закрытый словарь уже в схеме (`convert`/`extract`/`archive`/`inspect`/`render`), стиль — строчный однословный глагол, та же дисциплина, что у engine-классов и кодов ошибок. ROADMAP добавляет `sanitize` шестым.

### Какой набор значений `operation` API считает существующим?

| Option | Description | Selected |
|--------|-------------|----------|
| Только то, что есть в реестре | Источник истины — `convert.Default`; валидна операция с хотя бы одной зарегистрированной тройкой | ✓ |
| Весь DB CHECK-перечень | Go-константы зеркалят CHECK; точнее диагностика, но второй источник истины | |
| Отдельный явный allowlist в Go | Третий список, который надо держать синхронным с двумя другими | |

**Notes:** Пользователь оспорил предпосылку: «не ложится ли это в то, что каждый воркер при регистрации добавляет свой набор операций?» Проверено по коду и отвечено: такой модели в OctoConv нет. `convert.Default` — процесс-локальный синглтон, заполняемый `init()` на compile-time; воркеры лишь перерегистрируют сконфигурированные экземпляры в свою копию. Динамический реестр возможностей — SEED-010, отвергнут на уровне проекта (PROJECT.md, ретроспектива v1.12: ослабляет свойство безопасности). Зафиксировано как унаследованное решение в D-02.

### Каким кодом отклоняется неподдерживаемая тройка?

| Option | Description | Selected |
|--------|-------------|----------|
| Два кода: operation и пара | Новый `unsupported_operation` (нет операции) + существующий `unsupported_conversion` (нет пары под неё) | ✓ |
| Один `unsupported_conversion` | Вся тройка — один класс отказа, детали в `message`; ноль новых кодов | |
| Один новый `unsupported_operation` | Разводит один класс отказа по двум кодам по признаку «прислали ли поле» | |

### Явная `operation=convert` — тот же путь, что и отсутствие поля?

| Option | Description | Selected |
|--------|-------------|----------|
| Да, нормализация до ветвления | Пустое/отсутствующее → `convert` сразу после `FormValue`; ветвления по присутствию поля дальше не существует | ✓ |
| Да, но с трёхзначной семантикой | «Поля нет» → convert, «поле пустое» → 422; строже, но плодит ровно то ветвление, которое Pitfall 13 называет источником расхождения | |

### Два MCP-входа и референсный фронтенд — прокидывают `operation` в этой фазе?

| Option | Description | Selected |
|--------|-------------|----------|
| Нет — только REST | Пока операция одна, параметр в MCP-туле был бы мёртвой поверхностью | |
| Да — все три входа сразу | Опциональный параметр везде, чтобы Phase 60 трогала только движок | ✓ |

## Форма operation-aware реестра

### Как конвертер объявляет свою операцию реестру?

| Option | Description | Selected |
|--------|-------------|----------|
| Optional-интерфейс `OperationalConverter` | По прецеденту `ProgressConverter`; семь конвертеров и `converters.go` — ноль изменений | ✓ |
| Явный `RegisterOp(op, c)` | Операция видна в `converters.go`, но конвертер перестаёт отвечать за то, что он умеет | |
| Тройки в `Pairs()` | Самое прямое моделирование, но трогает семь реализаций и десятки тестов | |

### Чем доказывается дизъюнктность троек?

| Option | Description | Selected |
|--------|-------------|----------|
| Рантайм-отказ в `Register` + тест | Коллизия тройки → panic на `init()`, сервис не стартует; плюс тест по тройкам с identity-случаем `pdf→pdf` | ✓ |
| Только тест по тройкам | Продолжение прецедента v1.8/v1.10/v1.11; ноль изменений рантайма, защита остаётся CI-только | |
| Ошибка из `Register` без panic | Чище panic в `init()`, но требует правки всех вызовов регистрации — дифф шире всей остальной фазы | |

**Notes:** Выбор вскрыл конфликт, поднятый сразу: `cmd/av-worker`, `cmd/ocr-worker`, `cmd/pandoc-worker` намеренно опираются на last-write-wins для перерегистрации сконфигурированных экземпляров (несущих лимиты безопасности). Panic на коллизии убил бы старт всех трёх. Развязано следующим вопросом.

### Как отличить законную перерегистрацию от коллизии двух движков?

| Option | Description | Selected |
|--------|-------------|----------|
| Отдельный `Replace` | `Register` валится на занятой тройке; три воркера явно зовут `Replace` — намерение читается в коде, а не в 25-строчном комментарии | ✓ |
| Panic только при смене движка | Коллизия разрешена при совпадении `Engine()`+`Operation()`; воркеры не трогаются, но «безопасное перетирание» остаётся неявным правилом | |
| Пересмотреть решение | Откатиться к «только тест по тройкам» | |

### Когда в `GET /v1/formats` появляется новый ключ с деревом операций?

| Option | Description | Selected |
|--------|-------------|----------|
| Сразу, включая convert | Полное дерево `{operation → engine → pairs}`; `engines` байт-идентичен; клиенту и MCP есть откуда узнать список операций | ✓ |
| Только со второй операцией | Guarded на непустоту; ответ в этой фазе байт-в-байт сегодняшний, но параметр из D-05 некуда документировать | |
| Не в этой фазе | Минимальный дифф, но OPRN-01 явно требует «новое дерево операций отдельным ключом» | |

## Роли в ответе GET /v1/jobs/{id}

### Как отчёт (`role=report`) попадает в ответ?

| Option | Description | Selected |
|--------|-------------|----------|
| Массив `outputs[]` | Все выходы с `{role, ordinal, format, size_bytes, url}`; `download_url` всегда primary; покрывает будущие `preview`/`thumbnail` без новых ключей | ✓ |
| Отдельное поле `report_url` | Рекомендация Pitfall 3; структурно не спутать, но каждая новая роль — новый ключ | |
| Оба | Два представления одних данных — два места, где они могут разойтись | |

**Notes:** Появление `outputs[]` только при `len(outs) > 1` — не выбор, а следствие SC4 (байт-идентичность одновыходной convert-джобы). Зафиксировано без вопроса.

### Как презайнятся выходы в `outputs[]`?

| Option | Description | Selected |
|--------|-------------|----------|
| Все сразу (eager) | Готовый `url` в каждом элементе; один round-trip; N вызовов `PresignGet` вместо одного | ✓ |
| Метаданные без url | Ссылка только на primary; за отчётом нужен второй запрос к endpoint'у, которого не существует | |
| Eager, но только на `done` | То же, что первый, но явно внутри `case jobs.StatusDone` | |

**Notes:** Отмечено, что презайн уже сегодня живёт внутри `case jobs.StatusDone`, поэтому опрос активной джобы не делает ни одного вызова — третий вариант оказался тем же, что первый.

### Что делает API, если у `done`-джобы нет выхода с `role=primary`?

| Option | Description | Selected |
|--------|-------------|----------|
| Инвариант на записи | `MarkDone` не коммитит переход без ровно одного primary-выхода, в той же транзакции; API не ветвится | ✓ |
| 500 `internal_error` | Громко, не трогает транзицию, но дефект ловится на чтении, а не на записи | |
| Опустить `download_url` | 200 без ссылки; мягко, но клиент нигде не узнает почему | |

**Notes:** Выполнимость проверена по коду до фиксации: `AddOutput` (`worker.go:1317`) уже предшествует `MarkDone` (`:1328`) во всех семи движках. Планировщику передано предупреждение: проверка вписывается в замыкание `MarkDone`, НЕ в `Repo.transition` (инвариант PROJECT.md), и пиннинг-тесты Phase 56 должны пройти без изменений.

### На каких сценариях доказывается role-driven выбор?

| Option | Description | Selected |
|--------|-------------|----------|
| Обратный порядок + инверсия | `report` на ordinal 0, `primary` на 1 → `download_url` обязан быть primary; плюс инверсионный прогон (вернуть `outs[0]` — тест обязан упасть) | ✓ |
| Плюс retry/реконсилятор-интерливинг | То же плюс сценарии перезаписи строк через `ON CONFLICT ... DO UPDATE` в другом порядке | |

## Границы фазы: миграция и охват

### Когда `jobs_operation_check` расширяется до `sanitize`?

| Option | Description | Selected |
|--------|-------------|----------|
| Здесь, вместе с `role` | Одна миграция делает оба аддитивных шага; Phase 60 — чисто движок и очередь | ✓ |
| В Phase 60, с движком | Схема и код едут одним пакетом, как в `0009_ocr_engine.sql`/`0010_pandoc_engine.sql` | |
| Здесь, плюс `presets.operation` | Симметрично расширить идентичный CHECK у пресетов; пресеты для sanitize никто не заказывал | |

**Notes:** Осознанное следствие выбора — в базе появляется разрешённое значение, которое API отклоняет (реестр под него пуст). Расхождение без последствий, но требует комментария в миграции. `presets.operation` остаётся нерасширенным намеренно.

### Фиксируем ли инвариант «engine-класс обслуживает ровно одну операцию»?

| Option | Description | Selected |
|--------|-------------|----------|
| Да — инвариант с тестом | Роутинг реконсилятора, unique-лок TTL, очереди, KEDA и квоты остаются engine-ключевыми и корректны по построению — нулевой дифф в четырёх подсистемах | ✓ |
| Нет — делаем operation-aware | `(operation, engine)`-ключевание уже в этой фазе; готовность к двум операциям на одном движке ценой диффа там, где второй операции ещё нет | |
| Ни то, ни другое — только аудит | Назвать места в артефактах, решение оставить Phase 60 | |

**Notes:** Перед вопросом проверено и сообщено: `default`-ветка реконсилятора (`reconciler.go:377-386`) уже fail-closed (`unroutable_engine` + пропуск), поэтому misroute sanitize-джобы на convert-хендлер структурно невозможен уже сегодня — концерн #2 Pitfall 10 закрыт существующим кодом. Принятая цена инварианта: вторая probe-операция (SEED-013 `inspect`) потребует своего engine-класса или явного снятия инварианта.

### Как фиксируется «до-фазовый вывод» для пиннинга SC1/SC4?

| Option | Description | Selected |
|--------|-------------|----------|
| Golden-файлы, закоммиченные ПЕРВЫМИ | Отдельный первый коммит снимает сырые тела с сегодняшнего кода в testdata до любого нового кода; точный шаг 1 из D-10 | ✓ |
| Тест с инлайн-ожиданием | Проще читать в диффе, но ожидание пишется тем же человеком и в тот же момент, что и изменение | |
| Golden-файлы + инверсия | Как первый, плюс шаг 3 D-10: временно добавить `outputs[]`/`operations` — golden-тест обязан упасть на обоих | |

## Deferred Ideas

- **Deployment-profile awareness** — реестр отвечает «что скомпилировано», а не «что развёрнуто»; инсталляция с частичным флотом принимает джобу для неразвёрнутого движка и валит её непрозрачным `reconciler_exhausted` после ~3 циклов unique-лока, уже списав квоту и байты в S3. Поднято пользователем в ходе обсуждения области реестра. Собственная фаза.
- **`presets.operation` симметрично `jobs.operation`** — намеренно не расширяется в этой фазе.
- **Вторая операция на одном engine-классе** (SEED-013 `inspect` на `probe`) — упрётся в инвариант D-14 и в грань `client_usage_daily`.
- **`docs/openapi.yaml` enum + codegen (ERRC-V2-02)** — унаследовано из Phase 56, по-прежнему отложено.
