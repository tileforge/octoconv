Санировать PDF так, как это на самом деле работает, а не так, как выглядит убедительно.

Ресёрч построил фикстуру со всеми классами угроз и прогнал её. Прямой `gs -sDEVICE=pdfwrite` оставил **три из семи** маркеров: живое `/Type /Action /S /JavaScript`, дерево `/EmbeddedFiles`, и — опаснее всего — метаданные не удалились, а **мигрировали в XMP**: `/Info` перегенерирован, а заголовок и почта автора нашлись в XMP-пакете выхода.

Реализовать санитайзер PDF как ДВА вызова `runCommand`:

  1. `gs -dSAFER -sDEVICE=ps2write` — вход в промежуточный PostScript;
  2. `gs -dSAFER -sDEVICE=pdfwrite -dOmitXMP` — PostScript плюс `DOCINFO pdfmark` в итоговый PDF.

`-dSAFER` обязателен на ОБОИХ. Второй проход разбирает недоверенное производное первого, и послабление там — это разбор недоверенных байт без ограничений (см. Security Domain ресёрча).

Промежуточный файл живёт в серверном временном каталоге (`os.MkdirTemp`), удаляемом на всех путях возврата — форма из `ocrpdf.go`. Пути никогда не клиентские.

**Доккоммент обязан нести таблицу R1 с числами.** Не «мы выбрали два шага», а:

    вход           pdfwrite   через PS
    /OpenAction    0          0
    /AA            0          0
    /Launch        0          0
    /URI           0          0
    JavaScript     1          0     <- живой /S /JavaScript выжил
    EmbeddedFile   1          0     <- вложение выжило
    jane.doe@...   1          0     <- переехало в XMP

Причина именно такой формы записи: одношаговый вариант выглядит эквивалентным, читается лучше и встречается в большинстве статей. Аргумент «зачем два прохода» убедителен ровно до момента, когда видишь числа. Комментарий без чисел этот аргумент не переживёт — фаза 59 показала, что комментарий не умеет падать, поэтому числа дублируются тестом (Task 3), а комментарий объясняет, что тест защищает.

`-dOmitXMP` по D-09: верификатор будет проверять отсутствие `xpacket`, а не пустоту полей. Записать в доккоммент, почему пустых полей недостаточно: `pdf:Producer` называет точную версию ghostscript, `xmp:CreateDate` несёт часовой пояс сервера — утечка про инфраструктуру в каждом артефакте, который клиент дальше распространяет.

`sanitize.go` держит общую форму операции (интерфейс/диспетчер по формату), `sanitizepdf.go` — PDF-путь. Разделение как в `ocr.go`/`ocrpdf.go`.

Он ловит две вещи, которых не поймает ничто другое: попытку «упростить» до одного шага (тогда основной тест покраснеет, но причина будет неочевидна) и молчаливое изменение поведения ghostscript в новой версии (тогда покраснеет ИМЕННО этот тест, и станет ясно, что обоснование двух шагов надо перепроверить, а не что наш код сломался).

Skip при отсутствии `gs`, но с той же оговоркой, что в фазе 59: пропущенный тест не считается пройденным, и у гейта фазы должен быть режим, где отсутствие бинарника — провал.

**Тест одной ревизии.** SC3 требует не просто отсутствия объекта, а невосстановимости: PDF допускает incremental update, при котором старая ревизия целиком лежит в файле, а вырезанный объект достаётся чтением предыдущего `xref`. Тогда каждый тест выше остаётся зелёным — маркер в текущей ревизии действительно отсутствует, — а документ по-прежнему носит его в себе.

Потребовать, чтобы выход содержал РОВНО один `startxref` и ровно один `%%EOF`. Двухшаговый круг даёт это по построению: `ps2write` уничтожает структуру PDF полностью, восстанавливать нечего. Но «по построению» — это то же самое обещание в комментарии, которое фаза 59 уже видела неверным, поэтому оно проверяется.

Дополнительно: собрать incremental-update PDF (исходник плюс дописанная ревизия, скрывающая `/JavaScript`) и убедиться, что после санитации он тоже одноревизионный. Вход с ДВУМЯ ревизиями — тот случай, где различие между «переписали» и «дописали» видно, а на однореви́зионном входе оба поведения выглядят одинаково.
