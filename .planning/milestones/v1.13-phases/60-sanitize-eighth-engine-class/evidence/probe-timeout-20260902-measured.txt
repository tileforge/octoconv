THIS IS THE RUN PROBE_ENGINE_TIMEOUT=600s COMES FROM.

Read the analysis below before the numbers: the script's own p95-based
recommendation (602s) is NOT the derivation that was used, and the reason
matters.

WHAT THE COST ACTUALLY DEPENDS ON

Not bytes. Three independent points give a dead-linear per-page cost for
full-page scanned images:

     20 pages    39.738s   ->  1.987 s/page
    100 pages   200.437s   ->  2.004 s/page
    240 pages   481.308s   ->  2.005 s/page   (from the first run, same corpus)

A 219 KB document took 481 seconds while a 2.2 MB one took 39.7. Byte size is
irrelevant; page count is everything. A text page costs ~0.15s, a full-page
scan ~2.0s.

WHY p95 IS THE WRONG STATISTIC HERE

The script reports p95 = 200.437s and recommends ceil(p95 x 3) = 602s. That
number is an artifact of what is IN the corpus: mix in more multi-page scans
and p95 moves anywhere. When cost is determined by page count and the corpus
composition is chosen by hand, a wall-clock percentile measures the choice of
corpus, not the engine.

THE DERIVATION ACTUALLY USED

The shape OCR already uses in this project -- per-unit cost x a ceiling x a
margin -- applied to this engine's own measured per-page cost:

    PROBE_ENGINE_TIMEOUT = ceil(2.0 s/page x 200 pages x 1.5) = 600s

200 pages of full-page scans is a generous document bound. 600s sits 33% under
the 900s RECONCILER_ACTIVE_STALE_AFTER cap, which at 2.0 s/page is an absolute
ceiling of 450 pages no timeout may exceed.

Distinct from 65s/742s/744s/753s, and derived rather than picked.

WHAT THIS DOES NOT COVER, STATED RATHER THAN ELIDED

A document beyond roughly 300 pages of full-page scans will hit the timeout.
The right remedy is a page ceiling of probe's own, as OCR_MAX_PAGES is for OCR
-- so such a document is refused up front with an actionable code instead of
failing after ten minutes of work. Tracked as an open item.

ALSO ESTABLISHED BY THIS RUN

  * inspect-burst-pathological.pdf -- 2 MiB of the literal string
    "/JavaScrip", a marker-density fixture with a %PDF header, an %%EOF, and no
    objects, no xref and no pages -- is rejected by ghostscript in 0.127s. It
    is admissible through the API and costs nothing.
  * Memory is not the binding constraint: the container peaked at 84 MiB of
    its 1 GiB while pinned at 99.9% of 2 CPUs. This engine is CPU-bound.
  * The harness had no per-file bound (context.Background()) and the script
    buffered all output to a temp file, so an earlier run on a 3000-page
    synthetic sat silent at 100% CPU for 33 minutes with nothing on screen.
    Both are fixed: rows stream as they complete, and a file that exceeds the
    per-file budget is reported as exceeded-budget and excluded from the
    distribution rather than hanging the run.

  x3, not pandoc's x2: two ghostscript passes plus a parse give this
  pipeline a longer tail relative to its median than a single-subprocess
  engine has. A probe timeout is classified TRANSIENT (isProbeTerminal),
  so an over-tight bound spends retries rather than failing jobs -- but
  it spends them on every busy minute.

  This is a recommendation, not a decision. The share of timeout-driven
  retries that is acceptable for your load is not something this script
  can know.
