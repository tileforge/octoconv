PR #16, codex review round 1 -- every finding verified by RUNNING before any fix
================================================================================

P1: DETERMINISTIC TIMEOUTS WERE RETRIED  (internal/worker/descriptors.go)
-------------------------------------------------------------------------
Claim: a TeX document whose own execution exceeds the budget is a property of
the SUBMITTED PROGRAM, not of host load, so retrying it spends the whole budget
on something that can never succeed.

Verified. A document of 130 bytes:

    \count255=0
    \loop\advance\count255 by 1
    \ifnum\count255<1000000000
    \repeat

killed at 30s in the worker image, still running (exit 124). Note the FIRST
attempt at this probe was wrong and had to be discarded: a 1e8-iteration
version completed in 66s through the real worker (status done), so it proved
nothing. A document has to actually exceed the budget to demonstrate a budget
problem.

BEFORE the fix, by arithmetic on the shipped config: TECTONIC_MAX_RETRY=2 means
3 attempts x 271s = 813 seconds of a concurrency-1 worker for one upload, on a
class that scales to two replicas.

AFTER, through the live API:

    error_code    engine_error
    error_message the document did not finish typesetting within the time limit
    attempts      1
    engine_secs   271

One attempt. The message is deliberately not the compilation-error wording: the
document did not fail to COMPILE, it failed to FINISH, and telling a client
otherwise sends them hunting for a syntax error.

What retired the original reasoning, which was NOT arbitrary -- it was reasoned
by analogy with OCR and probe, and it carried its own falsifier in the comment
("only true while the timeout is generous relative to a document's real pass
count; if 64-05's measurement shows otherwise, the honest response is a bound on
the input, not flipping this branch"). Both halves came due:

  1. 64-05 measured the largest ADMISSIBLE document at 180.3s against a 271s
     bound. A deadline is no longer plausibly "the box was busy" -- it needs the
     box to be 50% slower than the measurement, on a document already at the
     ceiling.
  2. The prescribed lever -- a bound on the input -- was added (2 MiB) and does
     NOT cover this: the cost driver here is macro expansion, not source size.
     130 bytes is under every bound this engine has.

Cancellation is explicitly NOT swallowed by the same branch, and is pinned
separately: "terminal on deadline" is one errors.Is away from "terminal on
anything context-shaped".


P2: THE SCANNER REFUSED A DOCUMENT THAT COMPILES  (texpreamble.go)
-------------------------------------------------------------------
Claim: the raw substring search treats every literal \usepackage as executed,
including ones inside constructs the scanner explicitly does not evaluate.

Verified, in the built image, BEFORE changing anything:

    \newif\iffoo
    \foofalse
    \iffoo\usepackage{pgfplots}\fi

  engine:  COMPILES, 2504-byte PDF
  scanner: packages=[pgfplots] complete=true
  API:     422 "this deployment's TeX bundle does not provide the package
           pgfplots"

A valid document refused -- the exact failure this scanner was built to avoid
and the one 63-02 removed a whole admission gate for.

Fixed by tracking brace depth and \if...\fi depth, skipping any \usepackage
that cannot be proven to execute, and CLEARING `complete` when that happens so
the document routes to the worker rather than being treated as clean.

The regression test found a bug in the fix itself: \newif\ifdraft DECLARES a
conditional, and consuming only the \newif left the trailing \ifdraft read as
an opening \if -- ifDepth never returned to zero and every \usepackage after
the declaration was silently skipped. An abstention rule that swallows the rest
of the preamble is safe and useless.

Verified live, both directions:
  conditional document  -> 202 accepted
  \usepackage{pgfplots} -> 422 refused, by name


P2: fontspec WAS ADMITTED, AND THE DOCS SAY IT IS NOT AVAILABLE
----------------------------------------------------------------
docs/TYPESETTING.md: "Custom fonts, and fontspec. Deferred (TEX-07). fontspec is
the entry point to user-supplied fonts, so it is not in the set."

Measured: fontspec.sty IS in the bundle (the dependency closure pulled it in,
not a choice), \usepackage{fontspec} compiled and produced a 2504-byte PDF, and
the resolvable-set gate admitted it. The documented boundary and the enforced
one had drifted apart, in the direction where the document wins.

This is the one hole a resolvable-set gate has, and it is now closed by an
explicit deny list checked BEFORE resolvability, with its own reason in the
refusal:

    {"code":"unsupported_package",
     "error":"the package fontspec is not supported: user-supplied fonts are
              not available on this deployment (TEX-07)"}

Two tests keep the list from rotting in either direction: a deny entry for a
package the bundle does NOT have is dead (it reads as an enforced boundary
while enforcing nothing), and a deny entry for a package the declared set
promises is a contradiction the API resolves by refusing what the docs offer.


P2: biblatex's DEFAULT BACKEND IS BIBER, WHICH THIS IMAGE DOES NOT SHIP
------------------------------------------------------------------------
Measured. An ordinary \usepackage{biblatex} (no options), with an embedded .bib
and one \cite:

    Package biblatex Warning: Please (re)run Biber on the file:
    note: Running external tool biber ...
    error: No such file or directory (os error 2)

The declared set promises biblatex; only documents that explicitly request
backend=bibtex worked, which is exactly what the measurement corpus does. So
the promise was true only for people who already knew the answer.

Now named, terminal, with the remedy in the message:

    engine_error | biblatex requires the option backend=bibtex on this
                   deployment: no biber is available


P2: NON-CONVERGENCE -- THE PREMISE IS WRONG, THE GAP BEHIND IT IS REAL
------------------------------------------------------------------------
Claim: tectonic can exit 0 while reporting "TeX rerun seems needed, but
stopping at 6 passes", so a document with unresolved references is published as
done; detect THAT message and fail.

Refuted, by this PR's own evidence. 64-04's end-to-end paper prints exactly
that message and every one of its references resolves -- pdftotext shows
"Equation (1)", "Section 1", no "??" anywhere. Failing on the pass-cap message
would fail the document this phase ships as its proof of TEX-01.

The real signal is LaTeX's own, and it was measured separately:

    LaTeX Warning: There were undefined references.

emitted on exit 0 for a document referencing a label that does not exist. That
IS now terminal, with a message saying what the client would have seen.

AND THE FIRST VERSION OF THAT FIX WAS WRONG IN THE SAME WAY. Checking the whole
log failed 64-04's paper and both corpus bibliography documents, because the
warning is emitted on EVERY multi-pass document's early passes -- the .aux file
does not exist yet on pass one. Caught by running those documents through the
live API immediately after writing the check. The check now reads only the
FINAL pass, delimited by the engine's own "Transcript written" marker.

    fontspec                     REFUSED at admission, by name
    biblatex (default backend)   failed: backend=bibtex named as the remedy
    undefined references         failed: names what the PDF would have shown
    64-04's paper                DONE      <- regression
    corpus bib-s                 DONE      <- regression
    corpus xref-m                DONE      <- regression


P1: NO FRESH CHECKOUT COULD BUILD THE TEX IMAGE
-------------------------------------------------
Claim: deploy/tectonic-bundle/octoconv-bundle.ttb is gitignored and absent from
the repository, so the COPY fails before any image is built -- for CI's bake
job and for the documented `docker compose up -d --build` alike.

Verified. `git check-ignore -v` names .gitignore:11, `git ls-files` shows the
directory carries only MANIFEST/PROVENANCE/keep-*.txt, and building with the
file removed:

    ERROR: failed to solve: failed to compute cache key: failed to calculate
    checksum of ref ...: "/deploy/tectonic-bundle/octoconv-bundle.ttb": not found

That message says nothing about where the file comes from.

The out-of-band fetch WAS documented -- in a Dockerfile comment, as a gh
command to run by hand. That is the actual defect: a documented manual step
that nothing runs is a step that does not happen. 64-02 solved the credential
problem (no token inside the image build) and left the availability problem
standing.

scripts/tectonic-bundle-fetch.sh now does it, CI's docker-build job runs it
before bake, and README documents it beside the compose quickstart. The script:

  - READS the expected digest out of Dockerfile.tectonic-worker rather than
    carrying its own copy -- two copies of a checksum are two checksums that
    can disagree, and the one that matters is the one the image enforces;
  - takes the release tag from PROVENANCE.md for the same reason;
  - is idempotent (present-and-matching exits 0 without a download);
  - has a --check mode for CI and for humans who want to know before building.

Inverted, both ways:

  truncated bundle (1 MB of 122 MiB)  -> exit 1, prints have/want digests
  bundle absent, --check              -> exit 1, says how to get it

The bake target list also gained tectonic-worker cache scopes; it had ten
entries for what is now eleven services.
