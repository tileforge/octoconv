# Phase 71: Evaluation Gate - Context

**Gathered:** 2026-10-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Фаза выбирает по замеру ядро геометрии (колесо OCP против запасных вариантов),
рендерер (VTK + OSMesa против f3d и собственного растеризатора) и 2D-путь DXF
(ezdxf + `rsvg-convert`) — на настоящем образе `debian:bookworm-slim`, на
нативной архитектуре, под Landlock, с оценкой рендера по пиксельному
содержимому. Она собирает корпус реальных CAD-файлов с лицензиями, замеряет
пиковую RSS, время, размер образа и cold pull, выводит из замера лимиты входа и
закрывает вопрос лицензий библиотек колеса OCP.

Фаза оставляет только записи решений, измерительные скрипты, измерительный
Dockerfile и корпус. Продакшен-проводки нет: `AllEngines()`, `/v1/formats`,
`/v1/inspect`, очереди и чарт не меняются (критерий 5 роадмапа).

</domain>

<decisions>
## Implementation Decisions

### Корпус
- **D-01:** Два источника. В репозиторий идут только публичные файлы с
  открытыми лицензиями. Реальные файлы компании (поток PreviewGenerator)
  замеряются локально и не коммитятся: в evidence попадают только числа
  (размер, RSS, время, счётчики) и sha256, без имён клиентов и содержимого.
- **D-02:** Файлы компании лежат в каталоге вне репо, путь задаётся
  env-переменной (имя выбирает планировщик). Пользователь кладёт файлы туда сам.
  Пустой или отсутствующий каталог фазу **не блокирует**: замер идёт по
  публичному корпусу, а в записи решения явно стоит «реальный поток не
  замерен». Не «чисто», а «не проверялось» (память: optimistic answers for
  unexamined input).
- **D-03:** Хранение. Малые файлы коммитятся в testdata, рядом лежит
  `PROVENANCE.md` (источник, автор, лицензия, sha256 на каждый файл). Большие
  файлы (STL на десятки МБ, большие STEP) качает скрипт из `scripts/` по URL с
  закреплённым sha256 в кэш вне репо. Несовпадение хеша — ошибка, а не
  предупреждение.
- **D-04:** Для коммитящихся файлов допустимы только PD / CC0 / CC-BY / MIT /
  BSD. CC-BY-SA и NC не берём. Атрибуция CC-BY записывается в `PROVENANCE.md`.
- **D-05:** Замер по размеру идёт **выше** потолка PreviewGenerator (40 МБ) —
  до 100–200 МБ STL/STEP или до обрыва по памяти или времени. Лимит должен
  стоять с видимым запасом до замеренного обрыва, а не там, где кончился корпус
  (память: tectonic measure-at-bound).
- Синтетические файлы-уловки, которых нет в открытом доступе (cp1251/Latin-1
  DXF и STEP, IGES только из поверхностей, если не нашлось реального), делает
  детерминированный генератор. Он коммитится первым, до кода, который ими
  проверяется (протокол `scripts/sanitize-corpus.py`): без временных меток и
  случайности, с самопроверкой маркеров и ненулевым выходом при пропаже маркера.

### Бюджет памяти и лимиты входа
- **D-06:** Memory limit пода `cad` выбирается **по замеру**: сначала кривая
  «пиковая RSS от размера входа» по каждому формату, затем наименьший из
  1 / 2 / 4 GiB, при котором полезный потолок входа укладывается с запасом.
  Потолок кандидатов — 4 GiB. Во флоте у всех 1 GiB, у одного 2 GiB
  (`deploy/chart/octoconv/values.yaml`). Отклонение от этого допустимо, но
  должно быть записано с выводом.
- **D-07:** Запас: пиковая RSS **худшего** файла корпуса на потолке входа
  вместе с Go-воркером ≤ 70% limit пода. Множитель RSS/МиБ берётся по худшему
  файлу формата, не по среднему. Измеряется при `--cpus=2` и с limit пода,
  выставленным на контейнер (а не на хосте без лимита).
- **D-08:** Лимиты входа считаются **отдельно по формату**: STEP/IGES, STL
  (бинарный и ASCII отдельно, если множители заметно различаются), DXF. Вывод
  каждого числа показан в записи решения.
- **D-09:** Если даже при 4 GiB потолок STEP выходит ниже 40 МБ, **принимаем
  замеренный потолок**. В записи решения указывается, какая доля реального
  потока (если файлы компании есть) в него не входит. Большие файлы получают
  честный 413/422, а не OOM-килл.
- **D-10:** Фаза 71 также замеряет операционные счётчики на корпусе (число
  треугольников, сущностей STEP, вхождений NAUO/инстансов, вставок блоков DXF)
  и предлагает капы-**кандидаты** с выводом. Внедряет их фаза 73 (гард-стадия,
  CADIN-04) и фаза 75 для DXF. Байтовый потолок сам по себе от бомб не
  защищает.

### Планка качества рендера
- **D-11:** Приёмка двухступенчатая. (1) Скрипт проверяет пиксельные
  критерии: кадр не пуст, деталь вписана с полем и не обрезана, три ракурса
  различаются. Код возврата не используется как критерий. (2) Чекпоинт
  `checkpoint:human-verify`: контактный лист (сетка «деталь × ракурс») на
  реальных деталях корпуса, пользователь смотрит и одобряет. Без одобрения
  выбор рендерера не записывается.
- **D-12:** Стиль: нейтральная светло-серая заливка, тёмные контурные рёбра
  (feature edges), сглаживание. Подбор света и FXAA — на усмотрение
  исполнителя, но в пределах этого стиля.
- **D-13:** Фон по умолчанию — ровный белый `#FFFFFF`, без градиента. Тот же
  белый используется для letterbox в DXF. Прозрачный фон — опция (RNDR-05,
  фаза 74).
- **D-14:** Проекция ортографическая для всех ракурсов, включая `iso`. Деталь
  вписывается в кадр по bbox, а не через `ResetCamera()`. Z вверх.

### Пороги отката и лицензии
- **D-15:** Жёсткого потолка на размер образа нет. Размер и cold pull
  замеряются и записываются; сам по себе размер выбор рендерера не меняет.
  Цена большого образа учитывается при выборе `keda.cad.minReplicaCount` в
  фазе 76.
- **D-16:** С VTK + OSMesa уходим на запасной рендерер **только при
  функциональном провале**: не рендерит под Landlock на bookworm, не проходит
  пиксельные критерии или приёмку пользователя (D-11), недетерминирован в
  пределах одной архитектуры, не укладывается по времени при `--cpus=2`. f3d
  используется только для сравнения (только amd64, на нативном arm64 его не
  запустить). Собственный растеризатор — только если VTK провалился.
- **D-17:** VTK обрезается по keep-list (566 → ~290 МБ). Keep-list генерирует
  скрипт, а не пишется руками. Фаза 71 доказывает, что PNG с обрезкой и без
  совпадают на корпусе (одна архитектура, одна сборка). Рендер-тест должен
  падать, если после обновления VTK keep-list устарел.
- **D-18 (EVAL-04):** Сначала замеряем, загружает ли наш путь вообще
  `libfreeimage`, `libraw`, `libjasper` (trace/`ldd`/`LD_DEBUG` на всех
  операциях). Неиспользуемые удаляются из образа, и тест доказывает, что
  рендер и конвертация без них работают. На то, что осталось, пишется
  инженерная запись: лицензии, «только внутреннее использование, образ не
  распространяется вовне», плюс флаг «нужен OK юриста», который фазу **не
  блокирует**.

### Перенесено из прошлых фаз (не переобсуждалось)
- «Нативная архитектура» = arm64 на OrbStack. Гейта на amd64 нет, выбор
  amd64-хоста остаётся за пользователем (фаза 70, D-03/D-05). Эмулированный
  amd64 не даёт Landlock: такой замер считается за отсутствие замера.
- FreeCAD, Xvfb и f3d в продакшен-образ не идут (REQUIREMENTS Out of Scope,
  research SUMMARY).
- Корпус, который читают Go-тесты, лежит в `internal/<pkg>/testdata/` с
  `PROVENANCE.md` рядом. Фикстуры для shell-гейтов лежат в `scripts/fixtures/`
  с `README.md` (`scripts/sanitize-corpus.py`).
- Гейты гоняются локально, не в GitHub CI (память: local gates).

### Claude's Discretion
- Пин OCP: 7.9.3.1.1 или 8.0.1.0.0. Решается замером на одном корпусе, код
  хелпера использует `CornerMin()/CornerMax()`, чтобы работать на обеих.
- Величина поля вокруг детали; константы тесселяции для
  `draft`/`standard`/`fine` (относительно диагонали bbox) выводятся из замера
  времени, RSS и визуального качества.
- Закрытые словари, которые нужны фазе 72: единицы (с происхождением),
  коды причин `null`-объёма, ракурсы. Ракурсы зафиксированы в RNDR-02;
  единицы и причины предлагаются по тому, что реально встретилось в корпусе, и
  записываются в решение как черновик контракта (окончательно закрепляет
  MEAS-05 в фазе 72).
- `LP_NUM_THREADS` и потоки мешера OCP при `--cpus=2`: исполнитель замеряет
  и выбирает.
- Где лежит запись решения (например, `71-DECISION.md` в каталоге фазы плюс
  `evidence/`), имена скриптов (`scripts/cad-*-measure.sh`), имя
  измерительного Dockerfile (`Dockerfile.cad-measure`), имя env-переменной
  для приватного корпуса, путь кэша для больших файлов.
- Кандидатные наборы путей Landlock для четырёх хелперов из трассировки
  `scripts/sandbox-paths-measure.sh`. Это гипотезы для фазы 73, а не
  окончательные гранты.

## Existing Code Insights

### Reusable Assets
- `scripts/sandbox-paths-measure.sh`: уже умеет трассировать пути под пользователем образа и сверять архитектуру образа с сервером. Его используем для кандидатных грантов четырёх хелперов.
- `scripts/*-timing-measure.sh` / `*-rtf-measure.sh` (ocr, pandoc, av, audio, tectonic, probe): шаблон замера времени при `--cpus=2` и записи вывода в `evidence/`.
- `Dockerfile.probe-measure`: шаблон измерительного образа «та же база, те же версии».
- Готового инструмента для контактного листа нет. `scripts/fixtures/render_evidence.py` рисует графики CSV для KEDA-гейтов и сюда не подходит.

### Established Patterns
- Лимиты пода во флоте — `cpu: "2"`, `memory: "1Gi"` (один воркер на `2Gi`), рядом комментарий «measured timeout valid only at these limits». Замер `cad` делается при тех limits, которые потом пойдут в чарт.
- Evidence фаз лежат в `.planning/phases/<NN>-<slug>/evidence/*.txt` и коммитятся.
- Таймаут и лимиты выводятся из замера на потолке входа (tectonic `measure-at-bound`, pandoc OOM), а не копируются.

### Integration Points
- Нет: фаза не трогает `internal/`, `cmd/`, чарт и compose (критерий 5). Корпус кладётся туда, откуда его будут читать Go-тесты фазы 72, вероятно `internal/convert/testdata/cad/`; точный путь выбирает планировщик.

## Specific Ideas

- Контактный лист «деталь × ракурс» — то, что пользователь хочет увидеть
  глазами до записи решения о рендерере.
- Вид: как в обычном CAD-вьювере: серая деталь, тёмные рёбра, белый фон,
  ортографическая проекция. Повторять вид Fusion 360 из PreviewGenerator не
  нужно.
- Числа PreviewGenerator (40 МБ / 5 МБ / 60 с, порог 500 Б) — ориентир, с
  которым сравниваемся, а не источник лимитов.
