| client → API → jobs table | Untrusted client-influenced values (and, in later phases, engine-derived progress/duration) are persisted into the new `jobs` columns. This phase adds only the storage-layer guards; no write path is wired yet. |
| migration runner → live populated DB | The ALTER runs against a table that may already hold production rows; a schema change is a potential availability event. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-38-01 | Tampering | `jobs.progress_pct` / `eta_seconds` / `source_duration_seconds` writes (Phase 41) | mitigate | Fail-closed DB-layer CHECKs (`progress_pct BETWEEN 0 AND 100`, `eta_seconds >= 0`, `source_duration_seconds > 0`) reject out-of-range values at the storage boundary regardless of app-layer bugs — consistent with the existing status/engine/operation CHECKs on this table. Verified by Task 2's `check_violation` assertions. |
| T-38-02 | Denial of Service | `ALTER TABLE jobs ADD COLUMN` on a populated table | mitigate | All columns are nullable with NO DEFAULT → Postgres treats this as a metadata-only change (no full-table rewrite, no long ACCESS EXCLUSIVE hold on row data). Task 2's populated-DB scenario proves the ALTER completes instantly against a table with data. |
| T-38-03 | (Behavior regression) | Existing engine-worker INSERTs into `jobs` | accept | Nullable + no-default means every existing INSERT that omits the columns still succeeds; existing rows read NULL. | T-38-SC | Tampering (supply chain) | package installs | accept | No npm/pip/cargo/go-get installs in this phase — zero new dependencies added. No package-legitimacy surface. |
