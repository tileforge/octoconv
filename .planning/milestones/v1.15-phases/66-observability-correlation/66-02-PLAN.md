# 66-02 — Correlation-Id от вызывающего

## Задача

Вызывающий не может связать свой инцидент с нашей задачей по вебхуку: тот
приходит позже, возможно на другой инстанс, и несёт только `job_id`.

## Границы — не формальность

Значение окажется в двух чувствительных местах: в строке лога и в JSON
вебхука. Поэтому:

- **потолок 128 символов** — с запасом для UUID/ULID и любого разумного
  внутреннего ключа;
- **печатный ASCII, без CR/LF** — иначе клиент сочиняет строки в нашем логе;
- **отказ 422, а не обрезка.** Обрезанный correlation id хуже отсутствующего:
  он не смэтчится, и никто не поймёт почему.

## Почему заголовок

`target`, `opts`, `preset`, `callback_url` описывают *что конвертировать*.
Этот — метаданные о вызове. Без `X-` (RFC 6648).

## Что не делать

**Не генерировать при отсутствии.** Это второй внутренний идентификатор,
против которого весь раздел в CONTEXT. Нет заголовка — NULL, в логах `job_id`.

**Не называть это trace_id.** См. CONTEXT: имя занято контрактом W3C.

## Проверка

Живая: отправить задачу с `Correlation-Id`, дождаться вебхука, найти значение
в payload'е доставки и в логах воркера — то есть пройти путь вызывающего
целиком, а не проверить, что колонка заполнилась.

Инверсия: снять проверку набора символов и подать значение с `\n` — тест
должен показать расщеплённую строку лога.
