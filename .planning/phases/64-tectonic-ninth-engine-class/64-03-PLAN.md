<objective>
Make a `\usepackage` outside the declared set produce a clear refusal naming the
package, instead of a silent difference in typesetting or an unexplained engine
failure.

One list (64-01), two gates, and the cheap one is allowed to abstain — the shape
63-02 built and proved for the probe page ceiling, reused knowingly rather than
reinvented.
</objective>

## Task 1 — the preamble scan, over a window that is already read

`internal/convert/texpreamble.go`:

- `ScanTeXPreamble(prefix []byte) (packages []string, complete bool)` — collects
  `\usepackage[opts]{a,b,c}` and `\RequirePackage{...}` names from a prefix.
- `complete` is false when the prefix ends before `\begin{document}`, i.e. when
  the preamble ran past the window. **That flag is the whole reason the worker
  gate exists**, so it is a return value rather than an internal detail.
- `var ErrTeXUnsupportedPackage = errors.New("tex: package is not in the supported set")`,
  carrying the package name, so the failure message says *which*.

**Take the `FromPrefix` form, not an `io.ReaderAt` form.** Phase 59 D-12 split
every markup matcher in two precisely so a caller needing several matchers reads
ONE window instead of one per matcher, and `handleCreateJob` is already reading
that window for `LooksLikeLaTeXFromPrefix`. A second read here would be a second
answer to one question about one upload.

**It is a scanner, not a parser, and it must say so.** It does not follow
`\input`, does not expand macros, and does not know about conditionals. Every one
of those is a way for a `\usepackage` to be invisible to it — which is fine,
because it may abstain, and is exactly why Task 3 exists. A comment stating this
belongs in the file: this project has a recorded history of a bounded scanner
being quietly treated as authoritative.

**Verify:** table test over real preamble shapes — options, multiple packages in
one call, comments (`%` to end of line), `\RequirePackage`, a `\usepackage` after
`\begin{document}` (legal-ish and must not silently extend the preamble), and a
truncated prefix returning `complete == false`.

## Task 2 — the API gate (before the storage write)

In `handleCreateJob`, for `detected == "latex"` and `target == "pdf"`, in the
window already read for `LooksLikeLaTeXFromPrefix`, strictly before
`s.storage.Upload`:

- any scanned package not in `convert.TeXPackages` → **422 naming the package**;
- `complete == false` with no violation found → **admit**, and log the
  abstention at the same level the other content-validation rejections log, so
  an operator can see how often the cheap gate gives up.

**New error code, in BOTH vocabularies.** "Your document uses a package this
service does not ship" is a distinct client-actionable class — remove it, or ask
for the set to be extended — so it is not `invalid_request`. Add
`errcode.UnsupportedPackage = "unsupported_package"` and
`worker.CodeUnsupportedPackage` with the identical string, the same
cross-reference comment `InvalidOptions` and `TooManyPages` already carry, and
its own equality pin test (`TestSyncAndAsyncShareUnsupportedPackage`) so a
failure names which code drifted.

Update `docs/ERROR-CODES.md` (both tables, and the "one code space" section,
which will then list three shared codes) and `docs/openapi.yaml` (the `Error.code`
enum and the create-job 422 description). The doc-sync and openapi-sync tests in
`internal/errcode` must stay green; if they do not enumerate this code yet,
extend them rather than working around them.

**Also add `page_limit`'s neighbour to `RejectBindings`.** Every `reason=` token
logged by a "content validation rejected:" line needs a D-04 binding in
`internal/inspect/bindings.go`, and `TestRejectBindingsCoverEveryContentValidationReason`
will fail on the first full run otherwise — it did exactly that in 63-02. This
one is an **errcode** binding, not a finding: an unsupported package is a fact
about *our configuration*, not a risk in the client's file.

**Verify:** a storage double whose `Upload` calls `t.Fatal`. **Inversion:** move
the check below `s.storage.Upload` → that test fails naming the call. Record it.

## Task 3 — the worker gate, terminal, naming the package

Two things must be true and only one of them is code:

**(a) Capture tectonic's real output first.** Compile a document requiring a
package outside the bundle, in the built container, and commit the engine's
actual stderr/stdout as a fixture with a `PROVENANCE.md` recording the command,
the tectonic version and the date.

**Do not write the parser first.** This project's own retrospective records four
bypasses of a single bound produced by predicting a format instead of testing
against one, and the resolution both times was to derive from the real structure.
Capture, then parse, then test against the capture.

**(b) The parser and the classification.** Extract the package name from that
output; wrap as `ErrTeXUnsupportedPackage`. `isTectonicTerminal` returns true for
it, and `tectonicFailureCode` maps it to `CodeUnsupportedPackage`.

**If the output does not permit naming the package reliably**, say so and fail
with the generic engine error rather than emitting a guessed name. A confidently
wrong package name is worse than none: the client removes the wrong `\usepackage`
and the job fails again. That outcome is a legitimate finding of this task, not a
failure to complete it.

**Verify:** extend the pinning test with the tectonic row —
`ErrTeXUnsupportedPackage` → terminal, code `unsupported_package` — **and**
assert in the SAME test that a `context.DeadlineExceeded` from the same handler
is still TRANSIENT. The two verdicts are opposites on purpose: a missing package
depends on the document and reproduces exactly; a timeout depends on the box.
Pinning only the new one would let a later change collapse them without notice.

**Inversion:** remove the `ErrTeXUnsupportedPackage` branch from
`isTectonicTerminal` → the pinning row fails with "transient, want terminal".
Record the output.

## Task 4 — the two gates cannot drift

One test that sets up both paths against the same list and asserts they agree:
the API rejects package X and the worker classifies package X the same way, and
both admit a package that is in the set.

64-01's three-way test already holds the list equal to the bundle. This one holds
the two READERS of that list equal to each other. This phase deliberately puts
one rule in two places — the shape this project has been burned by four times —
so the test that holds them together is not optional and its absence is a plan
failure.

**Gates:** `gofmt`, `go vet`, `go build`, `go test ./... -count=1` against live
Postgres + Redis + MinIO, `yq` over `docs/openapi.yaml`. Serially, never
alongside a Kubernetes run.
