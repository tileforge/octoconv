P1-A  UNBOUNDED ENGINE LOG  (internal/convert/exec.go)
------------------------------------------------------
235-byte document, a \message loop:

    docker run --memory 1g --cpus 2 ... timeout 30 tectonic -X compile ...
    EXIT=124
    323 565 198 bytes of stdout in 30 seconds        = 10.8 MB/s

Against the largest ADMISSIBLE document (2 143 444 B source, 745 pages, 7
passes -- the file 64-05's timeout is derived from):

    1 416 019 bytes of stdout

So the cap is 8 MiB: 5.9x the largest legitimate log, 0.8% of the container.
The TAIL is kept, because all three parsers read the end of the log (the
missing .sty that aborted the run, the biber failure, the final pass's
warning).

WHAT THE LIVE RUN THEN SHOWED, and it is not what the finding said. With the
Go-side buffer capped, the same document through the real worker still drove
the CONTAINER to its limit:

    315 MiB -> 586 MiB -> 947 MiB -> 999 MiB, holding at the cgroup limit

The Go process holds 8 MiB. The rest is the CHILD -- tectonic keeps its output
files (here, a .log growing at 10.8 MB/s) in its own memory and page cache.
The container was NOT OOM-killed: status=running, restarts=0, OOMKilled=false
throughout, because the kernel reclaims the cache.


P1-B  NO OUTPUT CEILING  (internal/convert/tectonic.go)
-------------------------------------------------------
Only zero bytes was refused. The 2 MiB INPUT ceiling bounds what the client is
charged for and says nothing about what comes back, because TeX ships pages out
and frees the memory as it goes:

    198-byte document, 20 000 \newpage iterations
    EXIT=0  SECONDS=16   doc.pdf = 6 040 163 bytes

    largest ADMISSIBLE document (2 143 444 B, 745 pages)
    doc.pdf = 1 914 057 bytes

So a tiny upload produces THREE TIMES the largest real document's output in 16
of the 271 seconds available. At the same rate the timeout leaves room for
roughly 100 MB, uploaded to S3 and recorded, from an input billed at 198 bytes.

A 400 000-page variant was also run and did NOT finish inside 271s (EXIT=124,
no PDF) -- the attack has to stay under the timeout to land, which is what
bounds it at ~100 MB rather than arbitrarily.

TECTONIC_MAX_OUTPUT_BYTES = 32 MiB: 17x the largest real document, refused
before the upload, terminal, own code (output_too_large).

A legitimate counterexample was also measured, to check the ceiling is not
merely a bet on documents being small: a 2 090 036-byte TikZ-heavy document
(19 000 pictures) does NOT reach it -- it dies at 13s on TeX's own
"main memory size=5000000" limit. TeX bounds a page-accumulating document by
itself; only a page-SHIPPING loop grows the PDF.

P1-B  THE CEILING, PROVEN BY LOWERING IT
-----------------------------------------
Producing >32 MiB on demand turned out to be unreliable: these runs are NOT
linear under the container's memory pressure. 130 000 iterations produced
64 464 pages / 19 545 890 bytes in 93s; 240 000 produced FEWER -- 43 392 pages
/ 13 315 591 bytes in 163s. Extrapolating a rate to the timeout would therefore
have been a number nobody measured, and the earlier "~378 KB/s -> roughly
100 MB" comment was exactly that. It is corrected in the same commit.

So the ENFORCEMENT was proven directly, with a worker started at
TECTONIC_MAX_OUTPUT_BYTES=5242880 against the same 199-byte document:

    after 93s   error_code=output_too_large
                "the typeset PDF is larger than this deployment accepts"
    attempts    1
    S3          ls /data/octoconv/results/<job>/ -> No such file or directory

The bytes never reach the bucket, which is the half of the fix that matters.

ROUND 3 (2026-09-05) -- three findings, all P2, each reproduced first
=====================================================================

P2  A BYTE OF LOOKBACK IN PLACE OF TOKENIZATION  (texpreamble.go)
------------------------------------------------------------------
    \let\foo\\% \usepackage{pgfplots}

\\ is a control SYMBOL, so the percent after it starts a comment and TeX never
loads pgfplots. Before the fix the scanner returned:

    packages=[pgfplots] complete=true

which is a 422 for a document that compiles. Third instance in this PR of the
same shape (\fi as a prefix, \usepackage as a prefix, now % by one byte of
lookback), so the fix is the tokenization rather than a fourth special case: a
control symbol is consumed as one token, the comment branch needs no lookback,
and \{ / \} stop moving braceDepth.

P2  A MEASUREMENT THAT CLAIMED THE CEILING AND MEASURED 369 KB
---------------------------------------------------------------
The script prints "derived from a run AT the ceiling, never extrapolated to it"
and, run the documented way, iterated only the committed corpus.

How much that mattered, from this run's own numbers:

    committed corpus, worst   bib-xl     368 999 B   30.586s / 7 = 4.369 s/pass
                              -> ceil(4.369 x 7 x 1.5) = 46s

    with the ceiling staged   bib-bound 2 143 444 B  148.091s / 7 = 21.156 s/pass
                              -> ceil(21.156 x 7 x 1.5) = 223s

So a routine remeasurement would have recommended 46 SECONDS for an engine
whose largest admissible document takes 148 -- and printed that it measured the
ceiling while doing it.

The script now stages the generated corpus when the given one falls short, and
the staging doubles as a check nobody had: every committed file must come back
BYTE IDENTICAL from the generator (all nine do), or corpus and generator have
diverged and neither describes the other.

The 223s here is BELOW the shipped 271s, which is the safe direction: 271s came
from a 180.3s run of the same document on a busier machine, and a bound is
supposed to hold on the unlucky run.
