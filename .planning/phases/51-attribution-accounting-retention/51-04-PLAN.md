<objective>
Give the platform an executable retention mechanism: a bounded, advisory-lock-gated purge on the reconciler's existing tick that removes aged `jobs` rows (and, by cascade, their `job_events`/`job_inputs`/`job_outputs`/`webhook_deliveries`) and aged `client_usage_daily` rows — proven by tests that age data and assert the rows are gone (RETN-01).

Purpose: RETN-01 exists because `jobs`/`job_events` have never been deleted, and Phase 51 would otherwise add a third unbounded table on top of that debt. ROADMAP SC4 was tightened specifically to reject a policy stated in a migration comment.
Output: Purge queries, the sweep-tick host, the operator-configurable windows propagated through every deployment surface, and the aging tests.
</objective>

<design_decisions>
**Deleting `jobs` is enough.** `job_events`, `job_inputs`, `job_outputs` and `webhook_deliveries` all declare `job_id ... REFERENCES jobs (id) ON DELETE CASCADE` in `0001_init.sql`, and `jobs.parent_id` self-references with CASCADE. A separate `DELETE FROM job_events` is unnecessary and, if written first, would be wrong-order churn. This must be stated in a comment or the next reader will add one.

**Byte history survives the purge.** That is the entire reason D-01 chose a dedicated rollup table over aggregating `jobs`: this plan is what would have silently truncated consumption history to 90 days otherwise.

**The purge is called from the tick, not from inside `sweep()`.** `sweep()` returns early on any finder error (`reconciler.go:251-255, 391-394`); hosting the purge at its tail would let a persistently failing stale-scan silently disable retention. `Run` and `RunWithLock` call `s.purge(ctx)` immediately after `s.sweep(ctx)`, which keeps the advisory-lock gating (only the lock holder ever reaches either call), adds no ticker/goroutine/deploy unit, and leaves every existing line of `sweep()` untouched.
</design_decisions>

    Create `internal/jobs/retention.go` (package `jobs`) with `PurgeJobs` and `PurgeUsage` per `<interfaces>`.

    `PurgeJobs`: compute `cutoff := time.Now().Add(-olderThan)` in Go and bind it — never inline a SQL interval expression. Delete via `DELETE FROM jobs WHERE id IN (SELECT id FROM jobs WHERE created_at < $1 AND status NOT IN ('queued','active') ORDER BY created_at LIMIT $2)`. The `status NOT IN` predicate is the safety property, not an optimization: a queued job stranded for months is a reconciler problem, and deleting live work while a worker holds it would be unrecoverable data loss. `LIMIT` inside the subquery is required — Postgres does not accept `LIMIT` directly on `DELETE`. Return the command tag's `RowsAffected()`.

    `PurgeUsage`: `DELETE FROM client_usage_daily WHERE ctid IN (SELECT ctid FROM client_usage_daily WHERE day < $1 LIMIT $2)` with the cutoff computed in Go as a date (`time.Now().Add(-olderThan)`), using the `client_usage_daily_day_idx` created in Plan 01. Use `ctid` (or the full composite key) because the table has no surrogate id.

    Both must return `(0, nil)` immediately when `olderThan <= 0` or `batch <= 0`. Comment why this guard exists rather than treating zero as "purge everything": an operator who sets `JOBS_RETENTION=` to an empty value, or a `reconciler.Config` literal that omits the field, must get "retention off", never "delete the whole table". This is the single highest-consequence defect available in this plan.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator env → destructive SQL | An env value (or its absence) directly parameterizes a `DELETE` against the system of record |
| background sweeper → live job rows | A purge runs concurrently with workers holding in-flight jobs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-51-12 | Tampering | purge deleting more than intended | mitigate | `olderThan <= 0` returns `(0, nil)` without executing a DELETE; cutoff computed in Go and bound as `$1`; `status NOT IN ('queued','active')` spares live work; all three asserted by tests, including one that uses the exact `Config` literal shape every pre-existing test uses |
| T-51-13 | Denial of Service | one sweep tick deleting unbounded rows and blocking the tick | mitigate | `LIMIT $2` per statement plus `maxPurgeBatchesPerSweep` iterations, giving a hard per-tick ceiling; asserted by `TestPurgeIsBoundedPerTick` |
| T-51-14 | Denial of Service | concurrent purges from multiple webhook-worker replicas | mitigate | `purge` is called only from `Run`/`RunWithLock` after the advisory-lock gate, so exactly one fleet-wide purger runs, reusing the Phase 3 election |
| T-51-15 | Repudiation | silent retention failure | mitigate | Each non-zero batch reports through `octoconv_reconciler_actions_total{action="purged_jobs"/"purged_usage"}`, so an operator can see whether retention is running at all |
| T-51-16 | Information disclosure | consumption history lost with the job rows | mitigate | Usage lives in `client_usage_daily` on an independent, longer window (D-01/D-12); the jobs purge cannot truncate it |
| T-51-SC | Tampering | dependency supply chain | mitigate | No packages installed; `git diff go.mod go.sum` empty is an acceptance criterion |
</threat_model>
