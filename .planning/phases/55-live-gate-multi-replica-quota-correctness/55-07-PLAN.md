<objective>
Make the ten-round live gate's `admitted == K` assertion SOUND, and make its next failure diagnosable.

The 2026-08-07 run failed at round 4/10 (`expected [2], got [3]`) after 56 passing checks. The
evidence says the nine requests that went out inside 4 ms produced exactly 2 admits — the cap held
for the genuinely simultaneous population — and the tenth request, sent 159 ms later and answered
310 ms after the first admission response, was admitted as the third. With an 86-byte fixture and an
engine that converts it in well under 310 ms, a slot very plausibly freed LEGITIMATELY between the
two decisions. That reading is a reconstruction, not a fact: the run tore the namespace down on exit,
so no job-status timeline exists to prove it.

Purpose: fix the PREMISE, not the check. `admitted == K` is only sound while no admitted job can
reach a terminal status during the burst — so make jobs long-lived, tighten the burst window, remove
the process-start jitter that produced the straggler, and — the load-bearing part — turn the
unverifiable assumption into a CHECKED precondition read from Postgres, so the next run can tell
"legitimate slot reuse" from "real cap violation" instead of leaving a reader to reconstruct it.

Relaxing the assertion to `<=` is explicitly off the table: it reintroduces the vacuity `==` was
chosen to prevent (a round admitting 0 would pass).

Output: a committed heavy fixture + its deterministic generator, a jitter-free burst driver, and a
harness that refuses to start on a stale image, refuses to start on a broken spread/engine-time
ratio, proves the no-premature-terminal precondition every round, and commits a job-status timeline
artifact alongside the existing per-request TSV.
</objective>

<design_decisions_already_made>
Decide nothing below; it is settled. Implement it.

- **D1 — Heavy fixture, not a big upload.** A larger POST BODY would be the wrong fix: the API
  reaches its authoritative `admitLocked` transaction only after fully reading the multipart body
  and writing it to S3 (`handlers.go`: PreAdmit → dimension peek → `storage.Upload` → `Create`), so a
  multi-MB body spreads the DECISIONS apart — worsening defect 1 while trying to fix defect 2. The
  fixture must be small on the wire and expensive to CONVERT: a 9000x9000 low-entropy PNG, 254 KiB
  compressed, 81 MP decoded.
- **D2 — Target format becomes `webp`, engine stays `image`.** png→jpg at 81 MP is 601 ms; png→webp
  is 5.2–5.6 s. Switching ENGINE (to document/av/ocr/pandoc) was rejected: `octoconv-worker:dev` is
  the only engine image the gate's STEP 2 already waits on and the only one guaranteed built, so an
  engine switch imposes an image-build cost on the operator for no gain. `TARGET_FORMAT`, `FIXTURE`
  and `FIXTURE_CONTENT_TYPE` are already env-overridable at
  `scripts/quota-multireplica-liveproof.sh:104-107` — change the DEFAULTS there; do not add a
  parallel "heavy fixture path".
- **D3 — The fixture is COMMITTED, not generated at run time.** `scripts/fixtures/gen_heavy_docx.py`'s
  precedent (generate to /tmp, never commit) exists because that generator needs a third-party
  library (`python-docx` via ephemeral `uv`) and produces a multi-MB artifact. Neither applies here:
  this generator is stdlib-only and deterministic, and the artifact is 254 KiB — the same order as
  the committed `internal/e2e/testdata/*` fixtures. Committing also keeps the harness's existing
  STEP 1 `-f "$FIXTURE"` check and its sha256 + byte-count host↔pod transfer integrity path working
  unchanged, and avoids re-introducing a host `python3` dependency that Plan 55-06 deliberately
  removed. Record this divergence from the Phase 28 precedent, with these reasons, in the generator's
  own docstring.
- **D4 — New spread bound: `BURST_SEND_SPREAD_MS=250`, with a self-checking invariant.** The
  invariant to state plainly: *the burst window must be much shorter than the fastest possible job.*
  Encoded as `BURST_SEND_SPREAD_MS * SPREAD_SAFETY_FACTOR(20) <= MIN_ENGINE_WALL_MS(5194)` — asserted
  in STEP 1, so a future editor who loosens either knob trips a named failure. 250 ms is deliberately
  ABOVE the worst spread ever observed (159 ms): the straggler is fixed at its source (D5), and the
  soundness of `== K` no longer rests on the spread bound at all (D6). The bound's job reverts to
  what it was always for — proving the requests genuinely contended.
- **D5 — Fix the straggler at its source: the burst pod's own CPU limit and the driver's
  post-barrier forks.** A +159 ms outlier among ten `curl` processes released by one FIFO barrier is
  process-start jitter, and the burst pod runs at `limits.cpu: 500m` — forking ten subshells, ten
  `date` processes, ten `cat` processes and ten `curl` processes on half a core is exactly the shape
  that produces it. Three changes: raise the burst pod to `requests.cpu: 500m` / `limits.cpu: "2"`;
  hoist the api-key `cat` out of the per-request subshell; replace the per-request `date` fork with
  bash's fork-free `EPOCHREALTIME`. Pre-warming `curl` itself is NOT possible (a curl process cannot
  be started and then told to fire later), which is why the fix is "remove every OTHER fork from the
  post-barrier path" plus a deterministic readiness handshake replacing the blind `sleep 0.3`.
- **D6 — The discriminating assertion (the load-bearing part of this plan).** Before the exact-K cap
  assertion fires, the harness asks Postgres directly: did ANY of this round's admitted jobs reach a
  terminal status at or before the round's LAST response? If yes, the round's admit count is
  explained by legitimate slot reuse and the gate fails saying exactly that, dumping the timeline. If
  no, the premise for `== K` is proven for that round, and a subsequent `expected [2], got [3]`
  means a REAL cross-replica cap violation with nothing left to reconstruct. The timeline is
  committed as its own artifact so the question is answerable from evidence after teardown — the
  one thing the 2026-08-07 run could not do.
- **D7 — Clock domains.** The discriminating query compares a Postgres timestamp against the burst
  pod's millisecond clock. Both containers run on one OrbStack node and share the kernel's
  CLOCK_REALTIME, but that is an assumption, so it becomes a CHECKED one: STEP 5 measures the skew
  between the burst pod's `date +%s%3N` and Postgres's `clock_timestamp()` back to back and hard-fails
  above 1000 ms. The per-round wall-time ratio check compares two DURATIONS (DB-clock elapsed vs
  pod-clock elapsed) and is therefore offset-free by construction.
- **D8 — Upload/pixel limits.** 254 KiB is 0.25% of the chart's `MAX_UPLOAD_BYTES` (100 MiB) and far
  under the image engine's own 100 MiB per-engine ceiling; 81 MP is 81% of `MAX_IMAGE_PIXELS`
  (100,000,000). No limit interacts. Do not raise the fixture's dimensions without re-checking
  both.
- **PRESERVE UNCHANGED:** the in-cluster burst path, the two-phase install, the cross-pod D-05
  assertion, the ten-round loop, drain-and-assert-drained, the evidence TSV's column schema and
  header, the teardown trap, and "this script's exit code IS the gate".

  <action>
    Create `scripts/fixtures/gen_heavy_png.py`: a stdlib-only (`argparse`, `struct`, `zlib`, `os`,
    `sys` — nothing else, no `uv`, no pip, no requirements manifest touched) generator that writes a
    valid 8-bit truecolor PNG.

    Structure: the 8-byte PNG signature, then `IHDR`, then a single `IDAT`, then `IEND`, each written
    through one `chunk(tag, data)` helper emitting big-endian length, tag, data, and `zlib.crc32(tag+data)`.
    `IHDR` payload is `struct.pack(">IIBBBBB", width, height, 8, 2, 0, 0, 0)` — bit depth 8, colour
    type 2 (truecolour), no interlace.

    Raster content, and WHY (state this in the docstring, it is the entire design): one deterministic
    RGB row is built once as the ramp `((x*7)&0xFF, (x*13)&0xFF, (x*29)&0xFF)` for x in 0..width-1.
    Row 0 is emitted with filter byte 0 (None); EVERY subsequent row is emitted with filter byte 2
    (Up) followed by `width*3` zero bytes, because every row is identical to the one above it. That
    makes the compressed stream tiny while the DECODED raster is still `width*height*3` real bytes
    the converter must decode, resample and re-encode. Small on the wire, expensive to convert —
    which is precisely the property D1 requires, and precisely why a "just use a bigger file"
    approach is wrong. Compress with a single `zlib.compressobj(9)`, feeding row 0 then the repeated
    Up-filtered row, then `flush()` — never build the full raster in memory.

    Arguments: `--width` and `--height` (both required, both `int`, both must be >= 1), `--out`
    (required). On success print the output path, the WxH, the pixel count and the byte size, in the
    register `gen_heavy_docx.py` uses.
