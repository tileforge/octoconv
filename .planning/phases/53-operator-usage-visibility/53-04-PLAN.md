Envelope (top-level JSON object, mirroring `handleListJobs`'s `{"jobs": [...]}` wrapper rather than a bare array):

- `period` (string) — the resolved period, always one of `today` / `7d` / `30d`
- `day_from`, `day_to` (string, `YYYY-MM-DD`) — the inclusive UTC day range actually queried
- `remaining_matches_admission_gate` (bool) — `true` only when `period == "today"` (D-09)
- `remaining_semantics` (string) — `"live_admission_gate"` when `period == "today"`, otherwise `"hypothetical_single_day_equivalent"`
- `remaining_note` (string) — human-readable expansion of the two fields above
- `usage` (array, non-nil so an empty result marshals as `[]`)

Each `usage` element:

- `client_id` (uuid string), `client_name` (string), `engine` (string), `enforcement_mode` (string)
- `used_terminal`: `{ "job_count", "bytes_in", "bytes_out" }` (integers)
- `used_in_flight`: `{ "job_count", "bytes_in" }` (integers — an in-flight job has no outputs yet)
- `limits`: `{ "max_concurrent", "max_daily_bytes", "max_daily_jobs" }` — each `null` when unlimited
- `remaining`: `{ "concurrent", "daily_bytes", "daily_jobs" }` — each `null` when the matching limit is `null`

Implement `func (s *Server) handleSystemUsage(w http.ResponseWriter, r *http.Request)`:

1. Read `r.URL.Query()`. Resolve `period`: empty means `"today"` (D-04); if it is not a key of `validUsagePeriods`, `writeError(w, http.StatusUnprocessableEntity, "invalid period filter")` and return.
2. Resolve the optional `client_id`: when non-empty, `uuid.Parse` it; on error `writeError(w, http.StatusBadRequest, "invalid client_id")` and return; otherwise keep a `*uuid.UUID`. Never interpolate it anywhere — it is passed as a bound parameter by the repo layer.
3. Both validations MUST complete before either repo call, so an invalid request costs zero DB work (D-03, mirroring `handleListJobs`).
4. Call `resolveUsagePeriod(period, time.Now())`.
5. Call `s.usageRepo.UsageSummary(ctx, clientID, dayFrom, dayTo)`; on error `writeError(w, http.StatusInternalServerError, "failed to load usage")` and return — the underlying error is discarded, never echoed (CLAUDE.md: the HTTP layer never leaks internal error text).
6. Call `s.limitsRepo.ListAllLimits(ctx, clientID)`; on error `writeError(w, http.StatusInternalServerError, "failed to load limits")` and return.
7. Merge. Build a per-client metadata map from the `ListAllLimits` result keyed by `ClientID`, holding `ClientName` and `EnforcementMode` (every row for a client carries the same values). Build a limits map keyed by `(ClientID, Engine)` from rows whose `Engine` is non-nil. The emitted row key set is the UNION of the `UsageSummary` keys and the non-nil-`Engine` limits keys: a client with usage but no configured limits appears with all-`null` limits, and a client with a configured limit but zero usage appears with zero usage and `remaining` equal to the full limit (OPSV-02 — an operator must be able to see a limit that has not been consumed against yet). If a usage row's client has no metadata entry (impossible under `client_usage_daily`'s ON DELETE CASCADE FK, defensive only), still emit the row with empty `client_name`/`enforcement_mode` — never drop it, because dropping would hide real usage from the operator.
8. Compute `remaining` per row, each dimension independently, each `nil` when its limit is `nil` (never `0 - used`, never a sentinel), and NOT clamped at zero — a signed negative is the informative answer for OPSV-02's "set limits from observed data":
   - `concurrent` = `*MaxConcurrent - InFlightJobCount`. In-flight ONLY: `evaluate()`'s concurrency check counts queued+active jobs and never consults the rollup.
   - `daily_bytes` = `*MaxDailyBytes - (TerminalBytesIn + InFlightBytesIn)`. `TerminalBytesOut` is NOT part of this sum — `evaluate()` compares `max_daily_bytes` against `sum(bytes_in)` plus in-flight input sizes only. Add an inline comment saying so explicitly, because including `bytes_out` here is the single easiest way to make this endpoint disagree with the gate.
   - `daily_jobs` = `*MaxDailyJobs - (TerminalJobCount + InFlightJobCount)`.
9. Sort (D-02): order clients by total consumption for the resolved period, descending, where consumption is `TerminalBytesIn + TerminalBytesOut` summed across ALL of that client's engines; break ties by `ClientID` string ascending for determinism. Within a client, order rows by `engine` ascending so a client's engines stay contiguous and stable. Document the chosen consumption metric in a comment — bytes rather than job count, because job count treats a 1 KB job and a 2 GB video identically, and the choice is not self-evident from the requirement text.
10. Build the envelope. `remaining_matches_admission_gate` is `period == "today"`. `remaining_semantics` is `"live_admission_gate"` when true, `"hypothetical_single_day_equivalent"` otherwise. `remaining_note` explains, for the multi-day case, that `max_daily_bytes`/`max_daily_jobs` are DAILY caps that reset at UTC midnight, so a multi-day `remaining` compares a multi-day sum against a one-day cap, has no admission-gate analogue, and will legitimately go deeply negative for healthy clients; and for the `today` case, that the figure is exactly what `evaluate()` computes right now (D-09). Format `day_from`/`day_to` with `Format("2006-01-02")`. The `usage` slice must be built with `make([]..., 0, n)` so an empty result marshals as `[]`, not `null`.
11. `writeJSON(w, http.StatusOK, resp)`. Do not log — `internal/*` never logs.
