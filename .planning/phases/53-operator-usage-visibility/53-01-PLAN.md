<objective>
Add the read side of the Phase 51 usage rollup to `internal/jobs`: one exported repo method that returns per-(client, engine) terminal usage over an inclusive UTC day range PLUS the live in-flight (queued/active) term, using the exact SQL shape `evaluate()` uses.

Purpose: This is the load-bearing half of D-05. Every number the operator endpoint shows for "used" and "remaining" comes from here. If this query drifts from `evaluate()` — by filtering `client_usage_daily` on `status`, or by binding the in-flight statuses as parameters — the endpoint lies to the operator about what the admission gate will actually do, which is the exact failure D-05 exists to prevent.

Output: `internal/jobs/usage_query.go` (new) and `internal/jobs/usage_query_test.go` (new).
</objective>

Declare THREE package-level `const` SQL strings so a source-level test can assert their shape without a database:

1. `usageTerminalSQL` — groups the rollup over the requested day range:
   selects `client_id`, `engine`, `COALESCE(SUM(job_count), 0)`, `COALESCE(SUM(bytes_in), 0)`, `COALESCE(SUM(bytes_out), 0)`
   from `client_usage_daily`
   where `day BETWEEN $1::date AND $2::date` AND `($3::uuid IS NULL OR client_id = $3)`
   grouped by `client_id, engine`.
   This statement MUST NOT contain the substring `status` anywhere — no `status IN (...)` filter, no `status` in the select list, no `status` in the GROUP BY. 2. `usageInFlightJobsSQL` — counts live jobs:
   selects `client_id`, `engine`, `count(*)`
   from `jobs`
   where `status IN ('queued', 'active')` written as SQL LITERALS AND `($1::uuid IS NULL OR client_id = $1)`
   grouped by `client_id, engine`.

3. `usageInFlightBytesSQL` — sums live input bytes:
   selects `j.client_id`, `j.engine`, `COALESCE(sum(ji.size_bytes), 0)`
   from `jobs j JOIN job_inputs ji ON ji.job_id = j.id`
   where `j.status IN ('queued', 'active')` (literals again) AND `($1::uuid IS NULL OR j.client_id = $1)`
   grouped by `j.client_id, j.engine`.
   Add an inline comment stating why this is a SEPARATE statement from `usageInFlightJobsSQL` rather than one JOINed query: a job with N `job_inputs` rows would contribute N to a `count(*)` over the join. Two separate grouped queries is the faithful generalization of `evaluate()`'s own two-separate-subqueries structure (`admission.go:289-294`).

Also add an inline comment on both in-flight statements noting there is deliberately NO `created_at` / day predicate on the in-flight term — matching `admission.go:306-347`: a job that is queued or active right now consumes capacity right now regardless of when it was created, and adding a date predicate would introduce a timestamptz-vs-date comparison with a hidden session-TimeZone dependency.
