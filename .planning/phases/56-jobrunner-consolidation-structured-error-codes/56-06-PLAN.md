  <action>
Create `docs/ERROR-CODES.md`. Format is Claude's discretion (D-02 notes this); a table per half is
the natural fit given the repo's existing docs style. Whatever the layout, the code strings must sit
in a machine-parseable column so Task 2's test can extract them without heuristics.

Content required:

1. A header stating the vocabulary is FROZEN as of milestone v1.13 Phase 56. Later phases may ADD
   codes; no phase may rename or repurpose an existing one while the frontend and both MCP servers
   are migrating (PITFALLS.md Pitfall 11). Name the commit or phase at which the freeze takes
   effect.

2. The envelope section: synchronous errors are the flat shape `{"error": "<message>", "code":
   "<code>"}` — never nested — because `frontend/src/api.ts:54` reads `body.error` as a plain
   string (D-01). Extensibility comes from additional TOP-LEVEL fields such as `retry_after`, never
   from changing the shape (ERRC-01). Asynchronous failures surface as the `error_code` /
   `error_message` fields on `GET /v1/jobs/{id}` and on the terminal webhook body.

3. The synchronous table: one row per `errcode` constant with the code string, the typical HTTP
   status(es), the failure class it represents, and what a client should do about it. State
   explicitly that granularity is by failure CLASS, not per message string (D-02) — the specific
   detail always lives in `message`, never encoded as a finer code.

4. The asynchronous table: one row per frozen async constant with the code string, which engine
   class(es) can emit it, and the meaning. Note that `engine_error` is a deliberate catch-all used
   identically by all seven engines and is frozen against renaming by D-05, and that
   `reconciler_exhausted` is emitted by `internal/reconciler`, not by an engine.

5. A "one code space" note: `invalid_options` intentionally carries the SAME string in both tables
   (D-03). A consumer sees the identical code whether it caught the failure synchronously as a 422
   at job creation or asynchronously in `error_code` after the job failed. This is by design and
   must not be "disambiguated" by renaming either side.

6. A "Consumer contract" section stating, as a requirement rather than a suggestion (Pitfall 12):
   consumers MUST treat an unrecognized code as a generic fallback and MUST NOT throw, crash, or
   fail closed on it. Recommend an open string type with a curated set of known values plus an
   explicit unknown fallback, and explicitly warn against generating a closed TypeScript union or
   Go enum from the current list, because that turns every future addition into a breaking change.

7. A "Not in scope" note: publishing this list into `docs/openapi.yaml` as an enum with codegen is
   ERRC-V2-02, deliberately deferred (D-07). Migrating the two existing 429 bodies to a different
   envelope is ERRC-V2-01 and is not needed under D-01.

Add `docs/ERROR-CODES.md` to the index in `docs/README.md` following that file's existing entry
style.

Do not invent a code that no Go constant declares, and do not omit one that does — Task 2's test
enforces both directions, but the document should be correct on the first pass.
