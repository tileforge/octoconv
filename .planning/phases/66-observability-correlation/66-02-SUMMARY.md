# 66-02 — итог

## Что сделано

Заголовок `Correlation-Id`, разбираемый **до чтения тела**: 128 символов
печатного ASCII по белому списку, отказ 422 вместо обрезки. Колонка
`correlation_id` (nullable, без индекса — по ней ничего не ищут, её грепают в
логах). Эхо в `GET /v1/jobs/{id}`, в payload'е вебхука и в строках логов обоих
процессов.

Отсутствует — значит NULL: свой идентификатор не генерируется, потому что
`job_id` уже опознаёт задачу, а второй внутренний со временем разойдётся с
первым.

## Проверено живьём — весь путь вызывающего

- статус: `correlation_id = 'svc-checkout/req-8f31c2a4'`
- логи: записи **обоих** процессов находятся по **клиентскому** идентификатору,
  а не по `job_id`
- вебхук: `{"event":"completed","status":"done","correlation_id":"svc-orders/inc-2026-09-07-b1"}`
- отказы: пробел → 422, 129 символов → 422

Перевод строки до обработчика не доходит — `net/http` отвергает заголовок
раньше. То есть проверка набора символов здесь эшелонированная, а проверка
длины — единственная.

## Четыре собственные ошибки, все одного рода

Все — заявление результата без проверки того, что его произвело:

1. **Первый живой прогон показал отсутствие значения.** Работал контейнер,
   собранный ДО правок: я спрятал вывод `docker compose build` в `/dev/null` и
   поверил ему.
2. **Приёмник вебхука напечатал «запущен» безусловно** — он упал на кириллице
   в имени хоста и не слушал.
3. **Вебхук пришёл без значения:** `webhook-worker-2` работал на образе
   восемнадцатичасовой давности, потому что я собрал только `-1`.
4. **Инверсия, убирающая значение из вебхука, прошла.** Живое доказательство
   было, теста не было.

Четвёртая — самая дорогая: живое доказательство устаревает молча.
