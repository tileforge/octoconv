# Phase 66 — Observability: следы задачи и корреляция с вызывающим

**Defined:** 2026-09-07
**Origin:** вопрос владельца — «нужен ли нам correlation_id?»

## Требования

- **OBS-01**: По логам можно проследить одну задачу от приёма запроса до
  терминального состояния, не заходя в Postgres.
- **OBS-02**: HTTP-запрос и задача связаны в логах: существует строка,
  несущая одновременно идентификатор запроса и `job_id`.
- **OBS-03**: Вызывающий сервис может передать свой идентификатор, получить
  его обратно в статусе задачи и в вебхуке, и найти по нему наши логи.
- **OBS-04**: Клиентское значение не может испортить лог или payload вебхука:
  длина и набор символов ограничены, нарушение — явный отказ.

## Что уже есть, и почему второй внутренний id не нужен

`job_id` уже сквозной: он в payload'е asynq, в `jobs`, `job_inputs/outputs`,
`job_events`, `webhook_deliveries`. Payload намеренно не несёт ничего кроме
него (D-04) — воркер перечитывает состояние из Postgres. Заводить второй
внутренний идентификатор значит завести вторую сущность с тем же смыслом,
которая со временем разойдётся с первой.

**Дыра не в идентификаторе, а в логах.** `middleware.RequestID` от chi живёт
внутри одного HTTP-запроса и никуда не сохраняется; `internal/worker` не
логирует задачи вовсе. Сегодня «проследить задачу через процессы» = SQL, а не
`grep`. Это и есть боль, которую обычно называют «нужен correlation_id».

## Чего у нас нет и что клиент не может сделать сам

Клиенты — внутренние сервисы. При инциденте у сервиса на руках *его*
request id, а не наш `job_id`. Формально он может сохранить соответствие сам
(`job_id` возвращается синхронно), но:

- вебхук приходит **позже** и, возможно, на другой инстанс, а несёт только
  `job_id`;
- разбор инцидента начинается с логов вызывающего, а не с `job_id`.

## Решённые вопросы дизайна

**`Correlation-Id`, а не `trace_id`.** `trace_id` — термин с зафиксированным
контрактом (W3C Trace Context: 16 байт hex, порождается трассировщиком,
осмыслен только со span'ами). Занять имя без семантики значит получить, при
появлении трассировки, колонку `trace_id` с произвольными клиентскими
строками — либо миграция, либо поле, которое врёт именем. `correlation_id`
никакого контракта не несёт.

**Заголовок, а не поле формы.** Остальные параметры (`target`, `opts`,
`preset`, `callback_url`) описывают *что конвертировать*; этот — метаданные о
вызове. Без префикса `X-` (RFC 6648), API внутренний.

**Отсутствует — значит NULL.** Не генерировать своё: это вернуло бы второй
внутренний идентификатор, против которого весь первый раздел.

**Логирование из `internal/worker` — сознательное повторение прецедента.**
CLAUDE.md говорит, что `internal/*` не логирует. Проверено: конвенция
соблюдается везде, кроме `internal/api`, где она уже нарушена намеренно
(строки отказов вида `client_id=… reason=…`). Фаза повторяет это для воркера
в том же формате `key=value`, а не изобретает третий подход и не строит
инъекцию логгера ради чистоты, которой в кодовой базе уже нет.

## Не входит в фазу

**Трассировка (OpenTelemetry + Jaeger).** Отдельная фаза, и `Correlation-Id`
её не блокирует: `traceparent` придёт отдельным стандартным заголовком, а
`correlation_id` останется бизнес-ключом клиента.

Что выяснено заранее, чтобы та фаза не начиналась с сюрпризов:

- **Цепочка не будет одним водопадом.** Сервис асинхронный: API отвечает 202
  после постановки в очередь, воркер работает позже и, возможно, несколько раз
  (ретраи), вебхук — третий прыжок. Модель OTel для этого — **span links**, а
  не родитель-потомок; иначе трассы висят открытыми минутами, а ретраи
  слипаются в один span. В Jaeger это будет несколько трасс, соединённых
  ссылками.
- **Контекст класть в строку задачи, а не в payload asynq** — тогда воркер
  восстанавливает его так же, как всё остальное, и D-04 не получает
  исключения. Колонка из 66-02 — то же место.
- **NetworkPolicy в чарте только Ingress** (прочитано в шаблоне): egress к
  коллектору не заблокирован.
- **Песочница Landlock не помешает**: она ограничивает дочерний процесс
  движка, а не воркер. Сеть у воркера остаётся.
- У asynq нет официальной поддержки OTel — span в обработчике вручную.

## Порядок и почему он такой

01 идёт первым и, вероятно, снимает большую часть боли: без изменения схемы и
контракта API. 02 закрывает то, чего клиент не может сделать сам. Если после
01 боль ушла — 02 всё равно имеет смысл, но перестаёт быть срочным, и это
нормальный исход.
