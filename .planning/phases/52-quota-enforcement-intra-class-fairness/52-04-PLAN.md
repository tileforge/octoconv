<objective>
Turn the admission verdict into an HTTP contract: reject before the S3 write,
answer 429 with a machine-readable code and a limit-appropriate `Retry-After`,
log and count what would have been rejected, and give operations a global
kill-switch.

Purpose: QUOT-02 (fail-closed on every creation path), QUOT-03 (429 not 403,
`quota_exceeded` distinguishable from `rate_limited`) and QUOT-04 (observe-only
rollout) all land here. This is the single enforcement point D-09 chose.

Output: a gate and an error mapping in `handleCreateJob`, one new method on the
`api.Repo` interface, startup wiring in `cmd/api/main.go`, and the env/chart
plumbing for the kill-switch.
</objective>

In `internal/api/handlers.go`:

(1) Add `const quotaConcurrencyRetryAfterSeconds = 30` with its derivation stated in the comment (the project's "measured, not copied" convention): a concurrency slot frees only when one of this client's in-flight jobs reaches a terminal state, which is single-digit seconds for the image class and minutes for the av class, so a fixed hint must be long enough not to invite a hot retry loop and short enough not to stall a fast client; 30s sits an order of magnitude above the fast case and well below the slow one. Note that a daily rejection does NOT use this constant, because a constant would be wrong by hours there (D-11).

(2) Add `func secondsUntilUTCMidnight(now time.Time) int` returning whole seconds until the next UTC midnight, clamped to a minimum of 1 (a zero `Retry-After` would invite an immediate retry into the same rejection). Taking `now` as a parameter rather than calling `time.Now()` internally is what makes it unit-testable.

(3) Add `func writeQuotaError(w http.ResponseWriter, msg string, retryAfterSeconds int)`: set `Retry-After` to `strconv.Itoa(retryAfterSeconds)`, then `writeJSON(w, http.StatusTooManyRequests, map[string]string{"error": msg, "code": "quota_exceeded"})`. Status is 429 unconditionally — add a comment that 403 is forbidden here because a quota is a consumption limit, not an authorization boundary, and conflating them makes a client treat a temporary condition as permanent (QUOT-03). Do NOT widen `writeError`'s signature and do NOT add `code` to any other response — D-10 scopes it to the two 429s, and the general sweep is SEED-020.

(4) Add `func quotaRejection(err error) (msg string, retryAfterSeconds int, ok bool)` that switches with `errors.Is` over the three sentinels: `ErrConcurrencyLimit` → a prose message naming the concurrent-job limit for this conversion type plus `quotaConcurrencyRetryAfterSeconds`; `ErrDailyBytesLimit` and `ErrDailyJobsLimit` → their own prose messages plus `secondsUntilUTCMidnight(time.Now().UTC())`. Messages must describe only the caller's own limit — never a count, never another client's state, never the configured limit value (an operator reads limits from `manage-clients`, a client does not need them and should not be able to probe them). Returns `ok == false` for any non-quota error.

(5) Insert the pre-upload gate immediately AFTER the existing `s.maxEngineBytes[engine]` check and before every subsequent step (dimension checks, callback validation, `s.storage.Upload`): call `s.repo.PreAdmit(ctx, client.ID, engine, header.Size)`; when `quotaRejection` reports a quota error, emit a log line in the existing rejection format — `log.Printf("quota rejected: client_id=%s engine=%s reason=%s stage=preupload", client.ID, engine, jobs.QuotaReason(err))` — and `writeQuotaError`, then return. A NON-quota error from `PreAdmit` must NOT fail the request open and must NOT 500 the request either: log it and continue, because `Create`'s authoritative check still runs and is the correctness mechanism; say exactly that in a comment so a later reader does not "fix" it into a 500. Placement rationale in a comment: this is the earliest point at which `engine` and `header.Size` are both known, and it is upstream of `s.storage.Upload`, which is what keeps an over-quota client from repeatedly burning S3 (ROADMAP SC2b).

(6) Extend the existing `s.repo.Create` error branch: before the current generic `writeError(w, http.StatusInternalServerError, "failed to create job")`, call `quotaRejection(err)`; on a match, log `stage=create` with the same format and `writeQuotaError`, then return. Comment that reaching this branch means the request passed `PreAdmit` and lost the race at the lock (or the daily rollup moved), that no job row was created because the whole transaction rolled back, and that the already-uploaded object is left for TTL cleanup exactly as the preset-TOCTOU path above already does. The enqueue switch is never reached, so QUOT-02's "before enqueue" holds by construction.

Do not touch the enqueue switch, the response shape on success, or any other handler in the file.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted client → `POST /v1/jobs` | Multipart upload plus form fields; the only path that can create a job. |
| API → S3 | An upload consumes bandwidth and storage before any job row exists; an unbounded retry loop here is the resource-exhaustion vector. |
| API → client (429 body, headers, logs) | Anything placed in the error body, the `Retry-After` header, or a log line is disclosed to the client or to whoever reads logs. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-52-21 | Denial of Service | over-quota client burning S3 bandwidth/storage per attempt | mitigate | `s.repo.PreAdmit` runs before `s.storage.Upload`; a test asserts the upload call count is exactly 0 on a quota rejection. |
| T-52-22 | Elevation of Privilege | quota bypass via an unguarded creation path | mitigate | `handleCreateJob` is the only creation path (D-09); `cmd/mcp-server` and `cmd/mcp-http` both go through `internal/mcpserver/client.go` over HTTP and never touch the database. Plan 52-05 proves this by driving a real MCP tool, not by asserting it. |
| T-52-23 | Denial of Service | client hot-retrying into a rejection | mitigate | `Retry-After` is always set and always >= 1; a daily rejection returns seconds to UTC midnight rather than a constant that would be wrong by hours (D-11). |
| T-52-24 | Information Disclosure | quota error body leaking limits or other clients' usage | mitigate | Fixed prose per reason plus a fixed `code` literal — no counts, no configured limit values, no engine-population data. Asserted by the body-shape tests. |
| T-52-25 | Information Disclosure | `code` leaking onto unrelated error responses | mitigate | `writeError`'s signature is unchanged and `writeQuotaError` is a separate function; a test asserts non-quota bodies have exactly one key. |
| T-52-26 | Spoofing | fail-open when the pre-check itself errors | mitigate | A non-quota `PreAdmit` error deliberately continues to `Create`, whose in-transaction check is the authoritative gate — the request cannot be admitted without passing it. Documented at the call site and pinned by `TestCreateJob_PreAdmitInfraErrorDoesNotBlock`. |
| T-52-27 | Repudiation | silent rejections | mitigate | Every rejection logs `client_id`, `engine`, `reason` and `stage` in the file's existing rejection-log format, and increments the bounded counter through the observer closure. |
| T-52-28 | Tampering | kill-switch semantics inverted by an empty value | mitigate | Explicit-literal `== "true"` comparison, never `envInt64`'s empty-means-default path; a startup warning is logged when the switch is on so an operator cannot leave it enabled unnoticed. |
| T-52-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — no new dependency; `go.mod`/`go.sum` unchanged. |
