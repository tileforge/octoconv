this table.

(1) `CREATE TABLE client_limits` with columns exactly:
`client_id uuid NOT NULL REFERENCES clients (id) ON DELETE CASCADE`,
`engine text NOT NULL`,
`max_concurrent int`,
`max_daily_bytes bigint`,
`max_daily_jobs bigint`,
`created_at timestamptz NOT NULL DEFAULT now()`,
`updated_at timestamptz NOT NULL DEFAULT now()`,
`PRIMARY KEY (client_id, engine)`.
The three limit columns are nullable with NO default — NULL is the unlimited value (D-02, QUOT-01). Add
`CHECK (max_concurrent IS NULL OR max_concurrent >= 0)`,
`CHECK (max_daily_bytes IS NULL OR max_daily_bytes >= 0)`,
`CHECK (max_daily_jobs IS NULL OR max_daily_jobs >= 0)`.
Zero is deliberately legal and is NOT a sentinel: an explicitly-set `max_concurrent = 0` means "this client may run no jobs on this engine", which is how ROADMAP SC1's "allowed engine set" is expressed. State that in a comment on the column so the next reader does not mistake 0 for a disabled/unset marker.

(2) Do NOT add `CHECK (engine IN (...))`. Add a comment paragraph stating why, mirroring `0011_client_usage_daily.sql`'s equivalent paragraph and sharpening it: a stale allow-list here would abort every `INSERT INTO jobs` for a newly added engine (the admission read runs inside `Repo.Create`'s transaction, plan 52-03), i.e. it would break conversion, not merely fail to enforce a limit.

(3) `CREATE TRIGGER client_limits_set_updated BEFORE UPDATE ON client_limits FOR EACH ROW EXECUTE FUNCTION set_updated_at();` — reuse the function from `0001_init.sql`, never redefine it; note the reuse in a comment as 0011 does.

(4) `ALTER TABLE clients ADD COLUMN enforcement_mode text NOT NULL DEFAULT 'observe' CHECK (enforcement_mode IN ('observe', 'enforce'));`. No new trigger — `clients_set_updated` already exists from 0002. Comment must state that the `'observe'` default is what makes ROADMAP SC1 hold for already-provisioned clients: combined with D-02's NULL/absent-row semantics, both defaults independently preserve today's behavior.

(5) `CREATE INDEX jobs_client_engine_inflight_idx ON jobs (client_id, engine) WHERE status IN ('queued', 'active');` — the exact predicate plan 52-03's occupancy COUNT filters on (D-06). Derivation to state in the comment: that COUNT runs on every job creation while holding a per-(client, engine) advisory lock, so an unindexed scan would hold the lock for the duration of a scan of all in-flight rows; the existing `jobs_inflight_idx` is keyed on `created_at` alone and cannot serve a `client_id`/`engine` equality filter. If the D-06 predicate ever changes, this index must change with it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell → `manage-clients` → Postgres | Operator-supplied client id, engine string and numeric limits reach SQL. Not a client-facing surface, but a typo here silently changes enforcement for a real client. |
| `clients` table → every `/v1` request | `enforcement_mode` added here is read on the hot job-creation path in plan 52-03; a wrong default changes live behavior for all clients at once. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-52-01 | Tampering | `manage-clients set-limit` argument parsing | mitigate | `-` is the only NULL token; every other token must parse as a non-negative integer or the command aborts before touching the DB. No sentinel substitution, no silent clamp. |
| T-52-02 | Elevation of Privilege | `clients.enforcement_mode` default | mitigate | Column default is the literal `'observe'` with a two-value CHECK; a migration that defaulted to `'enforce'` would instantly reject traffic for every already-provisioned client. Acceptance criterion asserts `count(*) WHERE enforcement_mode <> 'observe'` is 0 after migration. |
| T-52-03 | Denial of Service | `CHECK (engine IN (...))` on `client_limits` | mitigate | Deliberately omitted. A stale allow-list would abort the job-creation transaction (plan 52-03 reads this table inside it), turning a limits-config defect into a total outage for a new engine class. |
| T-52-04 | Tampering | SQL injection via `engine` / `mode` strings | mitigate | All values are pgx bind parameters, never string-concatenated; `SetEnforcementMode` additionally allow-lists the two literals in Go before the query. |
| T-52-05 | Information Disclosure | `show-limits` output | accept | Operator-only local CLI already holding `DATABASE_URL` and `API_KEY_SALT`; it prints one client's own limits, no cross-client data. No new disclosure surface. |
| T-52-06 | Denial of Service | `CREATE INDEX` in migration 0013 | accept | Non-concurrent index build inside the migration transaction briefly blocks writes to `jobs`. Same posture as `0012_output_identity_and_retention_index.sql`; migrations are run as a deliberate deploy step on an internal service. |
| T-52-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — this plan adds no package-manager dependency. `go.mod`/`go.sum` are untouched; verified by the acceptance criterion that no new import is introduced beyond stdlib + already-vendored `pgx`/`uuid`. |
</threat_model>
