Rewrite the "Accepted daily overshoot" bullet in README's "Quotas and fairness" section. It currently says the daily cap "is checked against yesterday's-and-earlier committed usage, so it cannot see jobs still in flight" and that a client "can therefore overshoot its daily cap by up to `K x <per-engine upload ceiling>` bytes". Both halves are now false. Replace the bullet with one titled for what the check actually does, stating:
- the daily byte and job-count caps compare the request against today's committed usage PLUS all of the client's currently in-flight (`queued` and `active`) jobs on that engine, so the cap holds whether or not a concurrency cap is also set — the previous `K x ceiling` tolerance no longer exists and daily caps no longer need to be sized for it;
- the in-flight term is not scoped to a creation date: a job still in flight across a UTC midnight is charged against each day it is in flight and again against the day it terminates, which is deliberately conservative;
- the one residual an operator can still observe: because the pre-upload gate is unlocked by design, a burst of simultaneous requests from one client can upload before the authoritative check rejects them — wasted uploads, never over-admission — and that residual is measured by the phase's own burst test rather than assumed.

Add two short bullets to the same section, placed with the material they belong to rather than appended at the end:
- next to the limit-setting examples, that `set-limit` rejects an engine name that is not a known engine class and prints the valid set, so a typo fails loudly instead of writing a limit that is never matched; and that `clear-limit`/`show-limits` deliberately do not validate, so a row written before that check existed can still be listed and removed;
