Build the three narrow, additive surfaces the enforcement path in plans 52-03
and 52-04 will call into: the observe-only metric, the `rate_limited` error
code on the pre-existing 429, and the MCP proxy hop that carries a code and a

before enabling enforcement. D-12 needs the rejection to survive the MCP proxy.

function — each with a test. No enforcement logic in this plan.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API 429 response → client / MCP agent | Error bodies and headers cross to an untrusted-ish consumer; anything placed in them is disclosed. |
| upstream HTTP headers → MCP tool error text | `Retry-After` is attacker-influenceable if the MCP client is ever pointed at a hostile base URL; its value is interpolated into a string an agent reads. |
| client id → Prometheus label | Unbounded label values are a self-inflicted metrics DoS (the exact problem ACCT-04 closed). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-52-07 | Denial of Service | `octoconv_quota_would_reject_total` cardinality | mitigate | `client_id` routed through the existing `clientLabel`/`defaultClientAllocator`; `reason` is a closed three-value set; `engine` is a bounded compile-time set. A dedicated test asserts a malformed id lands on `overflow`. |
| T-52-08 | Information Disclosure | 429 body content | mitigate | Both 429 bodies carry only a fixed prose string and a fixed code literal — no client id, no engine-population data, no other client's state. `code` values are two hard-coded literals, never derived from input. |
| T-52-09 | Spoofing / Tampering | `Retry-After` interpolated into MCP tool error text | mitigate | Header value is only appended after it parses as a non-negative integer; a malformed or oversized header is dropped rather than echoed. |
| T-52-10 | Information Disclosure | API key leaking through the widened error path | mitigate | `redact(msg, c.apiKey)` retained on every return branch of `apiError`; new tests assert the key is absent from the code/retry-bearing branches specifically, since those are the new code paths `TestClient_KeyNeverLeaks` did not previously reach. |
| T-52-11 | Repudiation | Observe-mode evidence | mitigate | The counter is the QUOT-04 record of what would have been rejected; it is deliberately reused for actual rejections too so an operator's dashboard query does not change shape when enforcement is switched on. |
| T-52-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — no new dependency. `go.mod`/`go.sum` unchanged. |
</threat_model>
