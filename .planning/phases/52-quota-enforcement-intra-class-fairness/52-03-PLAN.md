<objective>
Build the admission gate itself: a serialized, transaction-scoped check that
runs as the first statement inside `Repo.Create`'s existing transaction, plus
a cheap non-locking pre-check the handler can call before the S3 write.

Purpose: this is the mechanism FAIR-01, QUOT-01 and QUOT-05 all reduce to. Its
one load-bearing property is that counting and inserting are not separable —
ROADMAP SC2a exists because a `SELECT count(*)` followed by an insert admits
twice under two replicas.

Output: `internal/jobs/admission.go`, a three-line change inside
`Repo.Create`, and a DATABASE_URL-gated test suite that proves the cap holds
under a concurrent burst.
</objective>

Advisory-lock key derivation: `func quotaLockKeys(clientID uuid.UUID, engine string) (int32, int32)` computing FNV-1a 32-bit hashes (`hash/fnv`, stdlib) of `clientID.String()` and `engine`, converted to `int32` (wrapping conversion is intentional and deterministic — say so). Derive the keys in Go rather than with Postgres's undocumented `hashtext()` so the mapping is deterministic, testable, and identical across replicas and PG versions.

Internal read helper `loadQuotaState(ctx, q pgxQuerier, clientID uuid.UUID, engine string)` returning enforcement mode plus the three nullable limits, using a single statement:
`SELECT c.enforcement_mode, l.max_concurrent, l.max_daily_bytes, l.max_daily_jobs FROM clients c LEFT JOIN client_limits l ON l.client_id = c.id AND l.engine = $2 WHERE c.id = $1`.
The LEFT JOIN is what makes "no row at all" and "row with NULL columns" indistinguishable at the read site — both yield nil pointers, both mean unlimited (D-02). Scan into `*int` / `*int64`. Define a tiny `pgxQuerier` interface with just `QueryRow(ctx, sql, args...) pgx.Row` so the same helper serves both `*pgxpool.Pool` and `pgx.Tx` without duplication.

`evaluate(ctx, q pgxQuerier, clientID, engine, inputBytes)` returning `(error, error)` — first is the quota verdict sentinel (nil when admitted), second is a real infrastructure error. Order of checks and short-circuits:
1. Load quota state. If all three limits are nil → return `(nil, nil)` immediately, doing NO further queries and taking NO lock. This is what makes ROADMAP SC1 free: a database with no `client_limits` rows performs exactly one extra indexed primary-key read per job creation and nothing else.
2. If `max_concurrent` is non-nil: `SELECT count(*) FROM jobs WHERE client_id = $1 AND engine = $2 AND status IN ('queued','active')` (build the status list from the `StatusQueued`/`StatusActive` Go constants, never inline literals). Reject with `ErrConcurrencyLimit` when `count >= *max_concurrent`. `>=` is deliberate and is what makes an explicit `max_concurrent = 0` deny the engine entirely.
3. If `max_daily_bytes` or `max_daily_jobs` is non-nil: `SELECT COALESCE(sum(bytes_in), 0), COALESCE(sum(job_count), 0) FROM client_usage_daily WHERE client_id = $1 AND engine = $2 AND day = (now() AT TIME ZONE 'utc')::date` — summed across `status` because the Phase 51 primary key includes it. Reject with `ErrDailyBytesLimit` when `bytes_in + inputBytes > *max_daily_bytes`, and with `ErrDailyJobsLimit` when `job_count + 1 > *max_daily_jobs`. The incoming request's own input size and its own +1 job participate, so the limit means "would exceed", not "already exceeded".
Checks evaluate in that order and the first violation wins; state that so the reason taxonomy is deterministic.

Immediately above the daily block, put the D-15 comment with its derivation, in full: `client_usage_daily` is written only at the terminal transition, so jobs admitted but not yet finished are invisible to this check and a burst can overshoot the daily cap. The overshoot is bounded by the concurrency cap: at most K in-flight jobs, each at most the per-engine input ceiling `s.maxEngineBytes[engine]` enforced in `handleCreateJob`, hence at most `K x MAX_INPUT_BYTES` bytes of unaccounted admitted work. Full reserve/consume accounting was rejected because it reintroduces a second source of truth plus reservation-leak failure modes on a path where the damage is already computable and small; with no reservation row written there is also nothing that could be double-counted when the job later completes (this is what resolves ROADMAP SC2b).

`admitLocked(ctx, tx pgx.Tx, clientID uuid.UUID, engine string, inputBytes int64) error` — the authoritative path:
1. Load quota state on `tx`; if all limits nil, return nil without locking.
2. `pg_advisory_xact_lock` with the derived keys, on `tx`.
3. Re-run the count/daily evaluation on `tx` (post-lock; the pre-lock state read is only used to decide whether locking is worth it).
4. On a violation: if enforcement is off for this request — `quotaDisabled` is true OR the loaded `enforcement_mode` is `observe` — fire `quotaObserver(clientID, engine, QuotaReason(verdict))` and return nil (admitted). Otherwise fire `quotaObserver` as well and return the sentinel. The observer therefore fires exactly once per rejected-or-would-be-rejected job on this path, in both modes — one counter, one taxonomy (D-14).
5. On no violation, return nil.
Infrastructure errors are wrapped `fmt.Errorf("quota admission: %w", err)` and abort the transaction; they are never converted into an admit.

`PreAdmit(ctx, clientID, engine, inputBytes) error` — the non-authoritative pre-upload gate, run on `r.pool` with NO advisory lock:
- Runs the same `evaluate`. When enforcement is off for this client (observe mode or the global kill-switch), it returns nil WITHOUT firing the observer — the authoritative `admitLocked` will fire it, and firing here too would double-count every observe-mode job.
- When enforcement is on and a violation is found, it fires the observer and returns the sentinel, so the handler can 429 before writing to S3; `admitLocked` will never run for that request, so there is still exactly one increment.
- Document precisely what it is and is not: it is an optimization that keeps an over-quota client from burning S3 bandwidth and storage on every attempt (ROADMAP SC2b's stated intent), and it is explicitly NOT the correctness mechanism — `admitLocked` is. Also document the residual: a request that passes `PreAdmit` and is then rejected by `admitLocked` leaves its just-uploaded object in place for TTL cleanup, exactly like the pre-existing preset-TOCTOU path in `handleCreateJob` already does.
- Also document the deviation from the literal wording of ROADMAP SC2b for the record: SC2b asks for an authoritative reservation before the S3 write with a release path on later failure; CONTEXT D-07/D-08/D-15 deliberately chose no reservation record at all (occupancy derived from `jobs.status`), so the pre-upload gate is advisory and the authoritative gate sits at the insert. The user-visible property SC2b protects — an over-quota client does not repeatedly burn S3 before its 429 — is delivered; the reservation-leak failure class SC2b's release path would create is avoided entirely.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client request → `Repo.Create` transaction | The only place a job row can be created; everything upstream of it is advisory. |
| API replica A ↔ API replica B (shared Postgres) | Two processes race for the same client's slots; correctness cannot rely on in-process state (the documented `internal/ratelimit` `replicas: 1` caveat this milestone must not repeat). |
| one client's quota state ↔ another client's | Occupancy counts and limit rows are per-client; a leak across this boundary would disclose another tenant's activity. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-52-12 | Tampering | check-and-admit race across replicas (TOCTOU) | mitigate | `pg_advisory_xact_lock(int, int)` acquired on the same `pgx.Tx` that performs `INSERT INTO jobs`; count and insert cannot interleave. Pinned by `TestConcurrentBurstAdmitsExactlyK` asserting exactly K admitted out of 12 simultaneous attempts. |
