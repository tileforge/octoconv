## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| build host -> pandoc release tarball | HTTP fetch of a prebuilt binary over the network at build time; a tampered/substituted tarball would ship a backdoored engine |
| pandoc-worker runtime -> untrusted job input | pandoc shells out on client-supplied markup in the container |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-49-SC | Tampering | pandoc static-release download | mitigate | pin the exact release version AND `sha256sum -c -` fail-closed on the selected-arch tarball BEFORE extraction; runtime `pandoc --version | grep "pandoc 3."` assertion catches a wrong/mis-extracted binary (mirrors Dockerfile.ocr-worker's tessdata SHA + version-grep discipline). This is a prebuilt-binary download, NOT an npm/pip/cargo package install — the package-legitimacy checkpoint is N/A; SHA-pinning is the supply-chain control. |
| T-49-01 | Elevation of Privilege | runtime container | mitigate | USER nobody (unprivileged), matching every other engine-worker image. |
| T-49-02 | Information Disclosure / Elevation | TeX shell-escape / \input file read | mitigate | NO TeX toolchain is installed at all (lean image) — the ->pdf/latex-engine attack surface simply does not exist in this container; pandoc itself runs `--sandbox` (pandoc.go, unchanged). |
| T-49-03 | Denial of Service | image cold-start / registry pull | accept | the single static binary + slim base keeps the image small; scale-from-zero economics are Phase 50's concern. |
