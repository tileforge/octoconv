<objective>
Give the probe engine a bound on its input. The phase-60 measurement showed the
cost is per PAGE (~2.0 s/page), not per byte, and that the timeout is therefore
the only thing standing between a 3000-page PDF and ten minutes of worker time
followed by a transient failure that retries and does it again.

Purpose: after this plan a too-large document is refused at admission with a
machine-readable code and no S3 write, and the one that slips past the cheap
check is refused terminally before Ghostscript starts. Output: one bound, two
enforcement points, and a test that fails if they ever disagree.
</objective>

## Task 1 — one bound, one comparison

Create `internal/convert/probebounds.go`:

- `var ErrProbeTooManyPages = errors.New("probe: pdf page count exceeds bound")`
- `func EnforceProbeMaxPages(count, max int) error` — `max == 0` means "no cap
  configured", matching `enforceMaxPages`'s zero-value convention in
  `ocrguards.go` exactly. Do NOT reuse `ErrOCRTooManyPages`: the codes are the
  same but the engines' bounds are not, and a shared sentinel would make the
  OCR path's terminal classification silently cover probe.

The error must carry both numbers, like OCR's does, so the failure message says
what the file had and what the bound was.

**Verify:** table test over the boundary — `max-1`, `max`, `max+1`, and `max == 0`.

## Task 2 — the default value, derived rather than picked

Phase 60 measured ~2.0 s/page. `PROBE_ENGINE_TIMEOUT` is 180 s, so the timeout
alone admits roughly 90 pages before it becomes the limit. A ceiling above that
is decoration — the timeout fires first. A ceiling far below it refuses work the
service can do.

State the arithmetic in the comment, pick the value from it with an explicit
margin, and mark it **PROVISIONAL** in the same words `PROBE_ENGINE_TIMEOUT`
used before it was measured. Do not invent a round number and justify it after.

Wire `PROBE_MAX_PAGES` through `cmd/probe-worker/main.go` and `cmd/api/main.go`
using the existing `envInt` helpers. Document it in `.env.example`, the chart
ConfigMap and `values.yaml`, and `docs/SANITIZE.md`.

**Verify:** a test asserts the env value reaches both the API server and the
probe converter — the same shape as `cmd/ocr-worker/main_test.go`'s
`OCR_MAX_PAGES` assertion, which exists because a bound that is configured and
not plumbed is a bound that does not exist.

## Task 3 — the API gate, before the storage write (PROBE-01)

In `handleCreateJob`, after the engine class is known and **before**
`s.storage.Upload`, in the same region as the `convert.Dimensions` bomb guard:

- Only for `operation == convert.OperationSanitize` and a PDF source.
- Bounded peek, re-stitched onto `rest` — copy the `Dimensions` pattern
  precisely, including returning the untouched stream onward. A peek that
  consumes bytes the upload then misses is a corruption bug, so the test must
  assert the stored bytes are byte-identical to the submitted ones.
- Count via `internal/inspect`'s existing bounded extractor. It is unexported
  today (`extractPDFPageCount`), so add a **narrow** exported entry point —
  `inspect.PDFPageCount(r io.ReaderAt, size, maxBytes int64, tr *Tracker)` —
  rather than calling `AnalyzePDF`, which also runs text-layer detection and
  would spend that budget on every sanitize upload for an answer nobody asked
  for here.
- **`pdfcpu` must not be called from `cmd/api`.** Phase 58 D-02a refused the
  project's first parser-on-untrusted-bytes in the API process, and
  `sanitizeverify.go`'s own header says in as many words that its use of pdfcpu
  is the exception those conditions were written for and is not a precedent.
  The API gate is a bounded byte scan; that is the whole reason it is allowed to
  be wrong (return unknown) and the whole reason the worker gate exists.
- **Known** count over the bound → 422 carrying `too_many_pages`. That string
  exists today only in the ASYNC vocabulary (`internal/worker/descriptors.go`);
  the synchronous one is `internal/errcode`. Add
  `errcode.TooManyPages = "too_many_pages"` — deliberately the same string in
  both, with the same cross-reference comment `InvalidOptions` already carries
  ("same name as the async code (D-03)"). A client should not have to learn two
  spellings for one condition, and `errcode`'s doc-sync test plus
  `docs/openapi.yaml` are what keep the two from drifting. **Unknown** → admit, and log at the same level the other
  content-validation rejections log, so an operator can see how often the cheap
  gate abstains.

**Verify:** a storage double whose `Upload` calls `t.Fatal`. If the rejection
path ever moves below the upload, the test fails loudly rather than passing with
a wasted write. Inversion: move the check below `s.storage.Upload` → that test
fails naming the call. Record the output.

## Task 4 — the worker gate, terminal (PROBE-02)

Before the first Ghostscript pass in the sanitize path:

- Count pages accurately with `pdfcpu`, which this file already imports and
  which is permitted here for the three reasons its header states: isolated
  worker, measured timeout, cgroup limits. This is where the accurate count is
  affordable and allowed, which is exactly why the API's cheap gate may abstain.
- `EnforceProbeMaxPages` with the same bound.
- `isProbeTerminal` returns true for `ErrProbeTooManyPages`, and
  `probeFailureCode` maps it to the existing `CodeTooManyPages`.

**Verify:** extend `internal/worker/pinning_test.go` with the probe row —
`ErrProbeTooManyPages` → terminal, code `too_many_pages` — **and** assert in the
same test that a `context.DeadlineExceeded` from the same handler is still
TRANSIENT. The two verdicts are opposites on purpose and the test should say so;
pinning only the new one would let a later change collapse them without notice.

Inversion: remove the `ErrProbeTooManyPages` branch from `isProbeTerminal` → the
pinning row fails with "transient, want terminal". Record the output.

## Task 5 — the two gates cannot drift

One test asserts that the API path and the worker path resolve the same bound
from the same env var and call the same function. The cheapest honest form: a
test that sets `PROBE_MAX_PAGES`, builds both, and asserts both reject the same
count and admit `count-1`.

This phase deliberately puts one rule in two places (CONTEXT D-04). That is the
shape this project has been burned by four times, so the test that holds them
together is not optional and its absence is a plan failure, not a nice-to-have.
