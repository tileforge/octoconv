# Pitfalls Research

**Domain:** Adding progress/ETA/live-push/listing/cancellation to an existing production-hardened Go async file-conversion service (asynq + Postgres + S3, per-engine worker containers)
**Researched:** 2026-07-24
**Confidence:** HIGH for pitfalls grounded directly in this codebase's existing code (`internal/convert/exec.go`, `internal/worker/worker.go`, `internal/reconciler/reconciler.go`, `internal/jobs/repo.go`); MEDIUM for general ffmpeg `-progress`/SSE ecosystem pitfalls verified against ffmpeg docs and widely-corroborated community sources; LOW flagged inline where only single-source community wisdom applies.

## Critical Pitfalls

### Pitfall 1: Progress-write storms hammering Postgres

**What goes wrong:**
ffmpeg's `-progress pipe:1` (or a file target) emits a full key=value block **every single frame** (or ~every 0.5-1s for `-stats_period`, but per-frame by default for `-progress`). A naive integration reads each block and calls `UPDATE jobs SET progress = $1 WHERE id = $2` synchronously on every emission. At 30fps this is ~30 writes/sec per in-flight job; with `AV_WORKER_CONCURRENCY` > 1 or multiple engine classes converting concurrently, this multiplies into a write-amplification problem against the single Postgres system-of-record that every other component (API polling, reconciler, webhook gap-sweep) also depends on for low-latency reads.

**Why it happens:**
It's the "obviously correct" naive translation of "ffmpeg tells us progress → we want clients to see progress" — nobody deliberately designs a write-storm, it falls out of wiring the pipe reader directly to the repo's update method with no throttle in between.

**How to avoid:**
Throttle writes on **two independent axes**, and only write when BOTH gates pass (not either):
1. **Time-based:** never write more often than a fixed interval (e.g. 1s) — track `lastWriteTime` in the reader goroutine, skip any progress tick that arrives sooner.
2. **Delta-based:** never write unless progress has moved by at least a threshold (e.g. ≥1 percentage point) since the last written value — a stalled/no-op ffmpeg tick (same `out_time_ms`, e.g. between duplicate progress lines) must not force a write just because the clock ticked.
Additionally: the final 100%/done write and any terminal (canceled/failed) write must always go through regardless of throttle state — the throttle governs *intermediate* updates only, never the terminal one, or a job could finish with a stale 87% progress row.
This mirrors the codebase's existing "guarded transition" discipline (`internal/jobs/repo.go` — every terminal status change already goes through a single `transition` helper with a `SELECT...FOR UPDATE` + allow-list); a **separate, cheaper** update path for progress (no need for full transactional guarding — a stale progress read is a display nit, not a correctness bug) is appropriate, but it must not use the row-locking `transition` helper per-tick (that would serialize progress writes against status-transition writes on the same row and reintroduce lock contention on the exact row the reconciler's `FindStale` query scans).

**Warning signs:**
- Postgres connection pool exhaustion / `pgxpool` wait-time metrics rising specifically during video/audio conversions (not image/document jobs, which are short and won't show it).
- `pg_stat_statements` showing the progress-UPDATE as the single highest-call-count query in the system, dwarfing everything else, on any moderately loaded worker.
- Local dev "feels fine" (one job at a time) but a KEDA-scaled fleet of av-workers (already proven capable of concurrent scale-out per Phase 28's load-proof) turns this into a real bottleneck — this is precisely the kind of "looks done, isn't" gap that only a live multi-job load test surfaces, matching this project's own established pattern of catching such gaps only under live proof (v1.8 retrospective: "two bugs surfaced only during live proof, not static checks").

**Phase to address:**
The phase implementing ffmpeg progress parsing / the progress-pipe-to-Postgres wiring — this must be a first-class design constraint of that phase's plan, not a follow-up optimization. Verification should include an explicit throttle unit test (inject N progress ticks in <1s and <1% deltas, assert exactly 1 write) plus a live multi-job concurrent-conversion smoke test measuring actual UPDATE call counts.

### Pitfall 2: Parsing ffmpeg `-progress` output incorrectly

**What goes wrong:**
Several distinct sub-mistakes, all commonly seen when integrating `-progress`:
- Using `out_time` (a formatted `HH:MM:SS.microseconds` string) instead of `out_time_ms` and doing fragile string-based duration parsing instead of a plain integer divide.
- **The trap is the reverse of what the name implies**: `out_time_ms` in ffmpeg is documented/known to actually report **microseconds**, not milliseconds, despite the field name — dividing by 1000 instead of 1,000,000 silently produces a progress percentage inflated by 1000x. This is a well-known ffmpeg wart, not a hypothetical.
- Dividing `out_time_ms` by a `source_duration` that is zero, unknown, `NaN`, or negative (e.g. a container that reports a garbage/absent duration, or a live/streamed input) — a naive `progress = elapsed / duration` panics or produces `Inf`/`NaN` written straight into a numeric Postgres column, or worse, silently written as a huge/negative percentage the client sees.
- Progress exceeding 100% (rounding, or `out_time_ms` briefly overshooting the last known duration due to encoder lookahead/B-frame reordering) or moving backward between ticks (non-monotonic — some encode passes, especially two-pass or when a stream has variable frame timestamps, can report `out_time_ms` that doesn't strictly increase tick to tick).
- Trusting the `speed=` field for ETA math without accounting for its own noise: `speed` is itself a coarse, recently-averaged ratio ffmpeg computes internally, and it fluctuates hard in the first few seconds of a run (start-up bias) and near the very end (buffering/flush behavior) — an ETA computed as `(1-progress)/speed * elapsed` naively during the first tick can report wildly wrong (sometimes 0 or negative) ETAs before the estimate stabilizes.

**Why it happens:**
`-progress` is a thin, deliberately unstructured key=value stream (not JSON, not versioned) intended for scripting — ffmpeg's own docs do not promise strict monotonicity or bounded ranges, and the microseconds-not-milliseconds naming bug in `out_time_ms` is a widely-reported but never-fixed (as of current ffmpeg) documentation/naming mismatch that catches nearly every first-time integrator.

**How to avoid:**
- Use `out_time_ms` (confirm empirically against the pinned `ffmpeg n8.1.2` build in this repo's own av-worker container — this project's own precedent, per `AV_ENGINE_TIMEOUT` measurement discipline, is "measure, don't assume" for anything ffmpeg-version-sensitive) and divide by 1,000,000 for seconds, not 1,000.
- Clamp `progress` to `[0, 100]` (or `[0, 1]`) before writing — never trust the raw computed ratio.
- Treat `source_duration` as **required input already available in this codebase**: `internal/convert/avduration.go`/`audioduration.go` already probe duration via ffprobe *before* conversion starts (existing `EnforceMaxDuration`/duration-guard machinery) — reuse that already-validated, already-guarded duration value as the percentage denominator rather than re-probing or trusting a client-supplied value. If duration is zero/unparseable (which the existing guard should already reject as terminal before conversion even starts, per `isAudioTerminal`'s ffprobe-failure classification), progress must fall back to an **indeterminate** state (matching PROJECT.md's own stated fallback: "indeterminate-фолбэк для остальных движков") rather than attempting a divide.
- Reject/clamp non-monotonic ticks: keep a `lastProgress` in the reader goroutine and only write forward-moving values (`if newProgress < lastProgress { skip or clamp to lastProgress }`), so a client polling never sees progress visibly rewind.
- Treat `speed=` as ETA input only after a warm-up window (e.g. ignore the first N ticks or first few seconds) and/or smooth it (moving average) rather than using the instantaneous value; alternatively derive ETA purely from `elapsed / progress * (1 - progress)` (pure progress-ratio-based, no dependency on ffmpeg's own speed estimate) as a simpler and more robust primary source, with `speed` as a secondary/display-only field.

**Warning signs:**
- Progress values >100% or negative observed in `job_events`/logs during manual testing with real video files (not just synthetic fixtures).
- ETA flapping wildly between polls in early manual QA (a strong tell the speed-field-without-smoothing mistake is present).
- A unit test asserting `out_time_ms / 1000` "looks right" against a *short* test clip — this is exactly the trap: a 1000x error on a 2-second test clip visually looks plausible, and only shows up wrong against a longer real clip. Any progress-parsing test suite MUST include at least one multi-minute-duration fixture (even if the actual conversion is faked/mocked for speed) to catch the units bug.

**Phase to address:**
The phase implementing the ffmpeg `-progress` parser (likely a new `internal/convert` helper, e.g. `progressreader.go`, parallel to the existing `avduration.go`). Verification: unit tests with recorded real `-progress` output fixtures (captured once from the actual pinned ffmpeg n8.1.2 binary, not hand-written, to catch any n8.1.2-specific field quirks) covering: normal run, duration-unknown input, an artificially non-monotonic fixture, and a >100%-overshoot fixture.

### Pitfall 3: Attaching a progress pipe to exec.Cmd breaks the Setpgid process-group-kill contract

**What goes wrong:**
This is the single highest-risk pitfall for this milestone because it directly threatens `internal/convert/exec.go`'s `runCommand` — the load-bearing hardening primitive underpinning every engine class shipped since Phase 9 (LibreOffice zombie-reaping) and reused verbatim through AV/audio. The existing `runCommand` contract is: spawn with `Setpgid: true`, run `cmd.Wait()` in a goroutine, and on `ctx.Done()` send `SIGKILL` to `-cmd.Process.Pid` (the whole process group) then block on `<-done` to reap. Progress reporting needs ffmpeg to write `-progress pipe:1` (or a named pipe/fd) to a *separate* stream from stdout/stderr (which `runCommand` already fully buffers via `bytes.Buffer`), which means a **new** `io.Pipe`/`os.Pipe` attached as an extra file descriptor, read by a **new background goroutine** distinct from the existing `done := make(chan error, 1); go func() { done <- cmd.Wait() }()` goroutine.

Concrete ways this breaks the existing contract if bolted on carelessly:
1. **Pipe reader goroutine leak on timeout/cancel**: if the progress-reading goroutine blocks on `pipeReader.Read()` and the process is SIGKILLed, the write end of the pipe closes (returning `io.EOF` to the reader) *only if the pipe's write-end file descriptor is actually closed*. If the write end is a fd passed via `cmd.ExtraFiles` and the child dies via SIGKILL, the OS does close the fd — BUT if a wrapper library (e.g. some progress-parsing packages spawn their own internal goroutine holding a duplicate fd, or the caller keeps the write-end `*os.File` open in the parent process too, e.g. because the same `*os.File` used to construct `cmd.ExtraFiles` was never closed in the parent after `Start()`), the reader will block forever on that dangling fd — an actual goroutine leak, worse under load because every canceled/timed-out job leaks one more goroutine permanently.
2. **Not reaped before the pipe closes**: `runCommand`'s existing "`<-done` — reap" step must stay unconditionally required. If a progress-reading goroutine is added but the `select` block's cancellation branch is refactored to also wait on the pipe-reader goroutine finishing (e.g. via a second channel merged into the select), it's easy to introduce a deadlock: SIGKILL fires, the child's process group dies, but if the progress pipe's read loop is waiting on a channel that only closes when `cmd.Wait()` returns AND `cmd.Wait()` internally waits for any goroutines copying to/from `Stdin`/`Stdout`/`Stderr` it started internally to complete (documented Go behavior) — if the progress fd were wired through `cmd.Stdout` reuse rather than a genuinely separate `ExtraFiles` fd, `cmd.Wait()` could block on drainage that never happens once the write side is gone mid-read.
3. **Whole-process-group-kill guarantee silently regressing to per-process kill**: if a future refactor of `runCommand` to support progress introduces a *second* command invocation path that doesn't go through the same `Setpgid`+`syscall.Kill(-pid, ...)` code, a canceled AV job's ffmpeg child could orphan exactly the class of process this project has spent multiple phases proving does NOT happen (Phase 9's live zombie-reaping proof, the AV Phase 34-37 hardening).

**Why it happens:**
Progress reporting is naturally implemented by developers as "just add a callback/reader on the side" without re-deriving why `runCommand`'s current shape (single `cmd.Wait()` goroutine, single `select`, blocking reap) is exactly as complex as it needs to be and no more — any addition that introduces a second concurrent "wait for this to finish" primitive needs the SAME cancellation-safety analysis the original code got, and it's easy to skip that analysis because "it's just reading a pipe for progress, not the actual work."

**How to avoid:**
- Do NOT modify the shared `runCommand` helper's core kill/reap contract. Instead, extend it with an **optional, explicitly-scoped progress channel parameter** whose reader goroutine is provably bounded by the SAME lifecycle as the existing `done` goroutine — i.e., the progress-pipe's write-end fd must be owned and closed by the exact same code path that already guarantees process-group death (SIGKILL), and the reader goroutine must select on **both** `ctx.Done()` and pipe-EOF, never block unconditionally on `Read()` alone. Concretely: use `os.Pipe()`, pass the write end via `cmd.ExtraFiles`, **close the parent's copy of the write-end `*os.File` immediately after `cmd.Start()`** (this is the single most common bug in exactly this pattern — forgetting to close the parent's fd copy means the read side never sees EOF even after the child dies, because the parent process itself still holds the fd open) — then the reader goroutine's `Read()` naturally unblocks with EOF the instant the child (and its inherited fd) dies, with no extra signaling needed.
- Add an explicit unit test (mirroring this project's own `exec.go`-adjacent hardening test style) that: starts a fake long-running command with a progress pipe, cancels the context, and asserts (a) the process group is actually dead (no PID lookup succeeds), (b) the progress-reader goroutine has exited (e.g. via a `sync.WaitGroup` the test can `Wait()` on with a short timeout), and (c) no descriptor/goroutine leak via `runtime.NumGoroutine()` delta across many cancel cycles.
- Treat this as a **live-verification-required** item per this project's own established pattern (Phase 9's "live process-kill proof discovered an actual zombie-reaping gap a mocked test would have declared safe") — a live test that actually SIGKILLs a real ffmpeg mid-progress-stream and confirms zero orphaned processes AND zero leaked goroutines is non-negotiable before this phase can close, exactly as it was for LibreOffice's `soffice.bin`.

**Warning signs:**
- `go test -race` passing is NOT sufficient evidence here — the risk is a leak/deadlock under cancellation, not a data race; a leaked goroutine or blocked-forever reader will not show up in `-race` output.
- Rising goroutine count over time in a long-running worker process under repeated cancel/timeout cycles (`runtime.NumGoroutine()` via `/metrics` or pprof) — this is the concrete, measurable warning sign to add as a metric/alert, not just a one-time test.
- Any code review finding a `cmd.ExtraFiles` write-end `*os.File` that is never explicitly `.Close()`d in the parent after `Start()`.

**Phase to address:**
The phase that wires ffmpeg's `-progress` output into the worker (do NOT bundle this with the progress-parsing-logic phase from Pitfall 2 unless the same plan explicitly budgets time for a live cancel/timeout proof — this is exactly the kind of item this project's retrospectives call out as "looks done in a mocked test, isn't"). Should be its own gated, live-verified plan given the project's history of exactly this class of gap (Phase 9 zombie-reaping) recurring.

### Pitfall 4: SSE connection/goroutine leaks and proxy/auth/fan-out mistakes

**What goes wrong:**
Several distinct SSE-specific failure modes:
1. **Goroutine/connection leak on client disconnect**: an `http.ResponseWriter`-based SSE handler that writes progress updates in a loop (e.g. `for { select { case p := <-progressCh: w.Write(...) } }`) will hang forever if it never detects the client going away — `net/http` DOES cancel `r.Context()` on client disconnect (HTTP/1.1 connection drop or HTTP/2 stream reset), but only if the handler actually selects on it — many naive tutorials write a bare `for { fmt.Fprintf(w, ...); flusher.Flush() }` loop with no `select` on `ctx.Done()` at all, which then blares writes into a closed connection until the *next* write finally errors, potentially much later, or never if writes have stopped entirely and it's just blocked reading from a channel with no timeout.
2. **Proxy/reverse-proxy response buffering**: any intermediary between client and API (nginx, cloud load balancers, some corporate proxies) buffers responses by default unless explicitly told not to (`X-Accel-Buffering: no` for nginx; `Content-Type: text/event-stream` alone is not always sufficient) — an SSE stream that works perfectly in local dev (direct connection) can silently batch/delay all the way to end-of-stream once it goes through a real internal-network hop, defeating the entire "live push" point. Since this project's clients are internal services (possibly behind internal load balancers per the k8s Ingress/Service layer added in Milestone v1.6), this must be verified against the actual deployment topology, not just localhost.
3. **Unauthenticated or cross-client SSE**: because SSE (a long-lived streaming HTTP GET) is just a long-lived request, it is easy to accidentally wire the SSE route outside the existing chi auth middleware chain, or to forget the same ownership check `handleGetJob` already applies (`job.ClientID != client.ID` → 404, never 403, per this project's established invariant) — an SSE endpoint that streams job progress by ID without re-checking ownership on stream-open is a direct violation of the project's own hard-won 404-not-403 cross-client-access invariant (Phase 1).
4. **Unbounded fan-out**: if progress events are broadcast via an in-memory pub/sub (e.g. a `map[jobID][]chan Event]`) with no cap, a client that opens many SSE connections to the same job (retry-without-backoff bugs on the client side, or a misbehaving internal service) can accumulate unbounded slices of channels, or — worse — if progress writes are the SAME throttled Postgres-write path from Pitfall 1, an SSE fan-out that re-queries Postgres per connected client per tick (rather than sharing one upstream progress feed per job, fanned out to N downstream SSE connections) reintroduces a second write/read storm on top of the direct-DB-write storm, scaling with the number of connected SSE clients, not just the number of active jobs.

**Why it happens:**
SSE in Go is deceptively simple to get "working" for a demo (write bytes, flush) but every one of these failure modes only manifests under conditions absent from a quick manual test: client disconnect mid-stream, real network intermediary, cross-client testing, or concurrent-connection load.

**How to avoid:**
- Every SSE handler MUST `select` on `r.Context().Done()` alongside the progress-event channel, and MUST return promptly (freeing goroutines/resources) the instant the context is done — this is directly analogous to `runCommand`'s existing discipline of always selecting on `ctx.Done()` rather than blocking unconditionally.
- Mount the SSE route through the SAME chi middleware chain as `GET /v1/jobs/{id}` (API-key auth, rate limiting) — do not create a parallel router/route-group for streaming endpoints. Explicitly re-derive the ownership check (`job.ClientID != client.ID` → `404`) at stream-open time, matching the existing pattern verbatim, not a bespoke reimplementation.
- If deploying behind any reverse proxy/ingress (this project already has a k8s Ingress-equivalent via the Helm chart and Service layer from Milestone v1.6), set the buffering-disable header/annotation for the SSE route specifically and live-verify (not just unit-test) that events actually arrive incrementally through the real deployed path, not just via direct `curl` to the pod — this project's own retrospective pattern ("live infra proofs are irreplaceable but expensive," v1.8) applies directly here.
- Design the progress fan-out as ONE upstream feed per job (e.g. a single Postgres LISTEN/NOTIFY channel, or a single in-process broadcaster reading the same throttled progress updates already being written for the polling `GET /v1/jobs/{id}` path) multiplexed to N SSE subscribers in-memory — never let SSE subscriber count multiply backend read/write load. Cap the number of concurrent SSE connections per job and/or per client as a defensive limit, reusing the existing per-client rate-limiting infrastructure (`internal/ratelimit`) rather than inventing a new limiter.
- If using Postgres LISTEN/NOTIFY for the fan-out signal, remember NOTIFY payloads are capped (8000 bytes) and are NOT durable/guaranteed-delivered if no listener is connected at NOTIFY time — treat it as a wake-up signal only ("something changed, re-read the row"), never as the sole source of truth for the progress value itself, exactly mirroring this project's own "Postgres is system of record, Redis/asynq only transient" architectural principle already documented in ARCHITECTURE.md.

**Warning signs:**
- Manual test only ever done via direct `curl http://localhost:8090/...` from the same host as the API — never through the compose/k8s network path with a real intermediary.
- No load test with >1 concurrent SSE client per job before shipping.
- Code review finds the SSE route registered outside the existing `r.Route("/v1", func(r chi.Router) { r.Use(authMiddleware...) ... })` block (or equivalent), or finds it re-deriving auth differently rather than reusing existing middleware.

**Phase to address:**
The phase implementing SSE — should explicitly include a live-network verification step (through the real docker-compose network topology at minimum, ideally through the k8s Ingress too given this project's dual-deployment reality) as a scripted, repeatable gate, not a one-off manual `curl`, matching the project's established "live-gate as self-contained script" pattern (`scripts/keda-gate.sh`, etc.).

### Pitfall 5: Cancellation races — cancel-after-done, orphaned workers, resurrection via reconciler/retry

**What goes wrong:**
This is the most structurally dangerous pitfall because it interacts with THREE existing hardened subsystems simultaneously (guarded transitions, the reconciler sweep, and asynq retry), and a naive cancellation implementation can silently break invariants in any of them:

1. **Cancel-after-done race**: `POST /v1/jobs/{id}/cancel` arrives at the API at the exact moment the worker's `process()` has already called `MarkDone` (or `MarkFailed`) but the API's read of current status (to decide whether cancellation is even valid) is stale. Without a guarded transition (same `SELECT...FOR UPDATE` + allow-list pattern `internal/jobs/repo.go`'s `transition()` already uses for every other status change), a cancel request could either (a) silently no-op against a job that already finished successfully — acceptable if handled correctly — or (b), worse, flip a `done` job back to `canceled` after the client already received/is about to receive the real result via webhook, corrupting the client's view of what actually happened.
2. **Cancel reaching the wrong/no worker**: the actual in-flight ffmpeg/whisper/soffice process lives inside a specific worker pod's `runCommand` goroutine — there is no existing mechanism for the API process (which only talks to Postgres/Redis) to signal "kill this specific OS process" to a specific worker replica. A signal must be relayed indirectly: Postgres row update (`status = canceling` or a `cancel_requested` flag) → the worker's `process()` loop must poll/check for it periodically DURING the long-running `conv.Convert()` call (which today runs synchronously to completion or timeout with no interruption point) → the worker must then actively cancel its OWN `context.Context` passed into `runCommand`, which (correctly, per the existing hardened contract) SIGKILLs the process group. If this signal-checking loop doesn't exist (e.g. only checked before `MarkActive`, never during the multi-minute `conv.Convert()` call itself), "cancel" becomes purely cosmetic — the job keeps consuming a worker slot and CPU for its full natural `ENGINE_TIMEOUT` regardless of the cancel request, defeating the entire feature's purpose for the workloads (video/audio, 700+ second timeouts) where cancellation matters most.
3. **Reconciler re-enqueuing a canceled job**: `internal/reconciler/reconciler.go`'s `FindStale` query currently matches ANY row with `status IN ('queued','active')` past a staleness threshold — it has no awareness of a future `canceling`/`cancel_requested` intermediate state. If cancellation is implemented as a transient intermediate status (e.g. `active` with a side-flag) rather than an immediate terminal transition, a job sitting in "canceling" past `ActiveStaleAfter` would be swept up by the EXISTING stale-job logic and re-enqueued via `EnqueueImageConvert`/`EnqueueAVConvert`/etc., directly resurrecting a job the client explicitly asked to stop — a severe regression of intent, not just a minor bug. Any new intermediate status/flag MUST be explicitly excluded from `FindStale`'s query (or the query must be extended with an additional `AND` clause / an explicit canceling-aware branch), and this exclusion needs its own test, not just an assumption that "canceled is terminal so it's fine" — the risk is specifically in the TRANSIENT window between "cancel requested" and "cancel actually applied."
4. **Double-processing on asynq retry resurrecting a "canceled" task**: if the in-flight worker's `process()` call is aborted (via context cancellation) partway through, and the handler returns a plain (non-`SkipRetry`-wrapped) error because it doesn't recognize "job was canceled" as its own outcome, asynq's default retry policy will requeue the SAME task and a fresh worker replica will pick it up, call `MarkActive` — which (per the existing guarded-transition allow-list in `repo.go`) should already reject re-activating a job whose current status is anything other than the expected pre-active states — but ONLY if the cancellation path actually flips status to a value `MarkActive`'s allow-list excludes. This is exactly why every existing `Handle*Convert` function already comments "Already active/done/canceled — let asynq drop it rather than loop" at the `MarkActive` call site: canceled is ALREADY anticipated as one of the statuses that must block re-activation. The pitfall is only in NOT explicitly wiring the cancel handler's terminal error return through `asynq.SkipRetry` (mirroring every other terminal-classification branch in `worker.go`) — a cancellation-detected-mid-flight abort must return `fmt.Errorf("%w: canceled", asynq.SkipRetry)`, never a bare unwrapped error that would trigger a real retry of a job the client explicitly stopped.
5. **Partial output left in S3**: if a job is canceled mid-upload (after `conv.Convert()` succeeds but before/during `h.uploadFrom`/`h.repo.AddOutput`), the partial/orphaned S3 object under `results/{job_id}/...` is never cleaned up by any existing mechanism — MinIO's ILM TTL rule (Phase 4) will eventually clean it up on the same 7-day default schedule as everything else, which is probably an ACCEPTABLE residual (matching this project's existing "accepted residual risk" precedent style, e.g. the chromium `file://` residual read from v1.3) rather than something requiring new S3 cleanup code — but this must be an EXPLICIT accepted-risk decision documented in the phase's CONTEXT/decisions, not a silent gap nobody noticed.
6. **Redis pub/sub (or any push-based cancel-signal channel) being unreliable**: if the mechanism used to notify a running worker of a cancel request is Redis pub/sub (fire-and-forget, no delivery guarantee, no persistence for a subscriber that isn't currently listening), a worker that misses the pub/sub message (e.g. briefly disconnected from Redis, or the message published before the worker's subscription for that job_id was established) will never learn about the cancellation and run the job to natural completion/timeout. The cancel signal MUST be idempotent and reconcilable from Postgres — i.e., the worker's long-running loop should POLL the job's row (or a lightweight cancel-flag) periodically as the source of truth, with pub/sub (if used at all) purely as a low-latency OPTIMIZATION to shorten the polling interval's effective latency, never as the sole delivery mechanism. This directly mirrors this project's own existing "Redis/asynq holds only transient queue state; it is not consulted for job status" architectural principle (ARCHITECTURE.md) — a cancel signal is job status, so Postgres must remain authoritative and pollable, with any pub/sub layer being pure latency optimization on top, not the delivery guarantee itself.

**Why it happens:**
Cancellation looks like "just set a flag and check it" in isolation, but this system already has three independent, carefully-designed correctness mechanisms (guarded transitions, reconciler staleness sweep, asynq retry classification) that a new terminal-ish status MUST be threaded through consistently — missing any one of the three reintroduces exactly the kind of race this project has already spent multiple phases (T-03-10, RECON-01, WR-04 precedents visible in the existing code comments) eliminating for the DONE/FAILED transitions, but for a NEW transition path nobody has hardened yet.

**How to avoid:**
- Cancellation MUST be a guarded transition through the same `transition()` helper (`SELECT...FOR UPDATE` + explicit allow-list of valid source statuses: e.g. `canceled` reachable only from `queued`/`active`, never from `done`/`failed`/already-`canceled`) — reuse the exact mechanism, do not hand-roll a parallel status-update path for this one feature.
- Model the in-flight-cancellation signal as a **poll-based, Postgres-sourced** check inside the worker's long-running loop (e.g. `process()` or the engine's `Convert()` call spawns a lightweight periodic check, e.g. every N seconds via a ticker racing against the ffmpeg/whisper/soffice completion, that re-reads `jobs.status` or a dedicated `cancel_requested` boolean and, if set, cancels the `attemptCtx` passed into `runCommand` — which then correctly SIGKILLs the process group via the EXISTING, unmodified hardening contract). This keeps the actual kill mechanism unchanged (Pitfall 3's concern) while adding only the trigger.
- If a push mechanism (Redis pub/sub, or an asynq-native "cancel" task type) is used to shorten the polling latency, it must be treated as pure optimization: the worker's periodic poll-the-row check remains the fallback/ground-truth path, so a missed pub/sub message merely means the cancellation takes up to one poll-interval longer, never that it silently never happens.
- Extend `internal/reconciler/reconciler.go`'s `FindStale` query (or add an explicit new exclusion) so any intermediate "cancellation requested but not yet applied" state is either (a) not modeled as a separate status at all — simplest: keep status as `active` and add a separate boolean/timestamp column the worker polls, so `FindStale`'s existing `status IN ('queued','active')` matching is completely unaffected and requires no change — or (b) if a distinct status IS introduced, explicitly add it to a documented exclusion and a dedicated regression test proving the reconciler will never resurrect it. Given this project's demonstrated preference for minimal-surface-area extensions (D-decisions favoring "extend the existing Converter/Registry contract" over new abstractions), option (a) — a side-column, not a new status enum value — is very likely the lower-risk design and should be the default recommendation unless research surfaces a strong reason otherwise.
- The worker's cancellation-detected code path must return through `asynq.SkipRetry`, mirroring every existing terminal branch in `worker.go` verbatim (`fmt.Errorf("%w: canceled", asynq.SkipRetry)`), and must call `MarkFailed`-equivalent (or a dedicated `MarkCanceled`) BEFORE returning, following the exact "Postgres-first, only enqueue webhook after the terminal status is actually committed" pattern already used by every other terminal branch (`ferr == nil && job.CallbackURL != ""` guard).
- Explicitly decide (and document as an accepted-risk line in the phase's Key Decisions, matching this project's established documentation style) whether a partial S3 output left behind by a mid-upload cancellation gets active cleanup or rides the existing ILM TTL — do not leave this undecided.

**Warning signs:**
- No unit test exercising `cancel` racing against `MarkDone`/`MarkFailed` concurrently (e.g. two goroutines hitting the repo's transition methods for the same job ID simultaneously, asserting exactly one wins and the other gets an "illegal transition" error, not silent data corruption).
- No test proving the reconciler will NOT re-enqueue a canceled/canceling job — this is a direct, cheap regression test to write (feed the reconciler's `jobStore` fake a job in the relevant state and assert `EnqueueXConvert` is never called), and its absence is a concrete, checkable gap.
- No live test that actually cancels a genuinely long-running video conversion (e.g. a multi-minute source) and confirms via `ps`/process inspection that the ffmpeg process is ACTUALLY dead within one poll interval, not just that the Postgres row says `canceled` while ffmpeg silently keeps running in the background consuming CPU — this exact category of gap (status says one thing, the real OS process says another) is precisely what Phase 9's live zombie-reaping proof caught for LibreOffice, and it recurs here for a structurally similar reason.

**Phase to address:**
Cancellation should be its own dedicated phase (not bundled with progress/SSE/listing), given it's the pitfall with the most cross-cutting risk to existing invariants (guarded transitions, reconciler, retry classification). It should explicitly budget a live test that cancels a real long-running video/audio conversion and verifies process death, not just status-row correctness — matching this project's own established "live proof over narrative trust" discipline.

### Pitfall 6: GET /v1/jobs listing — N+1 queries, unbounded results, cross-client leakage, offset drift

**What goes wrong:**
- **N+1 queries**: a naive listing implementation that fetches N job rows and then, per row, separately queries `job_inputs`/`job_outputs`/`job_events` (e.g. to compute progress/ETA per job by re-deriving it from the latest `job_events` row rather than a denormalized `jobs.progress` column) issues 1 + N queries per page load — fine at N=20 in dev, a real latency/load problem once any internal client scripts against the list endpoint at higher page sizes or polling frequency.
- **Unbounded result sets**: no default/max page size lets a client (accidentally or via a buggy retry loop) request `GET /v1/jobs?limit=100000`, causing a single query to materialize an enormous result set and serialize a huge JSON response — this project's existing size-consciousness (`MAX_UPLOAD_BYTES`, `MAX_IMAGE_PIXELS`, `MAX_DOCUMENT_UNCOMPRESSED_BYTES`) establishes a strong precedent that unbounded-by-default is treated as a defect class in this codebase, and listing should inherit a hard server-side max page size (clamped, not just documented) regardless of what the client requests.
- **Leaking other clients' jobs**: the listing query MUST filter `WHERE client_id = $1` at the SQL level (not filter-after-fetch in Go, which risks an accidental bug leaking a page of results before the filter runs, or an inefficient full-table scan) — this is the direct plural analog of the existing single-job ownership check (`job.ClientID != client.ID` → 404) in `handleGetJob`; the listing endpoint needs the equivalent invariant enforced at the query layer, and a missing `WHERE client_id = $1` clause is exactly the kind of one-line regression that a dedicated cross-client test (create jobs as two different API keys, list as one, assert the other's jobs never appear) should catch mechanically rather than relying on code review alone.
- **Offset pagination drift**: `OFFSET n LIMIT m` pagination against a table that is actively being inserted into (new jobs arriving continuously in a live system) causes classic drift — a client paging through results can see the same job twice or skip a job entirely as new rows shift the offset window between page requests. Given this project's jobs table is genuinely high-churn (every conversion request inserts a row), offset-based pagination is a real, not theoretical, risk here.

**Why it happens:**
Listing endpoints are usually the least-scrutinized part of a system because they "just read data," but in a genuinely multi-tenant (even if internal-only) system with a live-inserting table, every one of these mistakes is a natural default that only breaks under realistic (not demo-scale) usage.

**How to avoid:**
- Denormalize whatever's needed for the list view (status, progress%, created_at, engine, format pair) directly onto the `jobs` row (progress is already being added as a column per this milestone's own scope) so `GET /v1/jobs` is a single query with no per-row follow-up fetch — avoid N+1 by construction rather than by later optimization.
- Enforce a hard server-side maximum page size (clamp any client-requested `limit` to e.g. 100, regardless of what's requested) and a sane default (e.g. 20-50) — mirroring this project's existing "closed allowlist, never trust client input as-is" discipline already applied to `opts` validation (Phase 14).
- Filter by `client_id` in the SQL `WHERE` clause as a non-negotiable first predicate, and add a dedicated cross-client integration test for the list endpoint specifically (not just relying on the existing single-job 404 test to imply the list endpoint is also safe — it doesn't, they're different code paths).
- Use keyset/cursor pagination (`WHERE (created_at, id) < ($last_created_at, $last_id) ORDER BY created_at DESC, id DESC LIMIT $n`) rather than `OFFSET`/`LIMIT`, given the live-insert-heavy nature of the jobs table — this also naturally performs better against the existing `created_at`-based index this project already has for the reconciler's `jobs_inflight_idx` (a composite index touching `created_at` may need to be added/reused for the client-scoped list query too — verify during implementation whether a new `(client_id, created_at)` index is needed rather than assuming the existing reconciler-oriented index serves this different query shape).

**Warning signs:**
- A list-endpoint load test showing query time scaling linearly with page size in a way that doesn't match a single-index-scan expectation (a tell of hidden N+1 or an unindexed scan).
- No automated test creating jobs under two distinct API keys and asserting `GET /v1/jobs` under key A never returns any of key B's jobs — this is cheap to write and should exist explicitly for the list endpoint, not be assumed proven by the single-job 404 test.
- Manual QA only ever tested with a small number of total jobs in the table (e.g. a fresh dev DB) — pagination drift specifically requires a live-insert-during-paging test to catch, which won't show up against a static, already-populated dataset.

**Phase to address:**
The phase implementing `GET /v1/jobs`. Verification should include: an EXPLAIN-verified single-query-per-page-load design, a cross-client leak test, an explicit max-page-size clamp test, and (if resources allow) a live-insert-during-pagination test demonstrating keyset pagination doesn't drift where offset-based would have.

## Technical Debt Patterns

Shortcuts that seem reasonable but create long-term problems.

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|-----------------|------------------|
| Writing progress on every ffmpeg `-progress` tick (no throttle) | Simplest possible first implementation, "just works" in single-job dev testing | Postgres write-amplification that only surfaces under real concurrent-job load (Pitfall 1) | Never — throttle from day one, it's cheap to add up front and expensive to retrofit once a write-storm is already live |
| Modeling cancellation as a fire-and-forget Redis pub/sub message only, no Postgres poll fallback | Fast to build, low latency in the happy path | Missed messages (Redis blip, timing race) silently make cancel a no-op — directly contradicts this project's own "Postgres is system of record" principle | Never as the SOLE mechanism; acceptable only as a latency-optimization layered on top of a Postgres-poll fallback |
| Re-deriving progress at read-time from `job_events` rows instead of a denormalized `jobs.progress` column | Avoids a migration/schema change | N+1-prone reads, and complicates the listing endpoint (Pitfall 6) | Never for this milestone — a `jobs.progress`/`jobs.progress_updated_at` column pair is cheap and this project already has precedent for adding narrow, purpose-built columns (e.g. `preset_name`/`preset_version` provenance columns from Phase 18) |
| Offset-based (`OFFSET`/`LIMIT`) pagination for `GET /v1/jobs` as a first cut | Simpler to implement, matches naive REST tutorials | Drift under concurrent inserts (Pitfall 6) once real traffic hits the endpoint | Acceptable ONLY as a very short-lived placeholder behind an explicit "will migrate to keyset before general availability" note — better to just build keyset pagination from the start given the low incremental cost |
| Skipping active S3 cleanup for partial outputs left by mid-upload cancellation | Saves implementation time | Small amount of orphaned storage until the existing 7-day ILM TTL sweeps it | Acceptable IF explicitly documented as an accepted residual risk (matching this project's existing precedent for documented residual risks), never as a silent unexamined gap |

Common mistakes when connecting to external services/subsystems specific to this milestone.

| Integration | Common Mistake | Correct Approach |
|-------------|-----------------|--------------------|
| ffmpeg `-progress` | Assuming field names/units match documentation exactly across ffmpeg versions | Capture real fixture output from the actual pinned `ffmpeg n8.1.2` build in the av-worker container and write parser tests against that captured fixture, not hand-written or training-data-recalled sample output |

| Redis (asynq) as a cancel-signal transport | Treating a published pub/sub message as a delivery guarantee | Treat Redis pub/sub purely as a latency-reducing nudge; Postgres poll remains the ground truth (mirrors existing "Redis/asynq holds only transient queue state" architecture principle) |

| Existing reconciler `FindStale` query | Assuming a new cancellation-related status/column needs no changes to reconciler logic | Explicitly re-audit `FindStale`'s `WHERE status IN (...)` clause against every new status value or flag this milestone introduces — treat it as a required checklist item, not an assumption |

## Performance Traps

Patterns that work at small scale but fail as usage grows.

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|-----------------|
| Unthrottled progress writes | Rising Postgres write latency correlated with number of concurrent video/audio jobs | Dual throttle: time AND delta gates (Pitfall 1) | Breaks once 2+ long-running (video/audio) jobs run concurrently on a KEDA-scaled fleet — this project has ALREADY proven multi-replica concurrent scale-out (Phase 28 load-proof: 4 replicas from 0), so this is not a hypothetical future scale, it is the project's own already-demonstrated present scale |
| SSE fan-out re-querying Postgres per connected client per tick | Query volume scales with (jobs × connected SSE clients per job), not just jobs | Single upstream feed per job, fanned out to N subscribers in-process | Breaks once more than 1-2 clients watch the same job simultaneously (e.g. two internal services both polling/streaming the same conversion for different purposes) |
| Offset-based pagination on a live-insert-heavy `jobs` table | Duplicate/skipped rows across pages during active use | Keyset/cursor pagination | Breaks as soon as ANY new job is created while a client is mid-page-through — not a large-scale problem, a CORRECTNESS problem present even at low volume |
| N+1 queries for per-job progress/status in the list endpoint | List-endpoint latency scales with page size × per-row query cost, not just page size | Denormalize progress onto the `jobs` row | Breaks (becomes noticeably slow) once page sizes exceed roughly 20-50 rows, well within normal internal-client usage |

## Security Mistakes

Domain-specific security issues beyond general web security, specific to this milestone's features.

| Mistake | Risk | Prevention |
|---------|------|------------|
| SSE endpoint mounted outside the existing auth middleware chain | Any caller (internal network access is not the same as authorization) can stream another client's job progress | Mount SSE through the same chi middleware stack as every other `/v1/*` route; add an explicit unauthenticated-SSE-request test expecting 401, mirroring existing API-key auth tests |
| SSE/listing endpoint returning 403 instead of 404 for another client's job | Regresses the project's hard-won "404 not 403" cross-client invariant (Phase 1), leaking existence of another client's job IDs | Reuse the exact `errors.Is(err, jobs.ErrNotFound)` / `job.ClientID != client.ID` → 404 pattern from `handleGetJob` verbatim for both the SSE stream-open check and any per-job cancel/list-detail lookups |
| Cancel endpoint accepting a job ID without ownership re-check | A client could cancel another client's in-flight job by guessing/enumerating job IDs (UUIDs make blind guessing hard, but explicit ownership re-check is still required defense-in-depth, and cheap) | Cancel handler must perform the identical ownership check as `handleGetJob` before attempting any transition |
| Progress webhook payload leaking internal diagnostic detail (e.g. raw ffmpeg stderr fragments used for progress-adjacent error classification) to the external callback | Same class of internal-detail leak this project already guards against for `error_message` (sanitized message only in the client-facing field; raw stderr stays in `job_events.detail` only, per existing `T-03-03` precedent) | Apply the identical sanitization discipline to any new progress-related client-facing fields — never surface raw engine stdout/stderr text in a progress webhook payload or SSE event body |

## UX Pitfalls

Common user experience mistakes in this domain, for internal API consumers (not a browser UI, but the "user" here is a calling service/developer).

| Pitfall | User Impact | Better Approach |
|---------|-------------|--------------------|
| ETA that swings wildly between polls | Calling service can't build any reasonable "time remaining" UX on top of a noisy number, may distrust the whole feature | Smooth `speed`-derived ETA (moving average / warm-up window), or prefer the simpler progress-ratio-derived ETA over raw `speed` (Pitfall 2) |
| Indeterminate progress for non-ffmpeg engines silently reported as a numeric 0% (rather than a distinct null/indeterminate state) | Calling service renders a stuck "0%" progress bar for image/document/HTML jobs that actually complete near-instantly, looking broken | Use an explicit `progress: null` / `progress_state: "indeterminate"` field distinct from `0`, matching the project's own stated design intent ("indeterminate-фолбэк для остальных движков") |
| Cancel endpoint returning 200 immediately even though the underlying process takes up to one poll-interval to actually stop | Calling service assumes the resource (CPU, worker slot) is immediately free and may race to submit a new job assuming capacity is available | Document (and consider exposing via status) that `canceled` request-acceptance and actual process termination are distinct events; client-facing status should transition through an honest intermediate state if one exists, or the poll-interval bound should be tight enough that this is a non-issue in practice |
| List endpoint silently truncating results with no indication more pages exist | Calling service thinks it saw all jobs when it only saw a truncated page 1 | Standard cursor-in-response convention (e.g. `next_cursor` field, present/absent signals more/no-more pages) rather than a bare array with no continuation signal |

## "Looks Done But Isn't" Checklist

Things that appear complete but are missing critical pieces, specific to this milestone.

- [ ] **Progress throttling:** Often missing the DELTA gate even when the TIME gate is present — verify with a test injecting many same-value ticks within the time window and confirming zero extra writes, not just confirming time-gating alone.
- [ ] **Progress-pipe cancellation safety:** Often "tested" only with `go test -race` (which cannot catch goroutine leaks or deadlocks) — verify with an explicit live SIGKILL-mid-stream test asserting both zero orphaned OS processes AND zero leaked goroutines (via `runtime.NumGoroutine()` delta across repeated cancel cycles).
- [ ] **SSE auth/ownership:** Often verified only for the happy path (valid client, own job) — verify explicitly with (a) no API key → 401, (b) another client's job ID → 404 (never 403), (c) client disconnects mid-stream → handler goroutine actually exits within a bounded time.
- [ ] **Cancellation reaching the OS process:** Often verified only via "the Postgres row now says `canceled`" — verify with an actual `ps`/process-table check that the real ffmpeg/whisper-cli/soffice process is dead, not just that the database claims it should be.
- [ ] **Reconciler awareness of cancellation:** Often assumed safe by inference ("canceled is terminal, so FindStale's `status IN ('queued','active')` naturally excludes it") without an explicit test for the TRANSIENT window between cancel-requested and cancel-applied, which is the actual risk window, not the final terminal state.
- [ ] **List endpoint cross-client isolation:** Often verified only by manual single-client testing — verify explicitly with two distinct API keys and assert zero leakage in either direction.
- [ ] **ETA computation on unknown-duration input:** Often only tested against inputs where ffprobe successfully reports a duration — verify the indeterminate/fallback path explicitly with a fixture that has no reliable duration (or reuses the existing duration-guard's own rejection path, in which case verify the job is already terminal-failed before progress reporting would even apply).

## Recovery Strategies

When pitfalls occur despite prevention, how to recover.

| Pitfall | Recovery Cost | Recovery Steps |
|---------|-----------------|-------------------|
| Progress-write storm discovered in production | LOW | Add/tighten the throttle thresholds (time + delta); this is a config/logic-only fix, no data corruption, no migration needed |
| Progress-pipe goroutine leak discovered in production | MEDIUM | Requires a worker restart to reclaim leaked goroutines immediately, plus a code fix and redeploy; no data-layer damage since progress is a display-only value, but worker memory/goroutine pressure needs active mitigation until redeployed |
| SSE proxy-buffering discovered live (events batch/delay through the real network path) | LOW-MEDIUM | Configuration-only fix (proxy/ingress annotation) if the SSE handler itself is already correct; no code redeploy needed if only the ingress config was wrong |
| Cancellation not actually reaching the OS process | HIGH | Requires both a worker-side code fix (add the missing poll-and-cancel-context wiring) AND, for any jobs currently stuck in a false "canceled" state while still running, a manual/scripted sweep to reconcile Postgres status against actual process state — this is exactly the class of bug this project's reconciler pattern already handles well for OTHER staleness cases, so extending the reconciler to also detect "canceled but never actually stopped" (e.g. active-past-threshold jobs whose status transitioned to canceled but which never got a `finished_at`) is the natural long-term recovery mechanism |
| Reconciler resurrecting a canceled job | HIGH | Data-layer damage possible (a canceled job silently re-runs, potentially double-billing worker capacity or, worse, re-delivering a webhook for a job the client thought was stopped) — requires an emergency reconciler patch (add the exclusion) plus an audit of `job_events` to identify and manually correct any jobs that were wrongly resurrected |
| Cross-client leak in listing endpoint | HIGH (security incident) | Immediate hotfix + audit of API logs to determine whether the leak was exploited/observed by any client, following whatever this project's existing incident-response norm is for security-relevant defects (treat with the same severity as the historical SSRF webhook-redirect bug caught in Phase 2's code review) |
