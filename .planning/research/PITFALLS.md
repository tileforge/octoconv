**Researched:** 2026-10-02
**Confidence:** MEDIUM overall. ## Critical Pitfalls

### Pitfall 1: Reusing the text-shaped sniff envelope rejects real Cyrillic CAD files

**What goes wrong:** `ValidateSniffPrefix` (markupsniff.go) fails closed on a NUL byte or invalid UTF-8. A copied CAD sniffer inherits that. STEP headers and entity names written by Russian CAD (KOMPAS-3D, T-FLEX, older SolidWorks on a Russian Windows) are frequently cp1251 or raw UTF-8 in violation of Part 21 (which wants `\X2\` escapes); DXF R12-R2004 files carry `$DWGCODEPAGE ANSI_1251` and legacy 8-bit text, and only R2007+ (`AC1021`) is UTF-8. The result is false 422s on the exact files this company produces.
**Why it happens:** The envelope is the proven precedent for md/rst/org/latex, and "fail closed" is read as "reject anything that is not clean UTF-8".
**How to avoid:** Write CAD sniffers with their own envelope: reject NUL in the structural window only, tolerate high-bit bytes, judge structure from ASCII tokens. Never decode names for validation. Test with cp1251 and UTF-8 fixtures for STEP header, DXF text and IGES start section.
**Warning signs:** a "valid" CAD fixture generated by FreeCAD/ASCII-only passes while the first real customer file 422s; sniffers import `ValidateSniffPrefix`.
**Phase:** P2.

### Pitfall 2: STEP magic proves nothing about completeness, and truncated STEP imports "successfully" with partial geometry

**What goes wrong:** `ISO-10303-21;` at the start is a strong signature but says nothing about the rest. A truncated upload (or a file cut by a size limit elsewhere) is read by OCCT with warnings and yields a partial shape, so volume and bbox are silently wrong and the price estimate downstream is wrong. Over-strict variants reject real files: leading BOM, CRLF, blank lines, comments before `HEADER;`, lowercase keywords from sloppy writers, STEP-XML (`<?xml ... iso_10303`) and gzip `.stpZ` which are different formats entirely.
**Why it happens:** Only the first bytes are checked, as for every other magic-byte sniffer here.
**How to avoid:** Accept an optional BOM and ASCII whitespace, then require the token sequence `ISO-10303-21;`, `HEADER;`, and `FILE_SCHEMA` inside the window. Read the TAIL as well (last few KiB) and require `END-ISO-10303-21;`, tolerating trailing whitespace only. Tokenize, do not byte-search: STEP strings use `''` escapes and `/* */` comments, and this repo has paid three times for "a byte test standing in for tokenization" (v1.14 `\fi`, `%`, deny-list rounds). Give STEP-XML, `.stpZ`, and `ISO-10303-21` followed by garbage distinct 422 codes rather than one blanket reject. In the worker, treat "roots transferred != roots expected" or an empty shape as terminal, not as success.
**Warning signs:** a STEP that renders but has fewer parts than the source; bbox differs from the customer's own CAD; no tail test in the sniffer suite.
**Phase:** P2 (sniffer, tail read), P3 (worker-side transfer-count check).

### Pitfall 3: IGES detection by column 73 has three real-world forms and a cheap integrity check nobody uses

**What goes wrong:** IGES is 80-column fixed records with the section letter in column 73 (S, G, D, P, T) and a right-justified sequence number in 74-80. Failure modes: only checking the first record (any 80-column text with `S` in column 73 passes); requiring newlines (legacy IGES is a bare stream of 80-char records with NO line breaks, and some tools strip trailing spaces which destroys column 73); rejecting CRLF; confusing the rare compressed/binary flag records (`C`/`B` in column 73 of the first record) with ASCII IGES.
**Why it happens:** Treated as "a text format with a magic", which it does not have.
**How to avoid:** Validate structure, not a magic: the first record has `S` in column 73 and sequence 1; walk the first N records (bounded) and require every column-73 letter to be in {S,G,D,P,T} in non-decreasing section order with consecutive sequence numbers; accept both LF/CRLF-delimited and exact-80-multiple unbroken streams; reject flag `C`/`B` with a specific code. Cross-check the Terminate (`T`) record, which carries the counts of S/G/D/P records, against what the scan saw: that single check also detects truncation. Do not require specific delimiters in the Global section (they are redefinable).
**Warning signs:** IGES fixture only from one exporter; no test with a file lacking newlines; no test with a truncated T record.
**Phase:** P2.

### Pitfall 4: STL "starts with `solid`" decides nothing, and the validator can disagree with the engine's own reader

**What goes wrong:** ASCII STL starts with `solid`, but so do some BINARY STLs (their 80-byte header begins with it, a known exporter habit), and so does any English text beginning "solid ...". Picking ASCII on the prefix misclassifies binary files; picking binary on size misclassifies large ASCII. Worse, a polyglot that satisfies both interpretations can make the validator and FreeCAD/OCCT's reader (which has its own ASCII-vs-binary heuristic) choose differently, so the file the validator vetted is not the file the engine parses.
**Why it happens:** "Predict the parser" instead of testing against it (see MEMORY: dont-predict-a-parser-test-against-it, four bypasses of one bound).
**How to avoid:** Decide binary FIRST by an exact arithmetic test: `size == 84 + 50*n` where `n` is the little-endian uint32 at offset 80 (ASCII STL almost never satisfies this). Otherwise call it ASCII only if `solid` is followed by whitespace AND `facet normal`/`endsolid` appears in the window and the window is text. When BOTH hold, fail closed as ambiguous. Reject `n == 0`. Bound `n` against a triangle ceiling before any engine sees it (ASCII costs about 5x the bytes per triangle, so the bound must be on triangles, not bytes). Build a differential test: run the validator's verdict and the actual FreeCAD reader over a corpus of tricky files (binary with `solid` header, ASCII with CR-only endings, trailing newline on binary, `n` lying in both directions) and diff them, with a divergence table, rather than reasoning about it. Decide deliberately whether to tolerate a small trailing slack on binary files (some exporters append bytes); exact equality is the safe default, relax only with a measured reason.
**Warning signs:** validator and `Mesh.Mesh(path)` disagree on any corpus file; a binary STL named "solid_..." 422s; no ambiguity code exists.
**Phase:** P2 (verdict, differential test); P3 (differential needs the real reader).

### Pitfall 5: DXF structure is group-code pairs, with binary and DWG as look-alikes that must get their own refusals

**What goes wrong:** ASCII DXF is `code\nvalue\n` pairs. A sniffer demanding `0\nSECTION` as bytes 0..N fails on leading `999` comment pairs, padded codes (`  0`), CRLF, and R12-style files with no HEADER section. Binary DXF starts with the 22-byte sentinel `AutoCAD Binary DXF\r\n\x1A\0` and contains NULs, so a text sniffer calls it garbage; FreeCAD's importer cannot be assumed to read it. DWG starts `AC10xx` and is explicitly out of scope until the ODA licensing decision, but a client WILL upload it as `.dxf`.
**How to avoid:** Parse pairs on lines, bounded to the first few dozen pairs, accepting `999` comments, whitespace padding and both line endings; require a `0`/`SECTION` pair then `2`/`HEADER|ENTITIES|TABLES|CLASSES|BLOCKS`. Read the tail for `0`/`EOF` (truncation). Detect the binary sentinel and `AC10`/`AC1` DWG signature BEFORE the text path and return specific, closed 422 codes (precedent: OLE-CFB legacy/encrypted split, v1.5 Phase 22). Make the DWG code mention the licensing scope so it is not mistaken for a bug.
**Warning signs:** a "DXF" upload that is really DWG produces a generic 422 or, worse, a worker failure; no binary-DXF fixture.
**Phase:** P2.

### Pitfall 6: Format detection order and `inspect` parity: a CAD text format claimed as `text`, or two endpoints calling one file two formats

**What goes wrong:** ASCII STL, DXF and STEP are plain text. The pandoc family relies on `LooksLikeText` with no magic. If a CAD sniffer sits after the generic text matcher, `.stl` bytes are routed to the markup class; if before, a README beginning with "solid" is claimed as STL. `/v1/inspect` and `POST /v1/jobs` must call a file the same thing (PROJECT.md: detectInspectFormat's own doc comment names this invariant). Aliases (`stp`, `igs`) need `NormalizeFormat` entries; `Register` panics on collisions and `pairs_disjoint_test` will fire for any pair that overlaps (note `svg` as an OUTPUT of dxf must not shadow libvips' svg input handling).
**How to avoid:** Put the CAD sniffers into the single shared detection order with a stated precedence (most-specific first: STEP, IGES, binary STL, DXF binary/ASCII, ASCII STL, then generic text), covered by a table test that runs the same bytes through both endpoints. Add the aliases and pair rows in the same change as the sniffers.
**Warning signs:** `/v1/inspect` and job creation disagree; the markup class accepts an `.stl`.
**Phase:** P2.

### Pitfall 7: Magic bytes prove the container, not that the engine will not hang, blow up, or recurse

**What goes wrong:** A 1 MB STEP can reference itself (`#1=...#1`), declare a deeply nested assembly, or instantiate parts so many times that iterating the compound is astronomical. OCCT/FreeCAD then hang (no timeout reached until the 300s+ class timeout), recurse to a stack-overflow SIGSEGV, or allocate until OOM-kill. A valid DXF can `MINSERT` a block 32767 x 32767 times or have cyclic block references. A binary STL header can declare 4 billion triangles.
**Why it happens:** The ceiling is on input BYTES, but cost is superlinear in structure (the tex lesson, v1.14: "an input ceiling implies nothing about the output").
**How to avoid:** Add a worker-side guard stage before the engine (precedents: `ocrPDFGuardStage`, `enforceAudioGuardBeforeConvert`; cheap checks that need no S3 write belong in the API sniffer, O(n) scans in the guard stage and produce a terminal coded failure, not a 422). Guards: STEP entity count and count of assembly-occurrence entities (`NEXT_ASSEMBLY_USAGE_OCCURRENCE`, tokenized, not grepped) against a ceiling; DXF entity count, `MINSERT` row x column product, and block-reference depth; STL triangle count; all of it derived from a measured corpus, not guessed. After import, check bbox is finite and below a sanity extent BEFORE meshing. Each bound is a closed code in the error vocabulary.
**Warning signs:** a hand-written "billion laughs" STEP/DXF is not in the test suite; the only bomb test is an oversize file.
**Phase:** P2 (cheap bounds), P3 (post-import checks), P7 (bounds derived from measurement).

### Pitfall 8: Xvfb under Landlock and the shared `/tmp`: stale locks, sockets, xkbcomp, abstract sockets, orphans

**What goes wrong:** The only measured working render path is `f3d` under `xvfb-run` (notes, 2026-09-23). That is a second process, plus `/tmp/.X<N>-lock`, `/tmp/.X11-unix`, xkbcomp invoked via a shell (needs `/bin/sh`, `/usr/bin/xkbcomp`, `/usr/share/X11/xkb`, and writes compiled keymaps to its output dir, falling back to `/tmp`), and a network listener unless `-nolisten tcp`. As non-root Xvfb prints `euid != 0, directory /tmp/.X11-unix will not be created` followed by xkb failures; workarounds are `-nolisten unix`, `XKB_OUTPUT_DIR`, `HOME=/tmp` (MEDIUM, AWS re:Post / xorg list). Consequences here: (a) `/tmp` goes into the read-write set, which forces concurrency EXACTLY 1 plus the sweep (sharedTmpGuard, CONF-06) and loses the "nothing shared" posture that pandoc/probe have; (b) a SIGKILLed job leaves `/tmp/.X99-lock`, so the NEXT job on a fixed display number dies "Server is already active", and with `-a` auto-pick leaks locks; (c) `sock:` is a special grant that exists only because of soffice; Xvfb connections use an abstract socket that pre-ABI-6 Landlock does not mediate at all, so confinement does not cover who can talk to the X server; (d) the process-group kill (see Pitfall 12) is what keeps Xvfb from outliving the job.
**How to avoid:** Make the P1 decision on a measurement of "no X" first (see Pitfall 9) and treat Xvfb as the fallback that costs the class its `/tmp` posture, not as the default because it is what already worked. If Xvfb wins: `-displayfd` plus `-nolisten tcp -nolisten unix`, per-job `XKB_OUTPUT_DIR`/`TMPDIR` inside the job dir where measurement allows it, extend the sweep to `.X*-lock`/`.X11-unix`, run it from the Python wrapper (not `xvfb-run`, whose shell trap is the thing SIGKILL skips), tini as PID 1 (document-worker precedent, v1.2), concurrency exactly 1 enforced by the existing guard.
**Warning signs:** second job on a reused container fails with "already active"; `/tmp` in the cad grant set; `xvfb-run` in the argv; any `/tmp/.X*` after a timeout test.
**Phase:** P1 (decision), P3 (grant set), P6 (container/tini/concurrency), P7 (timeout-kill test must assert zero survivors and zero residue).

### Pitfall 9: "Offscreen EGL/OSMesa" is not a flag, it is a build of VTK plus env vars the scrubbed environment will drop

**What goes wrong:** f3d documents `--rendering-backend auto|egl|osmesa|glx|wgl` and says to use `egl` or `osmesa` on Linux for headless (HIGH, f3d.app options). But the Debian bookworm `f3d` is 1.3.1 built against Debian's `libvtk9.1`/`libglew2.2`/`libopengl0` (HIGH, packages.debian.org): the measured segfault without X is consistent with a GLX-only build, and the flag only helps if VTK itself was built with the EGL/OSMesa render window. Newer f3d is not in bookworm. Whether an upstream binary exists for BOTH amd64 and arm64 is not verified (LOW); if only amd64, the arm64 dev image and the prod image render with different binaries. Even when it works: EGL needs a platform hint (`EGL_PLATFORM=surfaceless` or a device), Mesa llvmpipe sizes its thread pool from the HOST core count (same trap as the JVM seeing the host under cgroup limits, v1.15 V0: 11 vs 2 CPUs) so `LP_NUM_THREADS` must be set, it JIT-compiles with LLVM (large libs) and writes a shader cache under `$HOME`, reads `/usr/share/drirc.d`, `/etc/glvnd`, `/usr/share/glvnd/egl_vendor.d`, and probes `/sys/class/drm`. `engineEnv` keeps ONLY PATH/HOME/LANG/LC_ALL/TMPDIR, so none of these variables arrive unless the class adds them (tectonicEnv is the precedent for per-class extras; extend `withEnv` for cad, do not widen `engineEnv`, so seven proven classes stay byte-identical).
**How to avoid:** P1 evaluates FOUR candidates by measurement on the real image under Landlock, judged by CONTENT (non-background pixel fraction, silhouette bbox, three views differing), not exit code: (1) f3d EGL/OSMesa from an upstream build, (2) FreeCAD/Coin offscreen, (3) Xvfb + f3d, (4) no GL at all: a small deterministic software rasterizer over the STL the pipeline already produces (Go or Python/numpy). Candidate 4 removes Mesa, LLVM, Xvfb, the env-var surface, and pixel nondeterminism across CPUs, at the cost of lower visual quality; it deserves a measured look rather than being skipped because GL "is standard". Record the renderer version in every gate transcript (chromium 153 to 154 silently defeated a negative control, v1.15).
**Warning signs:** the renderer works in `docker run` as root and fails in the confined worker; render time scales with host core count; first render per job is seconds slower (JIT and cold shader cache); a candidate "works" because it fell back to another mechanism.
**Phase:** P1.

### Pitfall 10: The grant set is under-measured because Python and FreeCAD load code lazily and per format

**What goes wrong:** Phase 68 already taught this twice (pdfinfo/pdftotext missing from the OCR set; fonts changing output with rc 0). FreeCAD/Python is worse: (a) FreeCAD runs the `Init.py` of every installed Mod at startup, so the read set is wide and includes Python packages; (b) DXF, IGES and STEP take different code paths and load different shared objects and Python modules lazily, so a STEP-only trace misses the DXF/IGES set; (c) OCCT reads resource files (`CSF_*` message and IGES/STEP resource dirs under `/usr/share/opencascade*`), absent ones print a warning for STEP but can fail IGES; (d) the interpreter, `FreeCADCmd` (a symlink), `f3d`, and the wrapper script itself are EXECUTED, and execve targets do not appear in an `openat` trace (SANDBOX-PATHS trap 1); a script with a `#!` adds the interpreter (trap 2); (e) `~/.config/FreeCAD`, `~/.local/share/FreeCAD`, `FreeCAD_Doc*` transient dirs under `/tmp`, `matplotlib` font cache, `__pycache__` writes: all attempt writes that Landlock denies, sometimes silently, sometimes as a startup exception; (f) trace under root versus nobody gives different `$HOME` paths (trap 3); (g) a denied import is a worker defect, and the error text looks like a bad file.
**How to avoid:** Run `scripts/sandbox-paths-measure.sh` over the FULL matrix of (format x operation) argv the code can issue, under the image user, `-ff`, symlink targets printed (trap 7), then prove sufficiency by sha256/content versus unconfined, necessity by one-at-a-time removal, effectiveness by an outside-file read that must fail. Prefer `python3 -I -B` with an explicit `sys.path` insert over `FreeCADCmd` (no user-cfg setup, no env dependence, no `__pycache__` writes); import only `Part`, `Mesh`, `MeshPart`, `Import` (never `Draft`, `TechDraw`, `FreeCADGui`, `PySide`, `matplotlib`); avoid `FreeCAD.newDocument()` where `Part.read`/`Mesh` suffice (it creates a transient dir); point `HOME` and `TMPDIR` into the job dir via `withEnv`. Classify "ImportError/PermissionError inside the wrapper" as an ENGINE/node fault (retry, alert), never as the client's file failing (v1.14 lesson: a stalled MinIO call was reported as a document that failed to typeset).
**Warning signs:** the preflight (STEP box) passes and the first DXF or IGES job dies with `ImportError`; the grant list contains `/usr/lib` wholesale to make Python work; trace taken as root.
**Phase:** P3 (measurement and wrapper), P6 (preflight per format, Pitfall 25).

### Pitfall 11: Exit codes and stdout lie, so judge by a coded result file and by content

**What goes wrong:** `FreeCADCmd script.py` is commonly reported to exit 0 after a Python exception inside the script (MEDIUM, community; verify on 0.20.2). Conversely, FreeCAD plus Qt/PySide modules are commonly reported to segfault at interpreter shutdown AFTER outputs were written, so rc 139 with a complete (or half-flushed) STL. OCCT's STEP/IGES readers print progress and diagnostics to stdout, corrupting any JSON parsed from it. FreeCAD error text changes between versions, so substring terminal-classifiers silently stop matching on an upgrade. Go's error here is `"%s failed: %w: %s"` over `ExitError`, so a crash arrives as the text `signal: segmentation fault`, a kill as `signal: killed`, indistinguishable from a cgroup OOM-kill unless the context says timeout.
**How to avoid:** One wrapper (`python3 -I -B wrapper.py`) that: never prints results to stdout; writes `result.json` (closed `status` and `code` vocabulary, schema-versioned) to the job dir; writes outputs to temp names, `fsync`s and renames; ends with `os._exit(0)` to dodge destructor crashes; maps every exception class to a code. The Go side judges by `result.json` plus output validation (PNG decode, STL arithmetic, JSON parse with `allow_nan=False`), never by rc alone (ghostscript lesson, SANDBOX-PATHS trap 8). Classification: wrapper code `invalid_input`/`too_complex`/`empty_geometry` terminal; `signal: segmentation fault` and `aborted` terminal for that input (deterministic; otherwise three retries x full timeout); `signal: killed` without ctx cancellation is OOM-ambiguous: follow the pandoc precedent (bound input by measured RSS per MiB, concurrency 1) rather than guessing; timeout terminal (document/pandoc/tex precedent) because the same file will time out again. New error strings ship in the SAME commit as their terminal-signature entry (D-04 discipline, v1.3).
**Warning signs:** `produced no output` appears for crashes; JSON parse errors mixed with OCCT banner text; a retry storm on a deterministic crasher.
**Phase:** P3 (wrapper/result contract), P6 (isCADTerminal), P7 (crasher corpus in the live gate).

### Pitfall 12: The process-group kill only fires on timeout, and Go's `Wait` can hang on a grandchild holding the pipe

**What goes wrong:** `runCommandCore` kills `-pgid` only on `ctx.Done()`. If the lead process exits (normally or by crash) while a helper (Xvfb, f3d, a TBB thread host, `xkbcomp`) is alive in the group, nothing kills it. And because `cmd.Stdout`/`Stderr` are `tailBuffer` writers (not `*os.File`), `cmd.Wait()` also waits for the copy goroutines, which finish only when EVERY holder of the pipe's write end closes it: an orphaned helper that inherited stderr stalls `Wait` until the ctx deadline, so a 4-second render becomes a full-timeout job (and then terminal). No `WaitDelay` is set. In the document class this exact family of problem needed tini as PID 1.
**How to avoid:** Keep helpers inside ONE supervised wrapper: the wrapper starts them, `finally:` kills their group, and `result.json` is the completion signal; give helpers `stdout/stderr` redirected to files in the job dir, not the inherited pipe. Do not change shared `exec.go` for this (v1.9 kept it byte-for-byte; every class shares it): handle in the cad wrapper, and prove with a live test that kills the job mid-render and asserts zero surviving processes AND zero residue AND `Wait` returning promptly (the 40/40 SIGKILL-mid-stream style of proof from v1.9). tini as PID 1 in the cad image.
**Warning signs:** jobs that succeed but take exactly the timeout; `ps` in the container showing `Xvfb`/`f3d` after a job; zombie count growing.
**Phase:** P3 (wrapper), P6 (tini), P7 (kill test).

### Pitfall 13: Memory and complexity: tessellation and the STEP RAM multiplier will OOM a 1 GiB worker; the answer is a measured bound, not a bigger limit

**What goes wrong:** OCCT keeps a heavy object graph (RAM many times the STEP text size), and tessellation with a small deflection on a detailed or large model yields millions of triangles and a multi-hundred-MB STL (and a multi-hundred-MB PNG-render input). The pandoc milestone is the template: a 4 MiB html->md OOMKilled a 1 GiB worker, measured ~300 MiB RSS per MiB of input, and "lightweight" turned out memory-bound. Fixed deflection (`0.1`) is also scale-blind: 0.1 mm on a 10 m model is fine, on a 2 mm part it is coarse, on a 1e5 mm model it explodes.
**How to avoid:** Measure RSS-per-MiB on a realistic STEP corpus under the deployment limits (not a 20x10x5 box; the OCR toy fixture read 0.148 s/page against a real 5.81), derive `CAD_MAX_INPUT_BYTES` and concurrency from it (expect 1, scale by KEDA). Choose deflection RELATIVE to the bbox diagonal with a floor, cap the triangle count after meshing and BEFORE writing (terminal `too_complex`), and cap what is STORED from the engine (v1.14: bound what comes back, not only what goes in). Include the converter's own working set (STL file plus render) in the bound.
**Warning signs:** `OOMKilled` only on large real files; `signal: killed` with no ctx error; STL outputs larger than the input STEP by 50x.
**Phase:** P3 (relative deflection, caps), P7 (RSS-per-MiB measurement, bounds).

### Pitfall 14: Volume is only meaningful for closed solids, and "volume: 0" or a plausible wrong number is worse than "unknown"

**What goes wrong:** `Shape.Volume` on non-solids is version- and type-dependent (MEDIUM): faces give 0, an open shell can give a signed nonsense integral, a reversed solid gives a NEGATIVE volume, compounds sum their solids. Real inputs: IGES is mostly surfaces (no solids at all), STEP may contain surface bodies, construction geometry, or sheet bodies; a multi-body part sums fine, but overlapping bodies double-count; assemblies instance one part many times so volume is per instance, and a STEP flagged "assembly of 100 identical screws" is a legitimate 100x. Sewing shells into solids (`BRepBuilderAPI_Sewing`) is tolerance-dependent, can be slow or hang, and fabricates a volume. This number feeds a price estimate (the notes: the old service's `part_volume` is "a calculation for pricing").
**How to avoid:** Define the JSON contract as a closed vocabulary, same style as inspect findings: compute volume ONLY from `Shape.Solids`, take `abs` after an explicit orientation check, report `solid_count`, `shell_only_count`, `volume_status` in {`solid`, `not_a_solid`, `partial`, `none`} and `volume: null` when there is no closed solid; never sew silently (an opt-in later, with its own status). Add a test that a box built as an open shell reports `null` not 1000 and not 0. Do not claim equality with the Fusion-based numbers; state "OCCT exact B-rep volume of closed solids".
**Warning signs:** `volume: 0` on an IGES that renders; negative volumes in logs; a shell-built box reporting a volume.
**Phase:** P4.

### Pitfall 15: Units: OCCT converts STEP/IGES to millimetres, STL has none, DXF `$INSUNITS` defaults to unitless, and "honest by source" needs a vocabulary

**What goes wrong:** OCCT's STEP/IGES readers convert to a target unit that defaults to MM (MEDIUM, OCCT forums), so a part authored in inches arrives 25.4x numerically larger and the JSON says "mm": correct, but the SOURCE unit is lost, and the requirement says units are reported honestly by source. Volume units are cubed (mm^3, not cm^3). STL carries no unit at all (mm by convention only). DXF `$INSUNITS` 0 means unitless, absent means unitless, and `$MEASUREMENT` is independent (HIGH, ezdxf docs); how FreeCAD's importer scales depends on version and preferences. STEP assemblies can carry several unit contexts and the global OCCT scale is known to mis-scale parts in multi-context files (LOW).
**How to avoid:** JSON carries `unit` (`mm`, `unitless`) and `unit_origin` in a closed set (`converted_from_declared` with `source_unit`, `assumed_mm_by_convention`, `unitless`), plus a separate `volume_unit` (`mm3`/`unitless`). Read the declared STEP/IGES unit from the file text for the origin field (STEP unit entities; IGES Global parameter 14/15). Fixture: the same part authored in mm and in inches must give the SAME mm bbox and an `unit_origin` that differs. Never default DXF/STL to `mm` silently.
**Warning signs:** a unit field that is a constant; inch fixture and mm fixture indistinguishable in output; consumers dividing by 25.4 twice.
**Phase:** P4.

### Pitfall 16: Bounding box depends on whether the shape was tessellated first, includes construction geometry, and can be NaN

**What goes wrong:** OCCT's default bounding box can use triangulation if present and control polygons if not, so `BoundBox` on NURBS can be loose and can CHANGE depending on whether you meshed before asking (order dependence, MEDIUM; the tight variant is `BRepBndLib::AddOptimal`; verify `optimalBoundingBox` exists in 0.20.2 or derive bbox from the exported mesh). Surface bodies, datum planes and sketches in the STEP inflate it. Gigantic or non-finite coordinates give `inf`/`nan`, and Python's `json.dumps` happily writes `NaN`/`Infinity`, which is not JSON and breaks every consumer.
**How to avoid:** One defined source for bbox (optimal bbox of the solids, or the mesh bbox), computed in a fixed order, documented in the contract; `json.dumps(..., allow_nan=False)`; refuse non-finite or beyond a sanity extent with a coded terminal failure before meshing (also Pitfall 7); report which geometry classes were included. Test: bbox identical with and without a prior mesh call; test a `1e300` coordinate.
**Warning signs:** bbox differs between runs of the same file after reordering steps; consumer JSON parse errors.
**Phase:** P4.

### Pitfall 17: Render correctness: degenerate bbox, view-up singularity, up-axis convention, blank-but-valid images

**What goes wrong:** Cameras are positioned from the bbox (the notes use explicit `--camera-position/--camera-focal-point`). A flat part (zero thickness), a line, or a single triangle gives a zero-radius sphere, and the camera sits ON the focal point (NaN matrices, blank image or crash). Top/bottom views have view direction parallel to the default up vector (VTK/f3d warn and produce an arbitrary rotation). CAD is Z-up but meshes from other tools are Y-up, so "front" is "top". A 2D DXF pushed through the 3D mesh path is a zero-thickness plane seen edge-on. Dark-on-dark or white-on-white colours (DXF colour 7) give a valid PNG that looks empty, exactly the ghostscript trap where the file was the right size and had no content. Absolute camera distances break on 1e-3 mm or 1e6 mm models (clipping range).
**How to avoid:** Normalize the MESH, not the camera: translate to origin and scale to a unit bounding sphere (floored at an epsilon) in the wrapper, then use fixed constants for every view in a closed vocabulary (front, back, left, right, top, bottom, iso) with an explicit `view-up` per view that is never collinear with the direction. Fix and document the up axis. Route 2D DXF to a 2D renderer, never to the 3D one. Judge output by content: non-background pixel fraction above a floor, silhouette bbox inside the frame, the three views of an asymmetric fixture pairwise different; never by "file exists and is non-empty". Compare against goldens structurally (pixel-fraction, silhouette, perceptual tolerance), not sha256 (Pitfall 18).
**Warning signs:** blank PNG with rc 0; flat-part and top-view tests absent; goldens compared by hash.
**Phase:** P4 (view vocabulary, normalization, content checks), P7 (live content gate).

### Pitfall 18: Nondeterminism and architecture differences make hash goldens and "same input, same output" claims false

**What goes wrong:** Parallel meshing (OCCT thread pool/TBB) can reorder or perturb triangulation; floating point differs between arm64 (FMA contraction) and amd64 in the last digits of volumes, bbox and vertices; Mesa llvmpipe renders differ across CPU features and LLVM versions; Qt/OCCT can read a non-C `LC_NUMERIC`; Python hash seeds affect set iteration order in a wrapper. The dev machine is arm64, production is probably amd64 (Debian ships native freecad for both, so there is no pin as with veraPDF, but there are two numeric stacks).
**How to avoid:** Pin `LC_ALL=C.UTF-8`; run the wrapper with `-I` (ignores `PYTHONHASHSEED`/`PYTHON*`) and sort anything iterated; set the mesher single-threaded or cap threads by affinity (`os.sched_setaffinity` from the cgroup `cpu.max`, reusing `internal/convert/cgroup.go`'s logic) because OCCT/TBB read the host core count, not the cgroup quota; round reported numbers to a fixed significant-digit count; compare numbers with a relative tolerance and images structurally; keep ONE differential check: native amd64 versus native arm64 over the corpus with a written divergence table (the v1.15 `DIVERGENCES: 0` pattern, but with tolerances). Two runs on one arch must be byte-identical for the JSON and STL or the contract says why not.
**Warning signs:** goldens flaky across machines or CI; STL hash differs between two consecutive runs.
**Phase:** P3 (determinism settings), P7 (two-run and cross-arch checks).

### Pitfall 19: DXF to SVG/PDF is probably NOT a FreeCAD-headless capability, and it is the highest feasibility risk in the milestone

**What goes wrong:** Evidence (MEDIUM, FreeCAD tracker and wiki, older versions): `importDXF` historically assumes the GUI (`FreeCADGui.draftToolBar` NameError without it); the C++ importer cannot read 3D solids stored as ACIS/SAT blobs (they vanish and the result is empty); the exporter drops text and dimensions and ignores colours; SVG export lives in Draft (Python), and PDF output goes through TechDraw/GUI. So "dxf -> pdf" likely needs a second tool (e.g. `ezdxf` drawing add-on, or SVG then an SVG-to-PDF converter), each adding its own binary, grant set, `engineExec` path and image weight; if it hangs on FreeCAD alone the milestone feature silently becomes "not possible". Rendering pitfalls follow: DXF Y-up versus SVG Y-down (mirrored drawing), model space versus paper space, layer colours (ACI 7), `$INSUNITS` scaling, hatch/dimension/text entity coverage; an entity-count zero result must be an honest terminal `empty_drawing`, not a blank file.
**How to avoid:** Put a DXF spike in P1 or P5-first with the real 0.20.2 package: does `Import.readDXF` run headless, what can produce SVG, what can produce PDF. Decide the second tool by measurement and size, not by default. Treat every generated SVG as untrusted output: escape all text (MTEXT/attribute content with `<`, `&`), forbid `<script>`, `<foreignObject>`, event attributes and external `href`s, validate by an XML parser, and reuse the probe/sanitize approach where the checker is broader than the generator (v1.13's most effective countermeasure). Round-trip test an entity named `&<>"'`.
**Warning signs:** DXF->SVG "works" only on files without text; mirrored output; an SVG containing a `javascript:` or `file:` href; PDF produced by a different tool than the one granted.
**Phase:** P1 (spike), P5.

### Pitfall 20: Image size and cold pull will dominate KEDA scale-from-zero latency, and apt FreeCAD drags in Qt/PySide/matplotlib

**What goes wrong:** Debian bookworm `freecad` is 0.20.2 and its `freecad-python3` depends on `libqt5gui5`, `libqt5widgets5`, `python3-pyside2.*`, `python3-matplotlib`, `python3-pivy` (HIGH, packages.debian.org), plus OCCT, VTK and boost via the lib packages. A headless worker therefore ships a GUI toolkit it never uses; expect the largest image in the fleet (size not measured here; the notes say only "noticeably larger"). `freecad` Recommends `calculix-ccx` and `graphviz`. On a cold node the pull plus pod start plus FreeCAD's multi-second import is the scale-from-zero latency. AVX-02 (registry cold-pull measurement) has been deferred since v1.7; this is the first class where it matters. Also a prior lesson: a collector-driven ScaledObject for a NEW queue sits at `fallback.replicas:1` forever when the API image predates `QueueCAD` in `AllConvertQueues()` (v1.8 stale-image incident).
**How to avoid:** P1 produces numbers: compressed and uncompressed image size, cold-pull time on the target registry, first-job latency from zero. Compare three routes on those numbers: apt FreeCAD with `--no-install-recommends`, a multi-stage headless FreeCAD source build (`BUILD_GUI=OFF`, the tesseract/ffmpeg/whisper precedent, long build but a much smaller runtime), or OCCT bindings plus pure-Python DXF tooling (STACK.md decides; this file's job is to require the budget gate). Then: `imagePullPolicy: IfNotPresent`, `keda.cad.minReplicaCount` (CAPA-01 already exists) as the cold-start lever, grace period at least the measured timeout, and a "rebuild images from HEAD" preflight in the load-proof script.
**Warning signs:** first job after idle takes minutes; HPA shows the pod `ContainerCreating` for the pull; cad queue depth metric stuck at fallback.
**Phase:** P1 (budget), P6 (chart/KEDA), P7 (scale-from-zero proof).

### Pitfall 21: Emulated amd64 gives neither Landlock nor a trustworthy renderer

**What goes wrong:** Landlock is unavailable to an emulated amd64 process on an arm64 host (measured 2026-09-19), so a cad image pinned or built for amd64 on the dev machine makes the worker refuse to start (correct) and makes any measurement on it meaningless. llvmpipe's LLVM JIT and CPU-feature detection under qemu-user commonly crash or run an order of magnitude slower (LOW, from experience, not measured here). Any single stage pinned to amd64 (an upstream f3d binary, a vendor tool) repeats the veraPDF situation.
**How to avoid:** Keep the image native on both arches (Debian provides FreeCAD for both); for any amd64-only binary, first prove it is an ELF at all or not (the v1.15 premise test: "no ELF under /opt/verapdf"), and pin only that stage. Measure the timeout bound on native amd64 at least once (the arm64 RTF caveat is an open advisory since v1.7). Record `uname -m` and the engine versions in every gate transcript.
**Warning signs:** worker "refuses to start" locally only; timings differ 20x between machines.
**Phase:** P1 (renderer arch matrix), P7.

### Pitfall 22: The second output (dimensions JSON) is a new role and a new failure mode: partial outputs, role mix-ups, and a premature contract

**What goes wrong:** A render job now has two outputs. PNG uploaded but JSON failed (or the reverse) leaves a job `done` with half a result unless atomicity is decided. v1.13's live defect was exactly "first uploaded output blindly presigned as the result": `handleGetJob` picks `download_url` by `role`, so a new `dimensions` role must be added to the CLOSED enum and the CHECK constraint (a migration), and must never become the default "result". Accounting sums bytes over all outputs (fine, by design). Webhook, SSE, MCP and `/v1/formats` surfaces must show `(operation, from, to)` triples and roles consistently. SEED-007 (the preview contract) is being "fixed on CAD" from one engine: freezing preview fields (size, format, fallback, failure shape) on a single case invites a contract that the document/video previews cannot meet.
**How to avoid:** Decide and test atomicity: either both outputs recorded in the same transition as `done` or the job fails and neither is exposed; inversion-test it (kill between uploads). Add the role with its migration and a derived-completeness test (`AllEngines()`/role enum cross-check, the pattern that survived the eighth engine). Version the JSON (`schema: 1`). Write the preview contract as the SMALLEST set CAD forces and mark the rest explicitly "not yet fixed"; keep consumer replacement of PreviewGenerator out of scope.
**Warning signs:** `download_url` points at the JSON; a `done` job with one output; contract fields that mention only CAD concepts.
**Phase:** P4.

### Pitfall 23: Opts and the Python wrapper: injection through a code string

**What goes wrong:** The wrapper is Python. Interpolating a view name or size into `python3 -c "..."` or a generated script is code injection; passing an opts-derived value as a FreeCADCmd positional argument can be treated as a file to open or a flag. FreeCADCmd also picks the importer by the file EXTENSION, so a client-supplied name steers the parser.
**How to avoid:** The script is a fixed, baked, read-only file granted by exact path; opts travel as a validated JSON file in the job dir (typed struct, strict parse, closed view enum, size clamped to a ceiling; the AudioOpts/PandocOpts precedent and its injection test); the wrapper never `eval`/`exec`s anything; the input is always named from the DETECTED format (`in.step`, never the client filename), and the argv uses `--`. Cap output size (a 16k x 16k render is a framebuffer/memory bomb on llvmpipe).
**Warning signs:** an f-string building Python; an opts field copied into argv without the closed enum; no injection test.
**Phase:** P2 (opts), P3 (wrapper).

## Moderate Pitfalls

### Pitfall 24: Locale and decimal separator
**What goes wrong:** OCCT and Qt consult `LC_NUMERIC`; a comma-decimal locale misparses STEP/IGES/DXF floats (specs mandate a dot) or writes `1,5` into output. Some Russian-locale exporters actually emit commas in DXF/STEP text, which parse as zeros.
**Prevention:** pin `LC_ALL=C.UTF-8` through `withEnv` (bookworm-slim has no ru_RU locale, so this is mostly about explicitness); write all numbers via `json`/`repr`, never `%s` with locale; test a comma-decimal STEP/DXF fixture and expect a coded failure, not zeros. Warning sign: bbox of all zeros on a non-empty file. **Phase:** P3.

### Pitfall 25: Preflight proves one branch, not the class
**What goes wrong:** The preflight is "a content-judged real-engine run before Postgres" (CONF-04). A STEP box passing says nothing about IGES resource loading, DXF import, the renderer, or the outside-file denial for each binary. FreeCAD cold import adds seconds to every worker start and to scale-from-zero.
**Prevention:** one preflight case per (format x operation) the class advertises (STEP render, IGES to STL, STL render, DXF path), each judged by content (volume equals 1000 within tolerance for the 20x10x5 box; PNG non-blank; the three views differ), plus the negative control (outside file must be refused) per binary, with the outside file under `/var/tmp` not `/tmp` when `/tmp` is granted. Budget the added start time in P7. **Phase:** P6.

### Pitfall 26: Fixtures from one generator
**What goes wrong:** Tests built from FreeCAD-authored boxes validate FreeCAD against itself. Real exporters (SolidWorks, Fusion, KOMPAS, CATIA) differ in headers, encodings, entity styles, units and surface-only output; proprietary customer files cannot be committed.
**Prevention:** build a corpus in tiers: generated (FreeCAD, OCCT, ezdxf), hand-written quirk files (cp1251 header, no-newline IGES, binary STL with `solid` header, DXF with `999` comment), malformed/bomb files, and a few real open-licence models from public repositories with their licences recorded; keep a private operator corpus for the live gate, not committed. Use the corpus for measurement (Pitfalls 13, 18) as well, so timeouts and RSS come from representative files. **Phase:** P2 (quirk set), P7 (measurement corpus).

### Pitfall 27: Timeout measured on a toy, or copied
**What goes wrong:** The cost is a function of geometry, not bytes (OCR: per page, probe: per page, tex: per pass), and the old pattern of "p95 of a percentile" can measure the corpus rather than the engine.
**Prevention:** measure AT the input bound on the worst-case corpus file (the tectonic method: derive `ceil(rate x bound x 1.5)` and pair the timeout inseparably with its input bound), verify that the document the measurement used is not above the ceiling that refuses it (v1.14 found 2.2% above), publish the measurement, not the rate, and keep chart grace at least the timeout. Timeout stays terminal. **Phase:** P7.

### Pitfall 28: Wiring omissions that derived guards will find late
**What goes wrong:** A tenth class touches: `CHECK` constraint (already has `cad` and `render`, per SEED-005), `AllConvertQueues()` and the metrics collector, the 7-way (now 10-way) env invariant for `queue.NewClient()`-derived TTLs, reconciler routing `default` branch ("a future engine must add its own case"), `/v1/formats`, MCP surfaces, compose and chart ScaledObject (`minReplicaCount`, fallback), CI bake targets derived from docker-compose, and the `sandboxcoverage_test` AST scanner (any exec outside `engineExec` fails the build, which also catches the wrapper's helper exec if it is written in Go).
**Prevention:** copy the latest class (probe/tectonic) and let the derived tests drive; add `cad` to every list through `AllEngines()`-derived tables; rebuild ALL images from HEAD before any live gate. **Phase:** P6.

### Pitfall 29: Dev-environment hygiene specific to a heavy image
**What goes wrong:** Building FreeCAD/Mesa on OrbStack under a parallel compose stack has wedged the daemon four times; an aggressive `docker system prune` wiped the tesseract build cache and forced a full source rebuild (v1.10); an unpinned apt FreeCAD/f3d/mesa makes gates non-reproducible across days.
**Prevention:** sequential dispatch for live gates (project memory), disk-reclaim step documented before the build, record package versions in transcripts, pin the base image by digest. **Phase:** P1, P7.

## Minor Pitfalls

### Pitfall 30: Matplotlib/PySide imports at module scope
**What goes wrong:** `import matplotlib` builds a font cache on first use (several seconds) and writes under `$HOME`/`MPLCONFIGDIR`; some FreeCAD helper modules import it. Prevention: import only the four C modules; if anything pulls it in, set `MPLCONFIGDIR` into the job dir via `withEnv` and measure. **Phase:** P3.

### Pitfall 31: STEP/IGES entity-level surprises
**What goes wrong:** blanked (hidden) IGES entities and STEP construction/datum geometry inflate bbox; AP242 tessellated-only STEP has no B-rep (volume `none`); assemblies with external references (`DOCUMENT_FILE`/URLs) are ignored by OCCT but must not be followed by any helper. Prevention: report geometry-class counts in `result.json` and never resolve external references. **Phase:** P4.

### Pitfall 32: Output validation asymmetry
**What goes wrong:** Input is sniffed fail-closed, outputs are trusted. A PNG that is truncated, an STL whose `n` does not match the size, a JSON with `NaN`. Prevention: validate every output with the same machinery as inputs (PNG decode plus dimensions through `dimensions.go`, STL arithmetic test, JSON strict parse; the `%PDF-` output check is the precedent), delete rather than serve an unverifiable output (probe precedent). **Phase:** P3/P4.

### Pitfall 33: Log and message volume
**What goes wrong:** OCCT/FreeCAD can print megabytes of diagnostics on a pathological file; `tailBuffer` bounds memory but the error string can still contain engine text that reaches clients. Prevention: never forward engine text; map to the closed `errcode` vocabulary (v1.13 contract, the no-text-matching tests apply). **Phase:** P3/P6.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Xvfb + `xvfb-run` because it already worked once | No renderer work | `/tmp` rw grant, concurrency 1, stale locks, orphans, abstract-socket exposure | Only after P1 measured "no X" as worse, and only with the wrapper-managed lifecycle |
| Return `Shape.Volume` raw | One line | Wrong prices from open shells and surfaces | Never |
| Hard-code `unit: "mm"` | Simple JSON | Silent 25.4x errors for DXF/STL and inch sources | Never |
| Broaden grant to `/usr/lib` + `/usr/share` to make Python start | Fast green | A confinement that confines nothing; hides the real read set | Never (class must meet the necessity-by-removal bar) |
| Reuse `engineEnv` unchanged | No shared-code change | Qt/Mesa/Python knobs silently missing, wrong HOME | Never; extend via per-class `withEnv` like tectonicEnv |
| Hash goldens for PNG/STL | Easy assertions | Flaky across arch/Mesa; trains people to regenerate | Never for renders; fine for the validator's own byte fixtures |
| Copy a neighbour class's timeout/concurrency | Fast wiring | Unmeasured OOM or timeout (pandoc concurrency 2 guaranteed OOM) | Never |
| One JSON schema with no version | Fewer fields | Breaking consumers (pricing) later | Never; `schema: 1` from the start |
| DXF->PDF via whatever FreeCAD offers | No second binary | Feature silently absent or wrong | Only if the P1 spike proves it headless on 0.20.2 |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| `engineExec` / `engineEnv` | Assume env passes through; Qt/Mesa/Python vars vanish | Per-class `withEnv` extras (tectonicEnv precedent); HOME/TMPDIR/MPLCONFIGDIR into the job dir |
| `runCommandCore` | Rely on the group kill after normal exit; ignore pipe-holding grandchildren | Supervise helpers inside the wrapper, redirect their output to files, tini as PID 1 |
| Landlock helper | Trace as root, execve targets, lazy Python imports | Image user, `-ff`, full format x operation matrix, add executables by hand, prove by removal |
| Sniffers / `inspect` | Add CAD detectors in only one of the two paths | One shared ordered detection, table test through both endpoints |
| Registry / aliases | `stp`, `igs` not normalized; `Register` panics on collisions | `NormalizeFormat` entries plus pair rows in the same commit; `pairs_disjoint_test` |
| Job outputs / roles | New role not in CHECK or `handleGetJob` role selection | Migration plus derived completeness test; both-or-neither outputs |
| asynq retry | Crashes retried 3x at full timeout | Signal strings and wrapper codes into `isCADTerminal`, same commit as the new error strings |
| KEDA | Stale API image lacks `QueueCAD`; cold pull ignored | Rebuild from HEAD preflight; `keda.cad.minReplicaCount`; measure pull |
| SSE/webhook/progress | Invent CAD progress | Reuse the unchanged v1.9 machinery; a single-shot job reports null to 100 like single-image OCR |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| STEP text to OCCT graph RAM multiplier | `OOMKilled`, `signal: killed` | Measured RSS per MiB, `CAD_MAX_INPUT_BYTES`, concurrency 1 | Real assemblies of tens of MiB |
| Fixed tessellation deflection | Huge STL, slow render | Deflection relative to bbox diagonal, triangle cap | Very large or very detailed models |
| Instancing (NAUO/MINSERT) | Hang with tiny input | Occurrence/entity-count guards | Adversarial or generated assemblies |
| llvmpipe thread count from host | CPU throttling, jitter | `LP_NUM_THREADS` from cgroup, or no GL | Any node with more cores than the pod quota |
| OCCT/TBB thread count from host | Slower under quota, nondeterminism | `sched_setaffinity` from cgroup `cpu.max`, single-thread mesher | Nodes with many cores |
| FreeCAD import cost per job | 3-8 s floor on trivial jobs (to measure) | Import only the C modules; accept as the floor and put it in the timeout derivation | Every job, worst on scale-from-zero |
| Cold image pull | Minutes to first job | Size budget, `minReplicaCount`, pre-pull | First job after idle on a fresh node |
| Output size explosion (STL/SVG) | Large uploads, slow webhooks | Caps on what is stored; entity caps for SVG | Dense models/drawings |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Serving generated SVG inline | Stored XSS via `<script>`, event attributes, external `href`s from DXF text | Escape all text, validate with an XML parser, strip active content; deliver as attachment; checker broader than generator |
| Trusting DXF/STEP external references | LFI/SSRF-style reads (`XREF`, IMAGE, `DOCUMENT_FILE`) | Never resolve; Landlock denies reads outside the job dir; test that a reference to `/etc/passwd` yields nothing |
| Interpolating opts into Python | Code execution inside the confined engine | Fixed script, JSON opts file, closed enums |
| Wide `/proc` or `/usr` grant for Python | Reads of other processes' `cmdline`/`status` (measured to open under `ro:/proc`) | Narrow grant by removal; measure N3-style canary for cad |
| Abstract-socket X server | Landlock does not mediate abstract sockets before ABI 6 | Avoid Xvfb, or `-nolisten` everything and rely on netns isolation |
| Engine text in client errors | Leaks paths/versions | Closed `errcode` vocabulary, never forward stderr |
| DWG accepted by accident | Out-of-scope proprietary parser path | Early signature rejection with an explicit code |

## "Looks Done But Isn't" Checklist

- [ ] **Sniffers:** pass on FreeCAD-made files only: verify cp1251 STEP/DXF, newline-less IGES, binary STL with `solid` header, `999`-comment DXF, binary DXF, DWG, truncated STEP/IGES/DXF each with a distinct code.
- [ ] **Differential:** validator verdict equals the real reader's verdict across the quirk corpus, with a divergence table.
- [ ] **Grant set:** necessity proven by one-at-a-time removal for EVERY (format x operation); an outside-file read fails per binary; measured as the image user.
- [ ] **Render:** judged by pixel content and three-view difference, not file size; flat part, top view, 1e-3 and 1e6 scale tested.
- [ ] **Volume/units/bbox:** open shell gives `null`; inch and mm fixtures give equal mm bbox and different `unit_origin`; bbox independent of meshing order; `allow_nan=False`.
- [ ] **Kill:** timeout kill leaves zero surviving processes and zero residue in `/tmp` and the job dir; `Wait` returns promptly; a crasher is terminal, not retried.
- [ ] **Bombs:** self-referencing STEP, deep assembly, `MINSERT` bomb, cyclic DXF blocks, binary STL with huge `n`, `1e300` coordinates all end in a coded terminal failure within bounds.
- [ ] **Outputs:** both-or-neither atomicity inversion-tested; role in enum, CHECK, `handleGetJob`; PNG/STL/JSON validated before being served.
- [ ] **Determinism:** two runs byte-identical (JSON, STL); cross-arch compared with tolerances and a divergence table.
- [ ] **Image and scale-from-zero:** size and cold-pull numbers recorded; first job from zero measured; all images rebuilt from HEAD before the gate.
- [ ] **Preflight:** one case per format family plus negative control per binary, content-judged.
- [ ] **SVG/PDF output:** round-trips `&<>"'` text; no active content; produced by a binary that is in the grant set.
- [ ] **Versions recorded:** FreeCAD, OCCT, renderer/Mesa/LLVM, Python, arch in every transcript.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Sniffer false rejects (cp1251 etc.) | LOW | Loosen envelope for CAD only; add fixture; no data migration since 422 happens before S3 |
| Wrong volume/unit shipped to consumers | HIGH | Bump `schema`, add `volume_status`/`unit_origin`, notify consumers (internal, so direct), re-render affected jobs from S3 within TTL |
| Xvfb locks/orphans in production | MEDIUM | Sweep extension, tini, restart policy; longer term replace the renderer |
| Grant set too narrow (lazy Python import) | MEDIUM | Re-measure with the missing format/operation, add the entry with its removal evidence; classify as engine fault so affected jobs retry |
| OOM on real files | MEDIUM | Lower `CAD_MAX_INPUT_BYTES` (Path-B), concurrency 1, relative deflection; derive from the OOM measurement, not a guess |
| Image too large for scale-from-zero | HIGH | Switch route (source headless build or OCCT bindings), `minReplicaCount: 1` as an interim lever |
| Role/outputs inconsistent | MEDIUM | Reconciler/ops query for `done` jobs with one output, re-run; add the atomicity fix and inversion test |
| DXF->PDF not feasible with FreeCAD | MEDIUM | Ship DXF->SVG only, add the second tool in a later phase with its own measured grant set |
