## Finding: Go defaults drifted from the measured truth (fixed in this audit)

`cmd/pandoc-worker/main.go` still encoded the belief the live gates disproved:

- `PANDOC_WORKER_CONCURRENCY` defaulted to **2**, with a comment asserting pandoc is "fast/light ... unlike the 1-at-a-time heavy OCR/AV/audio engines". The measurement says the opposite: pandoc is CPU-fast but **memory-heavy**, and two parallel worst-case conversions peak at 1022 MiB anon of 1024 in the deployed 1Gi container. Lowered to **1** with the measured rationale inline.
- `PANDOC_ENGINE_TIMEOUT`'s comment still described the 90s fallback as a placeholder awaiting "Phase 49's supervised measurement run" — that run has since happened and produced 65s. Comment updated to state the measured value and its conditions.
- `PANDOC_MAX_INPUT_BYTES`'s 50 MiB default is retained (it is the unconstrained-host default), but now documents that both deployed configs override it to 3 MiB and why (~300 MiB anon per MiB of input).

Deployment impact: **none** — compose and the chart both set all three explicitly, so no running configuration changed. This closed a latent trap for any path that runs the worker without env (bare `go run`, or a future deploy target that forgets the ConfigMap).

## End-to-End Flow

Upload markup → API validates + content-sniffs + enqueues to the `pandoc` queue → `cmd/pandoc-worker` consumes → converts under the measured timeout → uploads result → status `done` → presigned download + signed webhook. Every hop exists in code, and both ends are live-proven: Phase 49's `TestPandocConversionE2E` (md→html + md→docx + HMAC-verified webhook against the real compose stack) and Phase 50's cluster gates (SC3 scale-from-zero 12/12, SC4 downscale-survival 35/35).
