# Requirements: OctoConv — v1.12 Consumer Accounting & Fairness

**Defined:** 2026-08-02
**Core Value:** Внутренние сервисы компании могут безопасно и надёжно поставить задачу конвертации файла и получить результат — без риска для стабильности или безопасности продакшена.

**Milestone framing:** конвертация работает семь раз подряд. Чего платформе не хватает — знать своих потребителей: кто сколько потребляет, в каких границах, и как не дать одному выжрать класс движка целиком. Учёт здесь ради эксплуатации и справедливости, **не ради биллинга**.

## v1 Requirements

### Attribution & Accounting

- [x] **ACCT-01**: Оператор видит исходы джоб в разрезе клиента в Prometheus — через ОТДЕЛЬНЫЙ counter с меткой `client_id`. Метка НЕ добавляется в гистограмму `octoconv_job_duration_seconds` (она уже даёт ~250 серий и умножилась бы) и НЕ затрагивает `octoconv_queue_depth` — единственную метрику, которую читает KEDA.
- [x] **ACCT-02**: Потребление каждого клиента накапливается в Postgres как суточный rollup (число джоб, байты на входе/выходе, разбивка по классам движка), записываемый в той же guarded-transition точке, где сегодня фиксируется исход джобы.
  - **Ограничение (добавлено 2026-08-02, SEED-017):** байты суммируются по ВСЕМ входам и выходам джобы (`Repo.Inputs`/`Repo.Outputs`, уже есть в `repo.go` с сортировкой по `ordinal`), а не читаются с ordinal 0. Сегодня джоба всегда один вход и один выход, поэтому «взять ordinal 0» — естественное и работающее решение; писать так нельзя. Колонка `ordinal` есть в схеме с `0001_init.sql`, а SEED-017 (разбор/склейка PDF) — первый конкретный спрос на N: один разбор даёт N выходов из одного входа. Зашитое соотношение 1:1 сделает подсчёт байт молча неверным в тот же день и потребует переписывания учёта — ровно тот дрейф, на котором проект уже дважды терял время в v1.11. Суммировать по спискам сейчас не стоит ничего.
- [x] **ACCT-03**: Учёт идемпотентен: повторная постановка джобы реконсилятором или ретрай asynq не приводят к двойному счёту. Одна джоба учитывается ровно один раз.
- [x] **ACCT-04**: Кардинальность меток ограничена явным численным потолком числа различимых клиентов с задокументированным поведением при его превышении — не «надеемся, что клиентов мало».

### Quotas & Enforcement

- [ ] **QUOT-01**: Оператор может задать клиенту лимиты потребления. Отсутствие лимита выражается как `NULL` = безлимит, а НЕ большим числом-заглушкой (у проекта дважды была потеря на дрейфующих sentinel-значениях).
- [ ] **QUOT-02**: Лимит проверяется fail-closed на КАЖДОМ пути создания джобы — REST-хендлер, `cmd/mcp-server` (stdio) и `cmd/mcp-http`, — до записи в S3 и до постановки в очередь.
- [ ] **QUOT-03**: Превышение лимита отвергается кодом **429** с `Retry-After`, а не 403: квота — это ограничение потребления, а не граница авторизации. Тело ошибки машинно отличает `quota_exceeded` от уже существующего `rate_limited`, потому что ждать надо принципиально разное время.
- [ ] **QUOT-04**: Есть observe-only режим: лимиты вычисляются, логируются и отражаются в метриках, но не отвергают запросы. Ни один существующий потребитель сегодня не умеет обрабатывать отказ по квоте — включать enforcement вслепую нельзя.
- [ ] **QUOT-05**: Счётчик квоты корректен при нескольких репликах API — атомарно в Postgres, а не in-process. Существующий `internal/ratelimit` сам документирует, что верен только при `api.replicas: 1`; повторять это в квотах нельзя.

### Fairness

- [ ] **FAIR-01**: На клиента действует потолок одновременных джоб в классе движка, дающий структурную гарантию: при потолке K и `maxReplicaCount` M клиент занимает не более K из M слотов. Один потребитель не может голодом заморить остальных.
- [ ] **FAIR-02**: Семантика `octoconv_queue_depth` и PromQL всех семи `ScaledObject` остаются неизменными — scale-from-zero продолжает работать ровно как раньше. Это проверяется, а не предполагается.

### Operator Visibility

- [ ] **OPSV-01**: Оператор может получить ответ на «кто сколько потребил, по классам движка, за период» через эндпоинт, закрытый существующим механизмом `OPERATOR_CLIENT_IDS`.
- [ ] **OPSV-02**: По каждому клиенту видно текущее состояние лимитов и остаток — чтобы лимиты можно было выставлять по данным, а не наугад.

### Data Retention

- [x] **RETN-01**: Рост учётных и жизнециклических данных ограничен политикой хранения. Сегодня строки `jobs`/`job_events` не удаляются никогда — TTL есть только у объектов в S3 через MinIO ILM. Строить учёт поверх неограниченно растущих таблиц значит повторить уже имеющийся долг.

### Capacity Policy

- [ ] **CAPA-01**: `minReplicaCount` настраивается для каждого класса движка вместо жёстко зашитого нуля, чтобы под устойчивой нагрузкой можно было убрать холодный старт (SEED-011).

## v2 Requirements

Отложено намеренно, с причинами.

### Fairness

- **FAIR-V2-01**: Справедливость через суб-очереди на клиента или weighted-планировщик. **Evidence-gated:** этот дизайн переименовывает очереди, а значит ломает PromQL всех семи `ScaledObject`, `AllConvertQueues()`, коллектор глубины очереди и роутинг реконсилятора — то есть весь контракт scale-from-zero. Возвращаться к нему только если данные из OPSV-01 покажут, что admission-control потолка (FAIR-01) реально не хватает.
- **FAIR-V2-02**: Тиры приоритета между клиентами (не просто анти-голодание). Единственный реальный путь в asynq — дополнительные именованные очереди на класс движка, что удваивает число ScaledObject'ов.

### Accounting

- **ACCT-V2-01**: Учёт машинного времени (CPU-секунды) сверх wall-time — требует инструментирования воркеров, оправдано только если появится вопрос распределения ёмкости между командами.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Биллинг, инвойсинг, per-MB прайсинг | Сервис внутренний; учёт нужен для эксплуатации и справедливости, а не для монетизации |
| Self-service портал и регистрация клиентов | Клиенты — внутренние сервисы, заводятся оператором; портал решает задачу, которой нет |
| Полноценный weighted-fair-queueing планировщик с динамическими очередями на клиента | Избыточен при пуле в 2 пода на класс и 1-2 джобы на под; ломает контракт KEDA (см. FAIR-V2-01) |
| ML/anomaly-based троттлинг | Нет данных для обучения и нет проблемы, которую он решал бы лучше явного потолка |
| Формальные SLA-тиры и гарантии | Требуют организационного контракта, которого у внутреннего сервиса нет |
| Внешний distributed rate-limiter как зависимость | Postgres уже в hot path каждого создания джобы и даёт атомарность бесплатно |
| Redis как источник правды для квот | Redis в этом проекте контрактно транзитный брокер; квота должна переживать его потерю |

## Open Decisions

Требуют решения в фазе, а не по умолчанию:

1. **Форма учётной таблицы** — отдельный суточный rollup или достаточно существующего индекса `jobs_client_created_idx (client_id, created_at DESC)` для базовой отчётности. Решается в фазе, создающей схему (ACCT-02), с замером на реальном объёме.
2. **Состав лимитов** — какие именно измерения ограничивать (параллельные джобы, суточный объём байт, доступные классы) и какие из них реально защищают пул воркеров, а какие только выглядят полезными.
3. **Длительность observe-only периода** и критерий перехода к enforcement (QUOT-04).
