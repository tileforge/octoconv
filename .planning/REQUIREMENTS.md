# Requirements: OctoConv v1.13 "Inspect & Operations"

**Defined:** 2026-08-07
**Core Value:** Внутренние сервисы компании могут безопасно (через аутентификацию по API-ключу) и надёжно поставить задачу конвертации файла и получить результат — без риска для стабильности или безопасности продакшена.

**Milestone goal:** превратить OctoConv из конвертера форматов в processing API — ввести измерение «операция» с двумя первыми не-конвертерными возможностями (`inspect`, `sanitize`) и убрать ×7 тариф, который сегодня платит каждая сквозная забота.

**Locked decisions (приняты до определения требований):**

| Решение | Обоснование |
|---|---|
| `inspect` — **синхронный** `POST /v1/inspect`, не джоба | Весь смысл — решить ДО того, как ставить дорогую джобу. Цена принята сознательно: путь минует квоты, учёт, реконсилятор, webhook и SSE, поэтому обязан нести собственные границы (INSP-05) и доказать изоляцию живым гейтом (INSP-06) |
| `sanitize` — **новое значение** `operation='sanitize'`, движок `probe` | Глагол называет то, что делает. `extract` соврал бы (sanitize ничего не извлекает) и занял бы значение, нужное по назначению в Document-волне. `probe` зарезервирован в схеме с `0001`; восьмой класс — дёшево и прецедентно (доказано v1.10, v1.11) |
| **SEED-010 не берём** — третий отказ | Динамический capability-реестр экономит дешёвое (добавление движка по 4-фазному шаблону) ценой compile-time allowlist того, что вообще может быть выполнено. Тот же аргумент распространён на перечни кодов ошибок и находок: они закрытые и версионированные, не runtime-обнаружимые |
| SEED-021 берём **только Opportunity 1** (маршрутизация) | Opportunity 2 (постраничная классификация Mixed-PDF) по признанию самого семени не имеет решённого merging-контракта. Спайк, не фаза |
| Sanitize — **таргетированное удаление**, не rasterize-and-rebuild | Dangerzone-подход строго сильнее по гарантии, но лоссовый по построению (текст становится OCR-приближением, формы — растром) и несовместим с рамкой `pdf→pdf`/office→office. Легитимный будущий режим, но обязан называться иначе |

## v1 Requirements

### JobRunner (RUNR)

- [ ] **RUNR-01**: Все семь конверсионных хендлеров исполняются одним code-path — `Runner` поверх `EngineDescriptor`, где пер-энджинные различия (таймаут, лимит входа, opts-схема, retry-классификация, unique-lock TTL, progress-репортинг) выражены данными, а не ветвлением. `HandleWebhookDeliver` остаётся нетронутым — другая форма (retry/dead-letter семантика)
- [ ] **RUNR-02**: Терминальный исход задачи эмитится ровно одним вызовом в ровно одном месте, и структурно невозможно выстрелить им до коммита транзакции. Включает исправление живого дефекта `internal/reconciler/reconciler.go:311-312`, где `RecordReconcilerAction("exhausted")` инкрементится безусловно — тот же класс, что ревью PR #4 нашло в семи местах и не заметило здесь
- [ ] **RUNR-03**: Рефакторинг не меняет наблюдаемого поведения ни одного из семи классов: стадийная асимметрия retry-классификации сохранена (в частности противоположные полярности `isAudioTerminal` и `isAVTerminal` — дескриптор моделирует `(стадия, таймаут)`, а не `(движок, таймаут)`), закреплена пиннинг-тестами на все семь; метки `octoconv_job_duration_seconds{engine,status}` и `octoconv_queue_depth{queue,state}` не изменились, доказано диффом

### Structured error codes (ERRC)

- [ ] **ERRC-01**: Каждый терминальный отказ джобы и каждый клиентский 4xx несёт стабильный машиночитаемый `code` из закрытого версионированного перечня; одинаковый класс отказа даёт одинаковый код независимо от движка; конверт ответа расширяем, поэтому добавление стандартных полей позже не будет ломающим изменением
- [ ] **ERRC-02**: Терминальные отказы `invalid_options` учитываются в `octoconv_job_outcomes_total` и `octoconv_client_job_outcomes_total` — гэп закрыт в одном месте, а не добавлением счётчиков в шести скопированных
- [ ] **ERRC-03**: Ни один существующий потребитель (референсный фронтенд, `cmd/mcp-server`, `cmd/mcp-http`) не различает отказы по тексту сообщения — все переведены на коды, и это проверено, а не заявлено

### Operation dimension (OPRN)

- [ ] **OPRN-01**: Клиент может указать `operation` при создании джобы; отсутствие поля означает `convert`, и существующий клиент не наблюдает НИ ОДНОГО изменения — включая байт-идентичный ключ `engines` в `GET /v1/formats` (новое дерево операций добавляется отдельным ключом)
- [ ] **OPRN-02**: Реестр разрешает движок по тройке `(operation, from, to)`; `sanitize` с совпадающими исходным и целевым форматом (`pdf→pdf`) не коллизирует с convert-парой и не может быть выбран вместо неё
- [ ] **OPRN-03**: Неподдерживаемая тройка `(operation, from, to)` отклоняется 422 с машиночитаемым кодом до записи в S3 и до создания строки джобы — fail-closed, как и сегодняшняя проверка пары

### Output roles (ROLE)

- [ ] **ROLE-01**: `job_outputs` несёт роль выхода (`primary`/`report`/`preview`/`thumbnail`) через аддитивную миграцию с дефолтом `primary` — существующие строки корректны без backfill
- [ ] **ROLE-02**: `GET /v1/jobs/{id}` возвращает все выходы джобы с их ролями, и для одновыходной convert-джобы ответ остаётся байт-идентичным сегодняшнему. Закрывает живой дефект `internal/api/handlers.go:857-870`, где `outs[0]` презайнится без учёта роли — иначе отчёт sanitize может быть отдан как основной результат

### Synchronous inspection (INSP)

- [ ] **INSP-01**: Клиент может отправить файл в `POST /v1/inspect` и получить в теле ответа определённый по magic bytes формат (никогда по расширению) и характеристики, применимые именно к этому формату — размер всегда; страницы для PDF/office; длительность, разрешение и заявленный кодек для медиа; пиксельные размеры для изображений
- [ ] **INSP-02**: Отчёт содержит типизированный список находок из закрытого перечня — код, уровень серьёзности и, где осмысленно, местоположение: макросы OOXML, JavaScript и action-словари PDF, вложенные файлы, внешние ссылки, шифрование, признаки decompression bomb, legacy/зашифрованный OLE-CFB
- [ ] **INSP-03**: Отчёт никогда не переоценивает свою полноту: каждая заявленная проверка имеет трёхзначный статус (проверено-чисто / неприменимо к формату / не удалось определить), а отчёт, полученный под потолком работы, явно помечен как выборочный с указанием охвата
- [ ] **INSP-04**: Отчёт перечисляет доступные для этого файла `(operation, target)` с обслуживающим движком, оценкой длительности и проверкой против текущей квоты клиента — то есть отвечает «пройдёт ли эта джоба и сколько займёт» одним запросом
- [ ] **INSP-05**: Синхронный путь ограничен явно и независимо от v1.12 admission-гейта, который он минует по построению: потолок работы, потолок тела запроса, собственный rate-бюджет, отказ машиночитаемым кодом. Результат inspect не даёт оснований пропустить fail-closed проверки при последующем создании джобы — inspect ничего не пинит (TOCTOU)
- [ ] **INSP-06**: Изоляция процесса доказана живым гейтом, а не допущением: залп патологических inspect-запросов против живого API не выводит `/healthz` за liveness-порог, evidence закоммичен и перепроверяем

### Born-digital PDF routing (BDPD)

- [ ] **BDPD-01**: Отчёт inspect сообщает, содержит ли PDF пригодный текстовый слой, с честной пометкой выборочности по INSP-03
- [ ] **BDPD-02**: Born-digital PDF перестаёт быть тупиком: клиент получает осмысленный маршрут вместо слепого прогона через Tesseract или отказа, и вводящий в заблуждение комментарий `internal/convert/ocrguards.go:227-228` (советующий движок, который pdf на вход не принимает) исправлен

### Sanitize (SANI)

- [ ] **SANI-01**: Клиент может отправить PDF с `operation=sanitize` и получить тот же документ без JavaScript, action-словарей (`/OpenAction`, `/AA`), launch-действий, вложенных файлов и внешних URI-ссылок
- [ ] **SANI-02**: Клиент может отправить OOXML-документ с `operation=sanitize` и получить его без VBA-макросов (включая p-код, а не только исходник — защита от VBA stomping) и встроенных OLE-объектов, с корректно приведёнными `[Content_Types].xml` и relationship-ссылками
- [ ] **SANI-03**: EXIF/GPS/IPTC/XMP снимаются с изображений, а `/Info` и XMP — с PDF
- [ ] **SANI-04**: Чистота результата доказана, а не заявлена: выход проверяется **независимой** реализацией разбора (не тем же кодом, что удалял), удалённое физически отсутствует в выходных байтах (полная перезапись, а не incremental update, оставляющий объект восстановимым в предыдущей ревизии), и остаток любого признака — fail closed до записи в S3
- [ ] **SANI-05**: Клиент получает вторым выходом с `role=report` перечень того, что было найдено и удалено; формулировки описывают проверенные и удалённые классы угроз и НЕ заявляют общей свободы от вредоносного содержимого
- [ ] **SANI-06**: `probe` — восьмой engine-класс в полном контуре по отлаженному шаблону: своя очередь, `cmd/probe-worker`, свой контейнер, ИЗМЕРЕННЫЙ (не скопированный) таймаут, fail-closed валидация входа, transient/terminal классификация, ScaledObject — аддитивно, с нулевым диффом к существующим семи

### v1.12 debt tail (DEBT)

- [ ] **DEBT-09**: Оператор может снять застрявшую in-flight джобу штатным средством, а не сырым SQL, и связка «доступность квот ↔ здоровье `cmd/webhook-worker`» задокументирована (52 WR-01 — самый весомый перенос v1.12: навсегда застрявшая джоба блокирует суточный бюджет клиента каждый следующий UTC-день)
- [ ] **DEBT-10**: Секция квот в README непротиворечива, и список engine-классов выводится из `convert.AllEngines()`, а не хардкодится числом (52 WR-09)
- [ ] **DEBT-11**: `PurgeUsage` берёт cutoff из часов Postgres, как `evaluate()`, `recordUsage` и `UTCToday`, а не из `time.Now()` хоста (`internal/jobs/retention.go:126`)

## v2 Requirements

Отложено осознанно, с причинами.

### Inspection & routing

- **INSP-V2-01**: Постраничная классификация и маршрутизация Mixed-PDF (SEED-021 Opportunity 2) — семя само фиксирует нерешённый merging-контракт (порядок страниц, недублирование, асимметрия Markdown vs hOCR/ALTO). Спайк, не фаза
- **INSP-V2-02**: Точная детализация кодеков/профилей (H.264 profile/level, формат сэмплов AAC) в синхронном пути — требует `ffprobe` в контейнере API, а API-процесс никогда не вызывал подпроцесс. Inspect сообщает ЗАЯВЛЕННЫЙ кодек, как `dimensions.go` сообщает заявленные размеры
- **INSP-V2-03**: Клиентски настраиваемые границы выборки inspect
- **INSP-V2-04**: `plan_only` — построение pipeline без запуска обработки (из Notion-волны). Осмысленно только после SEED-018

### Sanitize

- **SANI-V2-01**: Rasterize-and-rebuild как альтернативный режим строго более высокой гарантии (Dangerzone-подход) — обязан быть отдельно названной операцией, никогда не молчаливой подменой таргетированного sanitize
- **SANI-V2-02**: «Чтение» половина SEED-013 — метаданные как `operation=inspect` на движке `probe`. Ограничение раскрыто заранее: гранулярность `client_usage_daily` — `(client_id, engine, day, status)` без операции, поэтому две probe-операции стали бы неразличимы в учёте и в `GET /v1/system/usage`
- **SANI-V2-03**: Accessibility/PDF-UA проверки, Repair, Comparison (из Notion-волны)

### Errors & contract

- **ERRC-V2-01**: Перевод существующих 429-тел (`quota_exceeded`, `rate_limited`) в новый конверт — сегодня они уже машиночитаемы, поэтому не блокируют; консистентность догоняется следующим шагом
- **ERRC-V2-02**: Публикация перечня кодов в `docs/openapi.yaml` как версионированного контракта

### Platform

- **OPRN-V2-01**: Составные pipeline (SEED-018) — parent/child jobs, снимок pipeline у родителя, агрегация статуса/прогресса/выходов. Следующий шаг после того, как операций станет больше одной
- **OPRN-V2-02**: N входов / N выходов (SEED-017, PDF split/merge) — учёт байт под это уже построен в v1.12 (суммирование по ВСЕМ ordinal), но `role` и `operation` должны сначала устояться
- **OPRN-V2-03**: `operation` в гранулярности `client_usage_daily` — понадобится, когда на одном движке появится вторая операция

## Out of Scope

Явно исключено. Причины записаны, чтобы не пересматривать по кругу.

| Feature | Reason |
|---------|--------|
| Динамический capability-реестр / самрегистрирующиеся воркеры (SEED-010) | Третий отказ с тем же аргументом: экономит дешёвое (добавление движка по отлаженному 4-фазному шаблону) ценой compile-time allowlist того, что вообще может быть выполнено. Распространяется и на перечни кодов ошибок и находок — они закрытые и версионированные |
| Открытый runtime-обнаружимый namespace кодов ошибок/находок | Тот же аргумент: баг или спешный PR молча ввёл бы новую машиночитаемую контрактную поверхность без ревью, и «документированный перечень» потерял бы смысл |
| Заявление, что выход sanitize свободен от вредоносного содержимого | Ложная гарантия. Индустрия прямо фиксирует, что CDR не определяет функциональность вредоносного кода и не покрывает большинство форматов изображений. Отчёт описывает проверенные и удалённые классы — и только их |
| Семантическая «починка» удалённого JavaScript форм | Ни один обследованный CDR-продукт не пытается реконструировать удалённое ПОВЕДЕНИЕ, только структуру. Попытка угадать безопасную замену возвращает code-execution-смежную поверхность внутрь санитайзера, созданного её убирать. Удаляем и сообщаем, какое поле затронуто |
| poppler / qpdf / mutool / ffprobe / exiftool в `Dockerfile.api` | API-процесс никогда не вызывал `runCommand`. Не открывать эту дверь синхронному, request-scoped пути, у которого нет очереди в качестве подстраховки при зависании подпроцесса |
| exiftool где бы то ни было | Perl-рантайм плюс задокументированная история RCE на разборе недоверенного ввода (CVE-2021-22204) — ради возможности, которую уже покрывают `vips[strip]` и `pdfcpu` |
| Ghostscript, pikepdf | AGPL-вопрос и лоссовая перезапись, не спроектированный санитайзер / Python-рантайм вокруг того же движка qpdf без единой дополнительной возможности |
| Байтовый скан PDF на `/JS` без разбора объектного графа | Ложноотрицательные против compressed object streams — тихий обход защиты, не косметический пробел |
| Принятие `firecrawl/pdf-inspector` как фазы | 0.1.x до 1.0, неизмеренный размер бинаря, отсутствие готовых dual-arch сборок и НОЛЬ пересечения с потребностью в risk-сигналах этого милстоуна. Спайк отдельно, по рекомендации самого семени |
| Переименование существующих очередей | Единственная действительно дорогая операция в KEDA-слое (7 PromQL + `AllConvertQueues()` + маршрутизация реконсилятора). v1.13 её не требует |
| Биллинг, публичная многоарендность, self-service портал квот | Сервис внутренний — зафиксировано в Constraints, не пересматривается |
