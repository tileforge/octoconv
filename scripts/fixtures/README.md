# Fixtures

Committed test/gate fixtures. Each generator listed below is deterministic
(byte-identical output on every run, no timestamps/randomness) and is
committed alongside the fixture it produces -- a fixture whose provenance
cannot be reproduced from a committed script is not a controlled input.

## Phase 58 (INSP-06/SC6) -- `inspect-burst-pathological.{pdf,docx,mp4}`

Committed fixtures for `scripts/inspect-burst-liveproof.sh` (the SC6 live
gate: a pathological burst of `POST /v1/inspect` requests must never cause
`/healthz` to fail six consecutive liveness probes). Each fixture targets a
specific CEILING inside `internal/inspect`'s byte/iteration bounds, not a
parser-correctness edge case -- per this plan's own framing, these fixtures
prove the RESOURCE bound holds, not that the parser is right about the
file's content.

Generated by:

```
python3 scripts/fixtures/gen_inspect_burst_pdf.py  --out scripts/fixtures/inspect-burst-pathological.pdf
python3 scripts/fixtures/gen_inspect_burst_docx.py --out scripts/fixtures/inspect-burst-pathological.docx
python3 scripts/fixtures/gen_inspect_burst_mp4.py  --out scripts/fixtures/inspect-burst-pathological.mp4
```

Each script is stdlib-only (`zipfile`, `struct`, `argparse` -- no
third-party package, matching this phase's own D-02 "zero new dependencies"
even at the fixture-generation layer, which is not part of the Go module at
all but is still worth holding to the same discipline).

### The gate's own ceiling overlay (why these fixtures are only 1-3 MiB, not 8-183 MiB)

`internal/api/api.go`'s DEFAULT `InspectMaxWorkBytes` is 8 MiB and the
shipped `INSPECT_MAX_UPLOAD_BYTES` is 183 MiB (`.env.example`,
`deploy/chart/octoconv/templates/configmap.yaml`). A fixture that must sit
strictly ABOVE the work ceiling and strictly BELOW the upload ceiling at
those defaults would need to be several tens of megabytes each --
technically committable, but far outside this plan's own "a few megabytes
total" instruction and needlessly slow to transfer during a burst whose
whole point is request VOLUME, not per-request payload size.

`deploy/chart/octoconv/values-inspect-gate.yaml` (Task 2 of this plan)
therefore LOWERS the gate run's own `INSPECT_MAX_WORK_BYTES` to 1 MiB
(1048576 bytes) via `api.extraEnv`, leaving `INSPECT_MAX_UPLOAD_BYTES`
at its 183 MiB default. Every fixture below is sized to sit strictly between
those two gate-run boundaries:

| Ceiling | Value | Source |
|---|---|---|
| `INSPECT_MAX_WORK_BYTES` (gate override) | 1,048,576 (1 MiB) | `values-inspect-gate.yaml` |
| `INSPECT_MAX_UPLOAD_BYTES` (unchanged default) | 191,889,408 (183 MiB) | ConfigMap default, restated explicitly in the overlay |

| Fixture | Actual bytes | > work ceiling (1,048,576)? | < upload ceiling (191,889,408)? |
|---|---|---|---|
| `inspect-burst-pathological.pdf` | 2,097,152 | yes (2.0x) | yes |
| `inspect-burst-pathological.docx` | 1,351,986 | yes (1.29x) | yes |
| `inspect-burst-pathological.mp4` | 3,145,728 | yes (3.0x) | yes |

Verified via `stat -f%z` (macOS):

```
$ stat -f%z scripts/fixtures/inspect-burst-pathological.pdf scripts/fixtures/inspect-burst-pathological.docx scripts/fixtures/inspect-burst-pathological.mp4
2097152
1351986
3145728
```

Total committed size across all three: ~6.4 MiB.

### `inspect-burst-pathological.pdf` -- 2,097,152 bytes

Targets `internal/inspect/pdf.go`'s token-scan (`scanTokenOccurrences`) and
its compression-signal downgrade (`containsCompressionSignal`):

- **`/ObjStm` present once**, near the head -- ISO 32000 Sec7.5.7 forbids
  encryption dictionaries and stream objects from living inside an object
  stream, so this project's byte scanner cannot see into one; its presence
  downgrades EVERY PDF risk-token verdict to `unknown/compressed_object_streams`
  (pdf.go's own file-level doc comment) rather than letting the scanner
  claim a false `clean`.
- **190,648 repeats of `/JavaScrip`** (the real risk token `/JavaScript`
  with its final byte cut off) -- a near-miss never matches
  `bytes.Contains`, so `scanTokenOccurrences` walks the FULL scanned window
  on every request instead of returning after an early real match. This is
  "tens of thousands" by a wide margin (the plan's own floor), chosen
  because the head window this fixture fills is itself close to a megabyte.
- **Valid `%PDF-1.7` signature** at offset 0 -- required for
  `convert.Sniff`'s `matchPDF` to route this upload to `AnalyzePDF` at all.

Observed (via `head -c 5` / `grep -c`):

```
$ head -c 5 scripts/fixtures/inspect-burst-pathological.pdf
%PDF-
$ grep -c '/ObjStm' scripts/fixtures/inspect-burst-pathological.pdf
1
```

Observed real-analyzer behavior (`inspect.AnalyzePDF` + `inspect.BuildReport`,
called directly with `maxBytes=1048576`, mirroring the gate's own
`INSPECT_MAX_WORK_BYTES` override and `dispatchInspectFamilies`'s own
`tr.Consume` accounting -- see "How this was verified" below):

- `characteristics.uses_compressed_object_streams = true`
- `characteristics.pdf_version = "1.7"`
- `characteristics.page_count = null`, `page_count_reason = "compressed_object_streams"`
- `findings = null` (none of the 190,648 near-miss repeats ever matches a
  real risk token -- confirms the fixture stresses the SCAN, not a false
  positive)
- every PDF-domain check (`pdf_javascript`, `pdf_action_dict`,
  `pdf_launch_action`, `pdf_embedded_file`, `pdf_encrypted`,
  `external_reference`, `metadata_present`) reports
  `status: "unknown", reason: "compressed_object_streams"` -- the
  downgrade fired, as designed
- `coverage.complete = true` -- see the "coverage note" below; this is the
  correct, honest value for a single-family dispatch, not an
  under-calibration of this fixture

### `inspect-burst-pathological.docx` -- 1,351,986 bytes

Targets `internal/inspect/container.go`'s central-directory scan
(`maxZipEntriesScanned = 4096`) AND `internal/api/inspect_handlers.go`'s
EARLIER, cheaper structural gate (`inspectMaxZipDirEntries * zipCentralDirMinRecordLen
= 4096 * 46 = 188,416` declared central-directory bytes) -- the two are
easy to conflate, and this fixture is sized specifically to exercise the
FIRST without tripping the SECOND (see the generator script's own header
comment for the full arithmetic: a real 4096-entry archive with non-empty
filenames trips the earlier gate almost immediately, since 46 bytes/entry
is the absolute floor with ZERO name bytes).

- **`word/document.xml` present** -- the ONLY signal
  `convert.SniffContainer` uses to set `Format = "docx"`
  (`docsniff.go`'s `ooxmlRootParts`); without it this upload reports as an
  unrecognized bare zip.
- **3,772 filler entries** (names `"0"` .. `"3771"`) + 6 real parts
  (`[Content_Types].xml`, `word/document.xml`, and 4 `.rels` candidates) =
  **3,778 total entries**, computed by the generator script itself (not
  hand-typed) to land the declared central-directory size at
  **187,895 bytes** -- just under the 188,416-byte earlier gate, so
  `AnalyzeContainer`'s own scan genuinely runs instead of being
  short-circuited by `zipDirectoryCeilingFamilyResult()`.
- **4 `.rels`-candidate parts** (`_rels/.rels`,
  `word/_rels/document.xml.rels`, `word/_rels/header1.xml.rels`,
  `word/_rels/footer1.xml.rels`), each **258,040 bytes** -- just under
  `maxRelsPartBytes` (256 KiB = 262,144), with `TargetMode="External"`
  placed in the last ~170 bytes of EVERY one of the four, so whichever part
  `archive/zip`'s central-directory order presents first to
  `appendExternalReferenceResult`'s scan (which stops at the FIRST match)
  gets read almost to its own ceiling before the match is found, regardless
  of scan order.
- **No macro part** (`word/vbaProject.bin` etc.) -- a macro finding matches
  on the FIRST central-directory entry naming it, which would short the
  scan this fixture exists to lengthen down to a handful of iterations.

Observed (via `unzip -l` / `unzip -p`):

```
$ unzip -l scripts/fixtures/inspect-burst-pathological.docx | grep -c 'word/document.xml'
1
$ unzip -p scripts/fixtures/inspect-burst-pathological.docx '*_rels/*.rels' 2>/dev/null | grep -c 'TargetMode="External"'
1
```

The second command's result (`1`) is `grep -c`'s LINE count, not an
occurrence count -- all four `.rels` parts are written with no internal
newlines, so `unzip -p`'s concatenated stdout across all four matched
files is one unbroken stream and `grep -c` counts it as a single "line
containing a match". Counting actual OCCURRENCES (there are genuinely 4,
one per part) requires `grep -o ... | wc -l`:

```
$ unzip -p scripts/fixtures/inspect-burst-pathological.docx '*_rels/*.rels' 2>/dev/null | grep -o 'TargetMode="External"' | wc -l
4
```

Both readings satisfy this plan's stated acceptance bar (`>= 1`); this note
exists so a future reader is not surprised the "line count" and the
"true occurrence count" diverge for a fixture built with no newlines.

Observed real-analyzer behavior (`inspect.AnalyzeContainer` +
`inspect.BuildReport`, `maxBytes=1048576`, `bombThreshold=200<<20` matching
`internal/api/inspect_handlers.go`'s `inspectZipBombFindingThreshold`):

- `characteristics.container_format = "docx"`
- `characteristics.declared_uncompressed_bytes = 1,036,622`
- `characteristics.has_macro = false`
- `findings = [{code: "external_reference", severity: "warning", location: "_rels/.rels"}]`
  -- the scan found the match in the FIRST candidate part in
  central-directory order (`_rels/.rels`, the root relationships part, added
  first by the generator), consistent with "stops at first match" and with
  every part carrying the marker near its own end regardless of which one
  is scanned first
- `checks: [{ooxml_macro: clean}, {zip_bomb_shape: clean}]` --
  `zip_bomb_shape` is `clean`, NOT a finding: `declared_uncompressed_bytes`
  (1,036,622, ~1 MiB) sits far below the 200 MiB
  `inspectZipBombFindingThreshold`. This fixture deliberately does NOT
  target the zip-bomb-shape finding -- see "What this fixture does not
  target" below.
- `coverage.complete = true`

### What this fixture does not target

The zip-bomb-shape finding (`CodeZipBombShape`) requires
`declared_uncompressed_bytes > 200 MiB` (`inspectZipBombFindingThreshold`,
`internal/api/inspect_handlers.go`). Reaching that with `archive/zip`'s own
declared-size accounting (trusted as-is by `convert.SniffContainer`,
`docsniff.go:86-90`, with NO verification against actual decompressed
bytes) would require either genuinely writing 200+ MiB of real payload (far
outside this plan's "a few megabytes, committed" budget) or hand-patching
the ZIP central directory's raw `UncompressedSize64` field after the fact
to lie about a size `archive/zip` never actually wrote -- the kind of
hand-crafted-binary provenance this plan's own constraint explicitly
prohibits ("never hand-crafted binaries whose provenance nobody can
reproduce"). This fixture instead stresses `maxZipEntriesScanned` /
`maxRelsPartsScanned` / `maxRelsPartBytes` -- the ceilings a
several-megabyte, honestly-generated fixture CAN actually reach.

### `inspect-burst-pathological.mp4` -- 3,145,728 bytes

Targets `internal/inspect/media.go`'s head-then-tail `moov` search
(`findMoov`) and its box-walk ceiling (`maxISOBMFFBoxes = 4096`).

- **4,096 minimal `free` boxes** (8 bytes each, header only) between `ftyp`
  and `moov` -- exactly `maxISOBMFFBoxes`, so `walkTopLevelBoxes`'s head-window
  scan consumes its full per-call step budget before concluding `moov` is
  not there, "maximizing steps within the ceiling" rather than past it.
- **`moov` at the file tail** (offset 3,145,464, 264 bytes, ending exactly
  at EOF) -- the realistic non-faststart shape `media.go`'s own doc comment
  names as the common case; forces `findMoov`'s STEP 2 tail-anchored
  fallback to actually run.
- **Valid `mvhd`/`tkhd`/`stsd`** inside `moov` (standard ISO/IEC 14496-12
  payload layouts, version 0) -- so duration/resolution/codec are genuinely
  EXTRACTED, not merely "moov was found".

Window arithmetic at the gate's `INSPECT_MAX_WORK_BYTES=1,048,576`
override (`media.go`'s `findMoov`: `headLen = min(maxBytes, size)`;
`tailLen = min(mp4TailWindow=2MiB, maxBytes, size)`;
`tailOff = size - tailLen`):

```
$ python3 scripts/fixtures/gen_inspect_burst_mp4.py --out /tmp/verify.mp4
Generated pathological MP4: /tmp/verify.mp4
total_bytes=3145728
free_box_count=4096 (mirrors maxISOBMFFBoxes)
moov_offset=3145464 moov_size=264
gate_head_window=[0,1048576) gate_tail_window=[2097152,3145728)
moov_within_tail_window=True
moov_within_head_window=False
```

head window = `[0, 1,048,576)`; tail window = `[2,097,152, 3,145,728)`;
`moov` at `3,145,464` is inside the tail window and nowhere near the head
window. The `[1,048,576, 2,097,152)` region (1 MiB) is never read by either
window -- the realistic shape of a large `mdat` payload no analyzer here
needs to see.

Observed (`grep` on binary content -- see the caveat immediately below):

```
$ tail -c 262144 scripts/fixtures/inspect-burst-pathological.mp4 | grep -ac moov
1
$ head -c 65536 scripts/fixtures/inspect-burst-pathological.mp4 | grep -ac moov
0
```

**Binary-`grep` caveat**: this plan's own acceptance criteria specify plain
`grep -c moov` (no `-a`). On this host's `grep` (BSD grep, macOS), running
`grep -c` against binary content with a genuine match prints NOTHING and
exits 1, rather than printing a count -- `grep -c` on a binary stream is
not portably numeric across `grep` implementations (GNU `grep` instead
prints `Binary file ... matches` unless `-a`/`--text` is given, which is
also non-numeric). `grep -ac` (force text mode) is what actually produces
the numeric count both criteria lines describe. Recorded here so a future
operator re-running this plan's literal acceptance commands is not
surprised by an empty result on a passing fixture; `scripts/inspect-burst-liveproof.sh`
does not depend on this shell idiom at all (it drives real HTTP requests
against the live API, never greps a fixture's raw bytes).

Observed real-analyzer behavior (`inspect.AnalyzeMedia("mp4", ...)` +
`inspect.BuildReport`, `maxBytes=1048576`):

- `characteristics.duration_seconds = 42` (from `mvhd`: `duration=42000`,
  `timescale=1000` -- `42000/1000 = 42.0`)
  `characteristics.width = 1920`, `characteristics.height = 1080` (from
  `tkhd`, 16.16 fixed-point decoded correctly)
- `characteristics.declared_codec = "avc1"` (from `stsd`'s first sample
  entry fourCC)
- `findings = null`, `checks` -- media.go publishes no
  domain-specific Finding/Check codes of its own; every characteristic
  above was genuinely extracted, proving `moov`/`mvhd`/`tkhd`/`stsd` were
  all correctly parsed after the tail-anchored search
- `coverage.complete = true`

### Coverage note (applies to all three fixtures)

All three fixtures report `coverage.complete = true` despite every one of
them sitting above the gate's `INSPECT_MAX_WORK_BYTES` override. This is
the CORRECT, honest value, not an under-calibration: `internal/inspect/report.go`'s
`buildCoverage` only flips `Complete` to `false` when (a) some individual
`Check` carries `Reason == ReasonWorkCeilingBytes` (none of ours do -- the
PDF's downgrade reason is `ReasonCompressedObjectStreams`, a DIFFERENT,
narrower "blind spot" reason, not a budget-exhaustion one), or (b) the
shared `Tracker` itself is `Exhausted()` (its own `Consume` call must
EXCEED the budget, not merely reach it exactly -- `internal/api/inspect_handlers.go`'s
`dispatchInspectFamilies` charges exactly one family's full allowance per
request today, landing AT the ceiling, never past it, for a single-format
upload). The size-above-work-ceiling sizing rule this plan requires still
matters -- it is what forces each analyzer's own INTERNAL head/tail
windowing to run selectively (PDF's `truncated` branch, MP4's
head-then-tail fallback, DOCX's bounded rels-part scan) -- it just does not,
by itself, flip the report-wide `Coverage.Complete` flag for a
single-family dispatch. Recorded here because a fixture's observed
behavior not matching an initial assumption is exactly the kind of gap this
plan's own honesty discipline exists to catch and write down, not paper
over.

### How this was verified

Each fixture was run, before commit, through the REAL analyzer functions
this project ships (`inspect.AnalyzePDF`, `inspect.AnalyzeContainer`,
`inspect.AnalyzeMedia`, `inspect.BuildReport`), called directly with
`maxBytes=1048576` (the gate overlay's own `INSPECT_MAX_WORK_BYTES`) via a
throwaway, NOT-committed `go run` script
(`//go:build ignore`, deleted immediately after use -- never part of this
commit) that mirrors `internal/api/inspect_handlers.go`'s own
`dispatchInspectFamilies` accounting (`tr.Consume(maxBytes)` after the
analyzer call, matching production's "charge the full allowance" rule).
The JSON emitted by that run is the source of every "Observed real-analyzer
behavior" block above -- transcribed, not estimated.
